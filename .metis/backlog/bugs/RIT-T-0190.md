# working_resume_tampered wedge after commit (reconcile does not clear)

## ⚠️ DECISION (2026-08-11, Daniel): SIMPLIFY — drop the out-of-band tamper detection

Daniel: "Let's simplify." Do NOT build the commit-vs-out-of-band baseline-advance machinery. Instead
REMOVE the sha256 tamper check (RIT-A-0001's 3rd gate) that causes the wedge — or reduce it to always
track the current working file so it can never wedge. The two truth-safety gates that matter
(logged-decision-by-path, refuse-CONTRADICTED) STAY intact. Net effect: open → edit → commit → open
again just works; no `working_resume_tampered`, no `reconcile` dance. Note this narrows RIT-A-0001's
stated gate set — record the change as an ADR addendum/update to RIT-A-0001 so the doc and code agree.

## Objective **[REQUIRED]**

Allow ITERATIVE editing: after an edit session commits changes to `working/*.tailored.json`, opening a
new session on the now-updated working resume must succeed. Today the second `open` fails with
`working_resume_tampered` because the tamper baseline hash is derived from the pristine `refine` source
rather than the current working file, and `reconcile` does not clear the condition — the only recovery
found was manually deleting `resume-kit/working/*.json`.

## Backlog Item Details

### Type
- [x] Bug

### Priority
- [x] P2 — Medium. It blocks multi-round editing and is confusing (looks like corruption), but a
  recovery exists (delete working files) and no data is lost. Touches the tamper-detection gate, which
  is safety-critical — must be fixed carefully, not by weakening the gate.

### Impact Assessment
- **Affected Users**: Anyone doing more than one edit session on the same resume (normal iterative
  tailoring). Discovered in the v0.15.2 black-box test run.
- **Reproduction Steps**:
  1. Open edit session, approve changes, commit → `working/<name>.tailored.json` is mutated.
  2. Open a NEW edit session on the active resume.
  3. Result: `working_resume_tampered` — the session refuses to open. `reconcile` does not clear it;
     only deleting `resume-kit/working/*.json` recovers.
- **Expected vs Actual**: Expected — after a legitimate commit, the tamper baseline advances to the
  committed working file, so the next `open` treats it as pristine. Or `reconcile` re-baselines it.
  Actual — the baseline hash stays pinned to the original `refine` source; the committed (legitimately
  changed) working file reads as tampered, and `reconcile` doesn't fix it.

### Root Cause (to verify against code)
- The tamper gate (sha256 baseline in the edit-session orchestrator, [[RIT-A-0001]] /
  `packages/facade/edit_session.py`) computes the "expected" working hash from the pristine
  refine/tailored SOURCE, not from the last committed working state. After a commit, the working file
  no longer matches that source hash → `working_resume_tampered`.
- `reconcile` (`edit_session_reconcile`) does not re-derive/advance the baseline to the current working
  file, so it cannot clear a post-commit wedge.

## Acceptance Criteria **[REQUIRED]**

- [ ] After a legitimate commit, a subsequent edit-session `open` on the same active resume succeeds
      (no false `working_resume_tampered`).
- [ ] Genuine out-of-band tampering (a hand-edit of the working file NOT via commit) is STILL detected
      — the gate is not weakened; only the post-commit baseline advance is fixed.
- [ ] `reconcile` can clear a legitimately-changed working file by re-baselining to it (with the same
      truth/gate protections), so manual deletion is no longer the only recovery.
- [ ] Regression test: open → approve → commit → open again succeeds; separately, an out-of-band edit
      is still flagged.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- On successful commit, advance the tamper baseline to the hash of the just-written working file so the
  next open compares against the committed state. Make `reconcile` re-baseline to the current working
  file behind the existing truth/gate checks.
- **Safety-critical (tamper detection, [[RIT-A-0001]]):** do not turn the gate into a no-op. The
  distinction to preserve is "changed BY a logged commit" (allowed) vs "changed out of band" (flagged).
  Confirm the intended semantics with Daniel if the commit-vs-out-of-band signal isn't cleanly
  available.

### Dependencies
- Edit-session orchestrator + hard write gate ([[RIT-A-0001]], [[RIT-T-0099]], [[RIT-T-0112]]),
  `reconcile` capability.

### Risk Considerations
- Weakening the tamper gate would defeat a core safety mechanism. Prefer advancing the baseline on
  logged commit over relaxing the comparison.

**Recommended Agent: opus + medium** — safety gate semantics; careful baseline-advance logic + tests.
