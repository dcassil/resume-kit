# Keyword hygiene gate: keep only concrete tokens out of the scored keyword denominator

## Objective **[REQUIRED]**

Stop full requirement sentences from polluting the keyword-scoring denominator.
The parse-job interpretation subagent sometimes emits prose (e.g. "4-6+ years of
professional experience building modern, large-scale web applications") as a
"skill". Today two code paths carry that prose into scoring:

1. `job-parser/parse._map_to_job_description` copies every skill string verbatim
   into `JobDescription.keywords` and into `Requirement.keywords=[text]`.
2. `matching/keywords._to_jd_keywords_dict` (the scoring boundary used by match,
   check-gaps, AND check-keywords) appends `req.text` — the FULL sentence — into
   `required_skills`, which becomes the denominator.

Because these unmatchable phrases sit in the denominator, the match score is
artificially depressed and the "missing"/"non-injectable" lists are cluttered
with sentences no resume would ever match. Introduce ONE deterministic keyword
hygiene gate that keeps only concrete tokens, applied at the scoring boundary
(load-bearing) and at parse time (keeps the stored artifact honest).

  1. Parse a job where a requirement sentence is classified as a required skill.

- **Expected vs Actual**: Expected — only concrete tokens are scored; prose is
  kept as requirement `text` for display but never as a keyword. Actual — prose
  counts against the score and clutters the gap lists.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Filter-only (NO comma-splitting): splitting prose on commas would turn a
  sentence into short fragments that falsely pass the word cap. Whole-entry
  concreteness filtering cleanly drops sentences (word count >> cap) while
  keeping array-element tokens, which is how the subagent emits skills.
- Heuristics: word cap ~6; regex for year clauses (`\d+ ... year`); regex for
  terminal sentence punctuation followed by whitespace/end (so "Node.js" is NOT
  rejected). All deterministic → identical inputs, identical output.
- Home in `schemas` because it is the lowest common dependency of both
  job-parser and matching (no layering inversion, single source of truth).

### Dependencies
Sibling of RIT-T-0126 (#4) and RIT-T-0127 (#2), same test-run triage. Independent.

### Risk Considerations
- Legit long skill phrases (>6 words) are rare; if dropped they were unlikely to
  match a resume verbatim anyway, so the denominator stays honest. Revisit the
  cap only if a real case surfaces.
- Dict-shaped inputs to `_to_jd_keywords_dict` (power-user/test path) are left
  as-is; only the `JobDescription` extraction path is gated, matching "enforce
  at extraction" intent.

**Recommended Agent: opus + medium** — spans two packages plus a new shared
module and the scoring boundary; the denominator invariant must stay correct.
