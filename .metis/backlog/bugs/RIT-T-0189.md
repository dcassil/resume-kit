# review-edits decide cannot disambiguate two changes on the same path

## Objective **[REQUIRED]**

Let a user decide (approve/reject/edit) each of MULTIPLE pending changes that target the SAME JSON path
within one edit session. Today `review-edits decide --path <p>` can only address the first change on a
path; a second change on the same path (e.g. two `add_skill` ops on `additional.technicalSkills`)
cannot be selected and errors with `wrong_section` ("current section is None").

## Backlog Item Details

### Type
- [x] Bug

### Priority
- [x] P2 — Medium. Workaround exists (one change per session), but it makes batch skill/terminology
  injection awkward and is surprising UX. Not a correctness/data-safety issue.

### Impact Assessment
- **Affected Users**: Anyone reviewing an edit session that proposes 2+ changes on the same path
  (common for multi-skill injection). Discovered in the v0.15.2 black-box test run.
- **Reproduction Steps**:
  1. Open an edit session with two `add_skill` changes both on `additional.technicalSkills`.
  2. `review-edits decide --path additional.technicalSkills --decision approve` → first change decided.
  3. Repeat for the second change → error `wrong_section` ("current section is None"); no way to select
     the second change by index/key.
- **Expected vs Actual**: Expected — a selector (index, change_id, or ordinal) disambiguates changes on
  the same path so each can be decided. Actual — `--path` alone is ambiguous and the second decide
  fails.

## Acceptance Criteria

## Acceptance Criteria

## Acceptance Criteria **[REQUIRED]**

- [ ] Multiple pending changes on the same path can each be decided in one session, via an unambiguous
      selector (e.g. `--change-id` / `--index`) in addition to / instead of `--path`.
- [ ] `review-edits status` (or equivalent) exposes the identifier needed to select each change.
- [ ] Existing single-change-per-path decide flow still works unchanged.
- [ ] Surface parity: the selector works across CLI/direct/MCP/API.
- [ ] Regression test: two same-path changes are both decidable and commit correctly.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Add a stable per-change identifier to the edit-session model (if not already present) and accept it
  in the `decide` capability; keep `--path` as a convenience when unambiguous. Code-owned in the
  edit-session orchestrator ([[RIT-A-0001]] / `packages/facade/edit_session.py`) so all surfaces share
  it.

### Dependencies
- Edit-session orchestrator ([[RIT-A-0001]], [[RIT-T-0099]]), `review-edits` skill/CLI surface.

### Risk Considerations
- Preserve the logged-decision-by-path hard gate semantics; adding an id selector must not create a
  path where a change is committed without a recorded decision.

**Recommended Agent: sonnet + medium** — contained selector addition following the existing
edit-session pattern; needs surface parity.
