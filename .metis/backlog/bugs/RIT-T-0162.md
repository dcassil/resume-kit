# Explicit custom-section→skills mapping is unsatisfiable (asymmetric claim-set computation) and lossy (whole lines/headings ingested as a single skill)

## Objective **[REQUIRED]**

Fix the custom-section → skills mapping in the shape/structure pass so that a user who explicitly maps
a custom section into `skills` can actually satisfy the gate, and so the ingested skills are tokenized
rather than swallowed whole. Two related defects:

- **B1 — unsatisfiable due to asymmetric claim-set computation.** The claim set computed for the
  *source* custom section and the claim set computed for the *destination* skills section are derived
  differently, so an explicit custom→skills mapping can never make the two sides equal. The
  claim-preservation / ledger gate then reports the mapping as lossy or unaccounted no matter what the
  user does — the mapping is structurally unsatisfiable.
- **B2 — lossy tokenization.** When custom content IS ingested into skills, an entire line (or the
  section heading) is captured as a single "skill" string rather than being split into discrete skill
  tokens. This produces garbage skills (e.g. one skill that is a full sentence or a heading), pollutes
  the scored keyword surface, and loses the individual skills that were actually present.

Discovered during a `parse-resume` → `build-structure` debug run on 2026-08-10 (resume-kit 0.9.0 /
plugin 1.2.0), while investigating why `ledger_ok` would not go true even when custom sections were
deliberately mapped toward `skills`. Closely related to RIT-T-0161 (custom/"other" sections cannot
satisfy the ledger) — same custom-section handling surface; fix the two together.

### Impact Assessment **[CONDITIONAL: Bug]**
- **Affected Users**: Anyone who has skills expressed inside a custom section (e.g. "Tools & Tech",
  "Core Competencies") and tries to map that section into the canonical `skills` list during shaping.
- **Reproduction Steps**:
  1. Ingest a resume with a custom section containing a comma/line-delimited list of skills.
  2. During `build-structure`, explicitly map that custom section into `skills`.
  3. Observe B1: the claim-preservation / ledger gate still reports the source and destination claim
     sets as unequal, so the mapping never satisfies the gate.
  4. In the case where content is ingested, observe B2: the whole line or the heading appears as one
     `skills` entry instead of individual skill tokens.
- **Expected vs Actual**:
  - **B1 Expected**: source and destination claim sets are computed with the *same* normalization so an
    explicit, faithful custom→skills mapping can satisfy the gate. **Actual**: asymmetric computation →
    permanently unequal → unsatisfiable.
  - **B2 Expected**: custom content mapped into `skills` is tokenized into discrete skills (delimiter /
    list-aware), headings excluded. **Actual**: entire lines/headings become single skill entries.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Root cause spans the shape canonicalizer's claim-set computation and its skills ingestion/tokenization.
  Start at `packages/scoring/src/resume_kit_scoring/shape_fix.py` — find where per-section claim sets are
  built (compare the custom-section path vs. the skills path; they must share one normalization) and where
  custom content is mapped into canonical `skills`. Reuse the existing skills tokenizer/normalizer rather
  than adding a second one (check `resume-kit-terms` / the normalizer used by matching so tokens agree with
  the scored keyword surface).
- For B1, the fix is to make both sides call the identical claim-derivation function; audit any place that
  derives claims from raw strings vs. from structured skill tokens and unify them.
- Coordinate with RIT-T-0161: both touch custom-section routing through the ledger. Land them as one
  reconciled change (or sequence 0161 first, then 0162) to avoid conflicting edits to `shape_fix.py`.

Recommended Agent: opus + high — claim-set symmetry is a gate-correctness invariant and the tokenization
must agree with the shared normalizer used by matching/ATS; wrong choices corrupt scoring downstream, and
it must be reconciled with RIT-T-0161 on the same module.

### Dependencies
- Non-destructive canonicalizer + content ledger + claim gates (RIT-T-0136), shape analyzer (RIT-T-0135).
- Shared normalizer / tokenizer in `resume-kit-terms` (RIT-T-0062..0064) so ingested skills match the
  scored keyword surface.
- Related open bug RIT-T-0161 (custom/"other" sections cannot satisfy the ledger).

### Risk Considerations
- Tokenization must not over-split (e.g. "CI/CD", "A/B testing") — reuse the established skills normalizer
  which already handles these, rather than a naive split on delimiters.
- Unifying claim-set computation must not weaken the claim-preservation gate for the non-skills paths that
  currently rely on it (RIT-T-0136); verify existing gate tests stay green.

*2026-08-10 — Root-caused + fixed on the same branch as RIT-T-0161 (which landed the canonical `custom`
holding slot + `PRESERVED_AS_OTHER` fate this builds on).*

**Pinned root cause** in `packages/scoring/src/resume_kit_scoring/shape_fix.py`:
- **B1 (unsatisfiable, asymmetric claim sets).** `_builddoc_claim_set` (source) only counted a custom
  section's skills when `policy.canonical_section_for_heading(display_name) is CanonicalSection.SKILLS`
  and derived them from whole strings via `_custom_skill_claims`; `_canonical_claim_set` (destination)
  counted `resume.skills[*].keywords` after ingestion. Two asymmetries made an explicit custom→skills
  mapping permanently unequal: (a) heading-gated inclusion on the source side vs. actual-routing on the
  destination side (e.g. "Core Competencies" normalizes to "other", so it was counted only on the
  destination once explicitly mapped to skills), and (b) whole-string normalization on the source vs.
  tokenized keywords on the destination.
- **B2 (lossy tokenization).** `add_skill_group` took each `section.strings` entry as ONE skill keyword.
  `coerce_string_list` only splits on newlines, so a comma/semicolon-delimited line
  ("Python, CI/CD, A/B testing") became a single garbage skill; the heading could also slip in as a skill.

**Fix.**
- B2: added `_split_skill_line(value)` (splits on `,`/`;`/`|`/bullets/newlines; deliberately NOT on `/`
  so "CI/CD" and "A/B testing" survive) and applied it in `add_skill_group` so each string yields
  discrete skill tokens; heading/parser-artifact drops unchanged. No over-split, no fabrication.
- B1: unified both sides onto ONE combined claim universe key `"skills_and_custom"` derived through the
  identical `_split_skill_line` tokenization (`_skill_claims_from_value`). Source folds
  `additional.technicalSkills` + every custom string-list section (parser-artifacts excluded, matching
  the canonicalizer's drops); destination folds `resume.skills` + work/project skills +
  `resume.custom[*].lines`. Content that moves custom→skills (or custom→preserved-as-other) stays in the
  same universe on both sides, so the mapping is satisfiable while genuine loss/fabrication is still
  caught. Removed the now-dead heading-gated policy lookup (and the unused `default_shape_policy` import).

**Regression test** (`packages/scoring/tests/test_shape_fix.py`):
`test_custom_to_skills_mapping_is_satisfiable_and_tokenized` — an explicit `{"Core Competencies":
SKILLS}` mapping with a comma line passes both `content_ledger_ok` and
`claims_preserved_across_sections` (B1), and asserts the resulting `skills[0].keywords` contain
`Python`, `CI/CD`, `A/B testing`, `Distributed Systems` while NOT containing the whole line or the
heading (B2). Existing gate tests for non-skills paths stay green (claim-preservation not weakened).
