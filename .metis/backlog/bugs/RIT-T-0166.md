# Multi-word / hyphenated aliases never take effect in matching or suggest-terminology (only single-token aliases fire)

## Objective **[REQUIRED]**

Fix the alias-widening path so curated aliases whose RESUME surface form spans more than one token (bigrams,
hyphenated terms) are actually honored — in keyword matching AND in the terminology-alignment suggestions
derived from it. Today only single-token aliases fire; every multi-word/hyphenated alias is silently inert,
which understates coverage and hides valid mirror-swap suggestions.

Discovered during an alias-seeding test run on 2026-08-10: after seeding an `alias_file` with four truthful
pairs, re-scoring moved keyword coverage by only +1 (matched 9→10). Only `web performance ← performance`
took effect; `responsive UI → responsive design`, `mobile-web → mobile web`, and `code-quality → code
quality` did not register despite those exact strings being in the resume. The common factor: the one that
worked is single-token; the three that failed are hyphenated/multi-word. `suggest-terminology` with the same
alias file returned exactly 1 suggestion (again only the single-token one), so the limitation is SYSTEMIC
across scoring and suggestion/apply — 3 of 4 truthful, confirmed aliases were inert.

### Impact Assessment **[CONDITIONAL: Bug]**
- **Affected Users**: Any project using an `alias_file` or built-in lexicon where the resume surface form is
  multi-word/hyphenated (very common: "responsive UI", "mobile-web", "code-quality", "CI/CD", "unit
  testing"). True coverage is understated and no mirror suggestion is offered.
- **Reproduction Steps**:
  1. Seed an `alias_file` with a pair whose resume surface form is multi-word/hyphenated (e.g. `responsive
     design` ↔ resume `responsive UI`; `mobile web` ↔ resume `mobile-web`).
  2. Run `match` / `check-keywords` with `--alias-file`; inspect the matched set.
  3. Run `suggest-terminology` with the same alias file.
  4. Observe: only single-token aliases appear in matches/suggestions; multi-word/hyphenated ones are absent.
- **Expected vs Actual**:
  - **Expected**: a curated alias is honored regardless of whether its resume surface form is one token or
    several; `check-gaps`/`match`/`suggest-terminology` all reflect it consistently.
  - **Actual**: only single-token aliases fire; multi-word/hyphenated aliases never match and never surface.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Root cause is in `packages/matching/src/resume_kit_matching/keywords.py` (alias-widening loop, ~lines
  153-158): after the exact/multi-word contiguous check, alias widening iterates **single whole tokens** of
  the resume text (`for token in _TOKEN_RE.findall(text): match(keyword, token, alias_index)`). Comparing one
  token at a time means an alias whose resume SURFACE form spans multiple tokens can never be assembled and
  never matches. The code comment ("compare the keyword against each whole token") states the limitation.
- Fix direction (design, don't over-engineer): allow the alias comparison to consider contiguous multi-token
  windows of the resume text bounded by the max token-length of any alias surface form in the index (n-gram
  window bounded BY THE INDEX, not arbitrary), preserving the contiguous-boundary guarantee that prevents
  substring/derivational false positives. Reuse `resume_kit_terms.match` / the alias index; do not
  reimplement matching. The normalizer already collapses `mobile-web → mobile web` (confirmed in the test),
  so the gap is the token-window lookup, not normalization.
- Verify `packages/matching/src/resume_kit_matching/terminology.py` inherits the fix (it emits from `alias`
  hits) — add a suggestion-side regression test.

Recommended Agent: opus + medium — bounded to one module's lookup, but the false-positive boundary is subtle
(n-gram windows must not resurrect substring matches) and it spans matching + terminology consumers; the
curated-synonym guarantee is load-bearing.
