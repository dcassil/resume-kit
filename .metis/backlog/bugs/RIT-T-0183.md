# add_skill rejects list values and silently no-ops without alias file

## Objective **[REQUIRED]**

Make the `add_skill` change action honest about its input contract and reliable as a skill-injection
path. Today it fails two ways: (1) `ChangeProposal.value` is schema-typed as string-or-list, but the
`add_skill` apply layer accepts only one non-empty string, so a list value is rejected at apply; and
(2) in the 0.15.1 re-test, with the alias file set `add_skill` throws `LexiconError`, and with the
alias file UNSET it silently no-ops (the skills never land). Bullet-replace is currently the only
reliable injection path. Fix `add_skill` so it either applies or fails loudly with a clear message —
never silently.

## Backlog Item Details

### Type
- [x] Bug — apply-layer contract mismatch + silent no-op (skills do not land, no error surfaced)

### Priority
- [x] P1 — High. A silent no-op means an agent believes a skill was injected when it was not, producing
  a resume that is missing content the flow reported as added. The list-rejection also makes the
  documented string-or-list schema a lie at the apply boundary.

### Impact Assessment
- **Affected Users**: Any flow that injects skills via `add_skill` (update-keywords, terminology/skill
  additions). Agents relying on the reported change succeeding are misled.
- **Reproduction (from 0.15.1 test run)**:
  1. Build an `add_skill` `ChangeProposal` with a LIST `value` → rejected by the apply layer despite the
     schema permitting a list.
  2. With the project alias file SET, apply `add_skill` → throws `LexiconError` (interacts with the
     commit-time alias-growth hazard; see [[RIT-T-0180]]).
  3. With the alias file UNSET, apply `add_skill` → returns success-ish but the skill does NOT land in
     the resume (silent no-op).
- **Expected vs Actual**: Expected — a list value is either accepted (expanded into multiple
  single-skill additions) or rejected at MODEL/tool validation with a clear message; a single-string
  value reliably lands the skill or fails loudly. Actual — list rejected at apply, and single value
  silently no-ops (or `LexiconError`s with alias file set).

### Root Cause (to verify against code before fixing)
- `ChangeProposal.value` typed string-or-list in the model, but the `add_skill` handler in the apply
  layer (`packages/facade/.../edit_session.py` change-application dispatch) unwraps only a single
  non-empty string. Locate the `add_skill` apply branch and the point where a non-matching value is
  dropped without raising.
- The silent no-op path: identify why a valid single-string add does not mutate the working resume when
  no alias file is present (likely a guard/branch that returns without applying). The `LexiconError`
  with alias set is the same commit-time alias-growth hazard tracked in [[RIT-T-0180]] — coordinate so
  fixing that does not mask this one.

## Acceptance Criteria

## Acceptance Criteria **[REQUIRED]**

- [ ] Explicit input contract for `add_skill.value`: EITHER (A) list values are expanded into multiple
      single-skill additions and each lands, OR (B) list values are rejected at model/tool validation
      with a clear, actionable error. Whichever is chosen is documented and enforced at the model/tool
      boundary — not silently dropped at apply.
- [ ] A valid single-string `add_skill` ALWAYS either lands the skill in the working resume or fails
      with a clear error. It must NEVER return success while the skill is absent (no silent no-op).
- [ ] The no-op-without-alias-file behavior is eliminated: `add_skill` applies identically whether or
      not an alias file is configured (alias-index safety is [[RIT-T-0180]]'s concern, not a reason to
      drop the skill).
- [ ] The `LexiconError`-with-alias-set path is either fixed here or explicitly deferred to
      [[RIT-T-0180]] with a cross-link; if deferred, `add_skill` must still not silently no-op in the
      no-alias case.
- [ ] Regression tests: (a) single-string add lands the skill; (b) list value behaves per the chosen
      contract (expanded-and-landed OR rejected-with-clear-error); (c) add with no alias file lands the
      skill (no silent no-op); (d) surface parity across CLI/direct/MCP/API.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Decide the list contract first (A expand vs B reject). Expansion (A) is more ergonomic and matches the
  string-or-list schema; if chosen, expand a list `value` into N single-skill `add_skill` operations in
  a code-owned place so all surfaces share it.
- Fix the silent-no-op branch so a failed/skipped application raises or is reported as a non-applied
  change in the result, never as a success.
- Keep truth/faithfulness gates intact; this is about apply-layer correctness and honest reporting, not
  relaxing what may be added.

### Dependencies
- `ChangeProposal` model (`packages/core`/facade `models.py`), edit-session apply dispatch
  (`packages/facade/.../edit_session.py`), and the alias-growth guard shared with [[RIT-T-0180]].
- Source: `POST_TEST_ISSUES.2026-08-11.md` ("`add_skill` List Values") + the 0.15.1 re-test note that it
  is now doubly broken (LexiconError with alias set, silent no-op without).

### Risk Considerations
- Coordinate with [[RIT-T-0180]] so the alias-growth fix and the add_skill fix do not collide or double-
  handle the `LexiconError`.
- Ensure a non-applied change is surfaced in the result envelope so agents can detect it.
- Watch the [[dev-env-editable-installs]] vendoring landmine when testing.
