# Faithfulness scorer content-string set: fix phantom ADDED_TOKENS and unscanned customSection keys

## Objective **[REQUIRED]**

Realign the faithfulness scorer's definition of "content strings" with the actual `ResumeDocument` schema shape so `validate-faithfulness` neither invents fabricated tokens from schema machinery (F1) nor drops legitimate user headings stored in dict keys (F2). Both are two directions of the same root cause: the tokenizer walks the wrong set of nodes. This task is to **investigate the scorer's tokenization boundary and fix it** so both symptoms are resolved by one deliberate content-string set.

Discovered during a debug run of the `parse-resume` ingest step on 2026-08-07 (resume-kit 0.9.0 / plugin 1.2.0).

## Backlog Item Details

### Type
- [x] Bug - Production issue that needs fixing

### Priority
- [x] P1 - High (F2 hard-fails the faithfulness gate and blocks ingest; F1 is non-blocking noise that erodes trust in the gate)

### Impact Assessment
- **Affected Users**: Anyone parsing a resume whose customSection headings live only in the dict key (F2 → gate fails, ingest blocked), and every parse run that emits customSections (F1 → phantom ADDED_TOKENS warnings).
- **Reproduction Steps**:
  1. Run `parse-resume` on a `.docx` containing a customSection whose heading is stored as the dict KEY (e.g. "Domains & Industries"), and containing customSections with `sectionType` enum values (`stringlist`, `text`).
  2. Let `validate-faithfulness` run as the gate.
  3. Observe: `ADDED_TOKENS: ["bullet","stringlist","text"]` (F1, warning) AND `DROPPED_SPANS` at error severity for the key-only heading (F2, blocking).
- **Expected vs Actual**:
  - **F1 Expected**: only true user-content string values are tokenized; schema enum values (`stringlist`/`text`) and any schema-example text (`bullet`) are excluded. **Actual**: schema machinery is tokenized as fabricated content. `bullet` appears in NEITHER candidate JSON (`grep -ic bullet` = 0) NOR source docx (0), suggesting bleed-in from the schema's own example (`"bullet verbatim"`) inside the scorer.
  - **F2 Expected**: a customSection heading stored as the dict key is recognized as preserved content. **Actual**: only customSection VALUES are scanned, so the key-only heading is reported DROPPED_SPANS at error → gate fails.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
The fix is one deliberate definition of the content-string set the tokenizer walks over a `ResumeDocument`:
- **Include**: user-content string values AND customSection dict keys (which legitimately hold user headings, since no `displayName` field exists).
- **Exclude**: `sectionType` enum values, any other schema enum members, and any schema-example strings that live in the scorer rather than the document under test.

Trace `bullet` first — it is the tell for whether the scorer is contaminating its token set with its own schema example. That single trace likely explains F1's `bullet` and confirms the tokenizer is walking schema/structural strings rather than only document content.

Recommended Agent: opus + medium (touches the faithfulness scorer core and its tokenization boundary; needs careful reasoning across schema shape + both candidate/reference token paths, plus regression tests, but is a bounded, well-understood fix).

### Dependencies
- Faithfulness scorer / `validate-faithfulness` engine in `resume_kit` (the ADDED_TOKENS and DROPPED_SPANS producers).
- `parse-resume` skill + `ResumeDocument` schema (customSection key-as-heading convention).

### Risk Considerations
- Widening the scanned set to include customSection keys must not re-introduce false ADDED_TOKENS from those same keys on the candidate side — keep the include/exclude rules symmetric across candidate and reference tokenization.
- Excluding enum values must be by schema knowledge, not by string denylist, so future enum members don't silently regress.

## Status Updates **[REQUIRED]**

### 2026-08-10 — Root cause traced + fixed (candidate-side content-string set)

**`bullet` root cause (traced first, as instructed).** The phantom `bullet`
token does NOT come from a schema *example* in the scorer as the ticket
hypothesized. It leaks from the **candidate (JSON) side only**. The scorer built
its JSON token set via `_json_flat_text` → `_extract_all_text(resume.model_dump())`,
a blanket walk over every string value of the serialized model. `model_dump()`
serializes `Experience/Project/CustomSectionItem.descriptionStyles` — a
`list[DescriptionStyle]` whose literal members are `"bullet"`/`"plain"` — as
plain strings. So any resume with a bullet description emits
`descriptionStyles: ["bullet", ...]`, and `bullet` was tokenized as authored
content → ADDED_TOKENS. The same mechanism produced `stringList`/`text`/
`itemList`/`personalInfo`: those are `SectionType` enum values serialized from
`CustomSection.sectionType` / `SectionMeta.sectionType`. There is only one
JSON-token code path (`_json_flat_text`), so this is unambiguously the
candidate-side set; the reference (source) side is raw text and never saw these
tokens. Confirmed by repro: pre-fix `_json_flat_text` token set contained
`bullet` and `stringlist`.

**F2 root cause.** `customSections` is `dict[str, CustomSection]` and the dict
KEY is the user's section heading (no `displayName` on `CustomSection`). The old
walk only visited `dict.values()`, so a key-only heading (e.g. "Domains and
Industries") never entered the JSON token set → DROPPED_SPANS at error severity
→ gate hard-failed.

**Fix.** Replaced the blanket `_extract_all_text(model_dump())` with a deliberate
`_content_strings(resume)` collector that walks the *typed* `ResumeDocument` and
gathers only authored content: personalInfo/summary/experience/education/
projects/additional user strings, customSection `text`/`strings`/`items`
values, AND customSection dict KEYS (the headings). It EXCLUDES
`descriptionStyles`, `sectionType`, and all `sectionMeta` structural fields by
schema knowledge (by not walking those typed fields — not a string denylist), so
future enum members cannot silently regress. This one set feeds both the
ADDED_TOKENS (candidate) scan and the dropped/altered (reference) comparison,
keeping include/exclude symmetric. The prior workaround (prepending the heading
into a customSection value) is no longer needed.

**Regression tests** (`packages/ats/tests/test_faithfulness.py`):
- `test_custom_sections_do_not_leak_schema_tokens` — asserts
  `bullet`/`stringlist`/`text`/`itemlist`/`personalinfo` are absent from
  ADDED_TOKENS for a doc with a customSection.
- `test_key_only_custom_section_heading_not_dropped` — a heading stored only in
  the dict key produces no DROPPED_SPANS error (and isn't falsely added).
Both confirmed failing against pre-fix code; both pass after the fix.

**Gates.** `ruff check .` → All checks passed. `mypy packages/ats/src` →
Success. `pytest packages/ats` and `pytest packages/scoring` → all pass.
