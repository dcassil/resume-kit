# internal_error responses swallow the real exception message

## ⚠️ INVESTIGATION FINDING (2026-08-11) — REOPENED AS A DECISION, DO NOT IMPLEMENT AS ORIGINALLY SCOPED

A codex agent implemented the naive fix (embed `str(exc)` as `details.detail` in the `internal_error`
envelope) and it was **REVERTED**. Reason: the current behavior is a **deliberate, documented,
test-enforced security invariant**, not an oversight. `from_exception()` in
`packages/core/src/resume_kit_core/interface.py` explicitly states it *"deliberately does NOT embed the
exception's string or any content in the envelope, to avoid leaking secrets or user data. Only the
exception's type name is recorded."* The test
`packages/core/tests/test_interface_mapping.py::TestErrorMapping::test_generic_exception_maps_to_internal_error`
asserts that a secret in an exception message (`ValueError("secret token abc123")`) does NOT appear
anywhere in the serialized response.

So the original premise ("just surface `str(exc)`") is unsafe: exception strings can contain provider
API keys, tokens, file paths, or user content. **This is now a DESIGN DECISION for Daniel**, not a
mechanical fix. Options:
- **A — Keep the invariant; improve diagnosis out-of-band.** Log the full exception (message +
  traceback) to a local diagnostics file/stderr the user controls, keep the response envelope
  content-free (type name only). No leak surface in transported responses. (Recommended.)
- **B — Curated safe detail.** Introduce an explicit, opt-in "safe detail" that specific capabilities
  populate with a vetted, non-sensitive message (e.g. build-base's claim-flip reason), never the raw
  `str(exc)`. Requires each raising site to opt in.
- **C — Redaction pass.** Surface `str(exc)` but run it through a secret/PII redactor. Highest risk;
  redaction is easy to get wrong — not recommended.

Do NOT relax `test_interface_mapping`'s no-leak assertion. RIT-T-0187's diagnosis difficulty is real,
but option A solves it without weakening the boundary.

## Objective **[REQUIRED]**

When a capability fails with `internal_error`, surface enough detail for a user/agent to diagnose it.
Today the error envelope reports only a generic message plus `exception_type`; the actual exception
message is dropped, so diagnosing (e.g. the [[RIT-T-0187]] claim-flip `ValueError`) required
reproducing the failure against the underlying functions.

  swallowed.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Locate the capability error-wrapping seam (the facade/interface envelope that maps exceptions to
  `internal_error`) and thread `str(exc)` into a `detail`/`message` field. Keep the generic
  category for programmatic handling; add the human-readable detail alongside.

### Dependencies
- The capability response envelope (`packages/facade` + interface adapters). Related to [[RIT-T-0187]]
  (whose diagnosis was blocked by this).

### Risk Considerations
- Verify no secret/PII leakage in the surfaced message; resume/job text is user-local data, so the bar
  is "don't leak filesystem/provider secrets", not "hide resume content".

**Recommended Agent: sonnet + medium** — contained envelope change with surface parity; low reasoning
load once the seam is located.
