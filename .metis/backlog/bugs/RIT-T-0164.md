# Best-practices output emits null finding code and null resume_version: report never stamps resume_version and the surface serializes a generic 'code' that doesn't map to the finding's rule_code

## Objective **[REQUIRED]**

Make the best-practices report identify itself. Two output defects observed on the same run:

- **B1 — `resume_version: null`.** `BestPracticesReport.resume_version` is `str | None` and defaults to
  `None` (`packages/schemas/src/resume_kit_schemas/best_practices.py:216`). The analyzer / facade
  capability that builds the report never populates it, so every emitted report shows `resume_version:
  null` — the output does not record which resume version was scored.
- **B2 — finding `code: null`.** In the emitted output each finding's `code` comes back `null`, and only
  the elicitation prompt reveals which rule fired. The schema's per-finding field is named `rule_code`
  (`best_practices.py:137`), not `code` — so wherever the output serializes a generic `code` key (a
  surface/adapter model, or a mismatched `.code` read), it does not map to `rule_code` and serializes
  null. The stable rule identifier is present on the model but lost in the output shape.

Discovered during a baseline debug run on 2026-08-10 (resume-kit 0.9.0 / plugin 1.2.0): the
best-practices report printed `resume_version: null` and every finding's `code` as `null`, forcing the
reader to infer the rule from the elicitation prompt text.

## Backlog Item Details **[CONDITIONAL: Backlog Item]**

### Type
- [x] Bug - Production issue that needs fixing

### Priority
- [x] P2 - Medium — no crash; the findings themselves are correct. But null `code` and null
      `resume_version` make the output hard to consume programmatically (can't key findings by rule,
      can't tell which version was scored), degrading every surface that renders the report.

### Impact Assessment **[CONDITIONAL: Bug]**
- **Affected Users**: Any consumer of the best-practices report output (CLI users reading it, MCP/API
  callers, and the `check-best-practices` skill) — they get findings with `code: null` and a report with
  `resume_version: null`.
- **Reproduction Steps**:
  1. Run `check-best-practices` / `resume_analyze_best_practices` on any resume with findings.
  2. Inspect the emitted report: `resume_version` is `null`.
  3. Inspect each finding: `code` is `null`; the rule is only inferable from `elicitation_prompt`.
- **Expected vs Actual**:
  - **B1 Expected**: `resume_version` is stamped with the scored version identity (the base/refine/
    structure pointer or document id). **Actual**: `null`.
  - **B2 Expected**: each finding's output carries the stable rule identifier (`WEAK_OPENER`,
    `MISSING_QUANTIFICATION`, ...). **Actual**: `code: null`; identifier only in the prompt.

## Acceptance Criteria **[REQUIRED]**

- [ ] B1: the analyzer/facade capability populates `BestPracticesReport.resume_version` with the identity
      of the resume version scored; emitted reports show a non-null, correct `resume_version`.
- [ ] B2: the finding's stable rule identifier is present and non-null in the emitted output across every
      surface (facade return, CLI render, MCP tool result, API response) — either by serializing
      `rule_code` under whatever key the output uses, or by aligning the output key to `rule_code`. No
      finding emits a null code.
- [ ] Root-caused: identify the exact serialization point where `rule_code` is dropped / a generic `code`
      is emitted (a surface/adapter model or a `.code` read) and fix it there rather than papering over it.
- [ ] Regression test: a report produced by the capability has a non-null `resume_version` and every
      finding has a non-null rule identifier in the serialized output.
- [ ] Cross-surface parity: CLI, MCP, and API renders of the same report all show the rule identifier and
      resume_version consistently (mirror the existing cross-surface parity tests).

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- **B1**: find where the report is constructed — the facade capability behind
  `resume_analyze_best_practices` (`packages/facade/src/resume_kit_facade/baseline.py` /
  `capabilities.py`). It has the active version pointer in scope (base/structure/refine); pass it into
  `BestPracticesReport(resume_version=...)`. Schema field:
  `packages/schemas/src/resume_kit_schemas/best_practices.py:216`.
- **B2**: the schema's per-finding field is `rule_code` (`best_practices.py:137`). Grep the surface/adapter
  models and renderers for a `code` field or `.code` read on findings —
  `packages/facade/src/resume_kit_facade/models.py`, `packages/api/src/resume_kit_api/models.py`,
  `packages/mcp/src/resume_kit_mcp/tools.py`, CLI `packages/cli/src/resume_kit_cli/app.py`. Whichever
  layer emits a generic `code`, map it from `rule_code` (or rename to `rule_code`). Note there is also a
  separate `common.py:39 code: str | None` and `analysis.py:171 code` — do NOT conflate the best-practices
  finding with those; confirm which model the best-practices output actually serializes.
- Fix at the true serialization point; do not add a fallback that hides the drop.

Recommended Agent: sonnet + medium — bounded: stamp one field (B1) and reconcile a field-name/mapping
mismatch across surface models (B2). Reasoning is mostly locating the exact serialization point; the
edits are small and follow existing cross-surface patterns.

### Dependencies
- Best-practices report schema (RIT-T-0116) and analyzer (RIT-T-0117).
- Facade/CLI/MCP/API surfaces for baselining capabilities (RIT-T-0119).
- Overlaps RIT-T-0163 (read-only analyzer misreads structure) — same report surface; can be worked by
  the same agent in one pass.

### Risk Considerations
- Renaming an output key (if that route is chosen) is a surface contract change — check for consumers
  (job-hunter bridge, tests, docs) that read the old key before renaming; prefer mapping `rule_code` into
  the existing key to avoid a breaking change unless the key is not yet consumed.
- Ensure `resume_version` is stamped with a real, resolved identity (not a raw path) consistent with how
  other reports identify versions.

*2026-08-10 — Fixed (worktree agent-a4edd9d87970eb9d0, on top of RIT-T-0163).*
B1 (`resume_version: null`): added `resume_version: str | None` to
`AnalyzeBestPracticesRequest`; the `analyze_best_practices_capability` now stamps it onto the returned
`BestPracticesReport` via `model_copy`. Surfaces pass the version identity: CLI passes the `--resume`
path, MCP accepts an optional `resume_version` arg, API accepts an optional `resume_version` body field.
When not supplied it stays `None` (no fabricated identity). Verified emitted `resume_version` is non-null
when passed.
B2 (finding `code: null`): root-caused — the best-practices finding model has only `rule_code`; any
consumer reading a generic `.code` got `None`. Rather than rename `rule_code` (the canonical key stays,
avoiding a contract break) or paper over it with a fallback, added a serialized `@computed_field` `code`
on `BestPracticesFinding` that mirrors `rule_code`, so every finding now emits BOTH `rule_code` and a
non-null `code` carrying the stable rule identifier. Did NOT touch the unrelated `common.py` /
`analysis.py` `code` fields or the error/warning `code` the job-hunter bridge reads.
Regression coverage in `packages/facade/tests/test_best_practices_readonly_parity.py`: asserts a report
produced by the capability has a non-null `resume_version` and every serialized finding has
`code == rule_code` (non-null). Gates pass against source: ruff clean, mypy clean, pytest green across
facade/scoring/schemas (and mcp/cli/api).
