# No supported code path persists alias_file into config: set-active lacks the param (MCP advertises it, capability rejects it → masked ValueError), project_init ignores it

## Objective **[REQUIRED]**

Provide a supported, documented code path to persist `config.alias_file` for an existing project. Today the
ONLY way to set `alias_file` is to hand-edit `config.json`: `set-active` has no `alias_file` parameter (the
MCP tool advertises one via its generic schema but the underlying capability rejects it, surfacing a MASKED
ValueError → generic internal error), and `project_init(alias_file=…)` silently ignores it. This is a
concrete blocker for RIT-T-0165 (which must create + register `alias_file` during the flow) and it also
demonstrates two systemic defects: an MCP schema that advertises a param the capability doesn't accept, and
the masked-error pattern (a ValueError surfacing as "internal error") that RIT-T-0156 fixed at the boundary.

Discovered during the alias-seeding test run on 2026-08-10: the tester had to hand-set `config.alias_file`
because no CLI/MCP path worked; the scoring engine still honored the file via the explicit `--alias-file`
flag, proving the gap is purely in PERSISTENCE, not in the engine.

### Impact Assessment **[CONDITIONAL: Bug]**
- **Affected Users**: Anyone who wants a persistent project-level alias index (the whole RIT-I-0009 /
  RIT-T-0165 value): there is no supported way to register it short of hand-editing `config.json`. Also
  anyone who calls the MCP `set_active` with `alias_file` and gets an opaque "internal error".
- **Reproduction Steps**:
  1. On an existing project, try to set `alias_file` via `set-active` (CLI): no such flag.
  2. Call MCP `project_set_active(alias_file=…)`: capability rejects the param → masked ValueError →
     generic internal error.
  3. Call MCP `project_init(alias_file=…)` on/again: `config.alias_file` stays `null` (ignored).
  4. Only hand-editing `config.json` sets it; the engine then honors it (proving persistence is the only gap).
- **Expected vs Actual**:
  - **Expected**: a supported command persists `config.alias_file` for an existing project, validated and
    path-normalized like other config pointers; invalid input yields a clear `validation` error, not a
    masked internal error.
  - **Actual**: no working CLI/MCP path; MCP advertises a param the capability rejects; the rejection is
    masked as an internal error; `project_init` silently ignores the param.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Add `alias_file` to the `set-active` capability (CLI flag + facade param), persisting into the config via
  the existing config-write path (RIT-T-0091 lineage), normalizing the path like other pointers (RIT-T-0127).
- Reconcile the MCP tool schema with the capability so the advertised param is real (this is the concrete,
  narrow instance of the broader RIT-T-0154 "opaque MCP schema" concern — fixing it here does not require
  the whole 0154 rework, just make THIS param honest).
- Ensure the ValueError path is mapped by the boundary added in RIT-T-0156 (`from_validation_error`) so it
  reads as `validation`, not `internal_error`.
- Decide `project_init(alias_file=…)`: either wire it or drop it from the schema; do not leave it advertised
  and ignored.

Recommended Agent: opus + medium — small but spans the config contract, the set-active capability, the MCP
schema/capability agreement, and the error-mapping boundary; correctness of the persisted contract matters
because RIT-T-0165 builds on it.

### Dependencies
- Config contract RIT-T-0091; path normalization RIT-T-0127; error-boundary RIT-T-0156 (validation vs
  internal_error). MCP tool defs (`packages/mcp`), facade set-active capability.
- **Unblocks / is a hard prerequisite for RIT-T-0165** (alias auto-seed must persist `config.alias_file`).

### Risk Considerations
- Keep this narrow: fix THIS param's honesty + persistence, don't fold in the whole RIT-T-0154 MCP-surface
  redesign (that's deferred).
- Path normalization must match the other pointers to avoid the working-dir prefix-doubling class of bug
  RIT-T-0127 addressed.

*Fixed 2026-08-10:* Persistence path wired end to end (TDD, failing tests first).
- **Capability/config**: `set_active()` (packages/facade/.../project_config.py) now accepts `alias_file`,
  normalizes it via the existing RIT-T-0127 `_normalize_pointer` (no working-dir prefix-doubling), validates
  it resolves to an existing file under the project root (missing file → `ValueError`), and persists it
  through the RIT-T-0091 atomic config-write path without clobbering other pointers. `alias_file` alone is
  now a valid set-active call.
- **Request model**: `SetActiveRequest` gains an `alias_file` field.
- **Error boundary**: added `from_validation_error` to `packages/core/.../interface.py` (the RIT-T-0156
  boundary was NOT actually present on main — it did not exist — so it was added here) mapping caller-input
  `ValueError`s to `validation_failed` with actionable text. `set_active_capability` now catches `ValueError`
  → `from_validation_error` (was masked as `internal_error` via `from_exception`).
- **CLI**: `set-active --alias-file <path>` added.
- **MCP**: `project_set_active` now reads and forwards `alias_file` (the generic schema already advertised
  it, so advertised == accepted now — the narrow honest-param fix from the RIT-T-0154 concern, no broader
  redesign).
- **project_init decision — REMOVE (documented non-support)**: `init_project` is scaffold-only; `alias_file`
  belongs to the pointer-owning `set-active` path, not init. `InitProjectRequest` never had an `alias_file`
  field, so nothing was wired; a regression test (`test_project_init_does_not_accept_alias_file`) locks in
  that `project_init(alias_file=…)` never persists it (silently ignored), directing callers to
  `project_set_active`.
- **Tests**: facade round-trip + normalization + idempotency + missing-file-rejection + capability
