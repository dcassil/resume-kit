# Non-omit build-structure can never preserve custom sections (claims_ok always False)

## ⚠️ DECISION (2026-08-11, Daniel) — RESCOPED: always omit + always seed; drop the preserve path

Daniel: "Always omit custom and always seed. Never keep custom sections in the resume." This SUPERSEDES
the original "make the preserve path pass the claim gate" framing. Do NOT fix `PRESERVE_IN_CANONICAL_CUSTOM`
to succeed — instead make omit the DEFAULT and only behavior:
- `build-structure` OMITS custom sections by default (no flag needed); custom sections never appear in
  base/structure/refine/tailored/final output.
- Before omitting, ALWAYS auto-seed full-resume evidence (so RIT-T-0186's receipt gate passes and the
  omitted content is safely captured) — even when `build-structure` is called directly outside Flow 1.
- Remove or hard-deprecate the preserve path (`PRESERVE_IN_CANONICAL_CUSTOM`) and the now-redundant
  `--omit-custom-sections` opt-in becomes the default (keep the flag as a no-op/alias or drop it).
- Keep the claim gate strict; the auto-seed + omit ordering is what makes it pass, not a gate relaxation.
The original preserve-path acceptance criteria below are OBSOLETE — retained only for context.

## Objective **[REQUIRED]**

Make the DEFAULT (non-omit) `build-structure` path viable for a resume that has custom/non-standard
sections. Today the only route that produces a `structure` artifact for such a resume is
`--omit-custom-sections` (which requires seeded evidence, per [[RIT-T-0186]]). The preserve path
(`PRESERVE_IN_CANONICAL_CUSTOM`) re-tokenizes the custom-section text into skill-claims, so the
cross-section claim gate sees NEW claims and returns `claims_ok: False`, and nothing is written — even
when the content ledger is fully accounted (`moved` / `preserved_as_other`).

## Backlog Item Details

### Type
- [x] Bug

### Priority
- [x] P1 — High. It means the advertised default behavior ("keep custom sections in a canonical custom
  bucket") silently never succeeds for real resumes with custom sections; the user is forced down the
  omit path whether or not they want to drop those sections. Combined with [[RIT-T-0187]] it makes a
  custom-section resume very hard to baseline.

### Impact Assessment
- **Affected Users**: Any resume with a genuine custom/non-standard section (in the test data:
  "Domains & Industries", "Ventures & Consulting"). Discovered in the v0.15.2 black-box test run.
- **Reproduction Steps**:
  1. Faithful original with a custom section containing descriptive text.
  2. `resume-tool build-structure` (NO `--omit-custom-sections`).
  3. Result: `claims_ok: False`, no `structure` artifact written, even though the content ledger shows
     all tokens as `moved` / `preserved_as_other`.
- **Expected vs Actual**: Expected — the preserve path keeps the custom section in a canonical custom
  bucket and passes the claim gate (re-bucketing is not new information). Actual — the custom text is
  re-tokenized into skill-claims that did not exist as claims in the source layout, so
  `claims_preserved_across_sections` counts them as ADDED and fails.

### Root Cause (from test-run inspection)
- In `PRESERVE_IN_CANONICAL_CUSTOM` mode, custom-section text is re-tokenized/extracted as skill-claims
  during canonicalization, producing claims absent from the pre-transform claim set.
- `claims_preserved_across_sections` (the whole-resume claim gate from [[RIT-I-0019]],
  `packages/scoring/shape_fix.py`) therefore sees new claims and returns False.
- The `_without_evidence_preserved_claims` subtraction that makes the OMIT path work (custom content
  that moved to evidence is excluded from the added-claim check) has NO equivalent for the PRESERVE
  path — preserved-in-canonical-custom content is not excluded from the added-claim computation.

## Acceptance Criteria **[REQUIRED]**

- [ ] Default `build-structure` (no omit) on a resume with a custom section writes a `structure`
      artifact and passes the claim gate, with the custom section preserved in the canonical custom
      bucket.
- [ ] The claim gate still catches GENUINELY new claims (fabrication) — only re-bucketed/preserved
      custom content is excluded from the added-claim check, mirroring how the omit path excludes
      content that moved to evidence.
- [ ] Deterministic, no-LLM (consistent with [[RIT-A-0002]]).
- [ ] Regression test: preserve-path structure for a custom-section resume passes; a fabricated new
      claim injected into a custom section still fails the gate.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Extend the added-claim computation so content that is PRESERVED_IN_CANONICAL_CUSTOM is treated the
  same way omit-to-evidence content is: excluded from the "new claim" set (it is a re-bucketing, not
  new information). Reuse/parallel the existing `_without_evidence_preserved_claims` logic in
  `shape_fix.py`.
- **Design question for Daniel:** should the preserve path (a) treat re-bucketed custom text as
  non-claims (no skill extraction from custom prose), or (b) extract those skills but whitelist them as
  preserved? This is a shape/ledger semantics decision under [[RIT-A-0003]]; confirm direction before
  implementing.

### Dependencies
- `packages/scoring/shape_fix.py` (content ledger + `claims_preserved_across_sections`), the canonical
  shape policy in `packages/policy` ([[RIT-I-0019]]), interacts with [[RIT-T-0186]] (omit-path
  evidence receipts). Governed by [[RIT-A-0003]].

### Risk Considerations
- Must not open a fabrication hole — the exclusion has to be scoped strictly to content the ledger
  marks as preserved/moved, never to arbitrary new tokens.
- Watch the [[dev-env-editable-installs]] vendoring landmine.

**Recommended Agent: opus + medium** — claim-gate semantics; needs the (a)/(b) decision first.
