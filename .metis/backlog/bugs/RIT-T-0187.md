# build-base crashes (opaque internal_error) on faithful non-ASCII: FORMATTING_NON_ASCII auto-fix flips claim set

## Objective **[REQUIRED]**

Make `build-base` succeed on a faithful `-original.json` that legitimately contains non-ASCII
characters (curly apostrophe `’`, middot, en/em dash, accented names). Today the base non-ASCII
auto-fix normalizes those characters, which changes the extracted claim set, trips the
claim-preservation gate, and surfaces as an opaque `internal_error` with no actionable detail. This
directly contradicts the faithfulness gate's own stated policy ("preserve the characters verbatim and
normalize at export, not here").

## Backlog Item Details

### Type
- [x] Bug

### Priority
- [x] P1 — High. Hard-blocks Flow 1 (`build-base`) for any real resume whose text contains a smart
  quote/dash/accent — extremely common in DOCX/PDF sources. The failure is an opaque
  "An internal error occurred" with the real message swallowed, so a user cannot self-diagnose.

### Impact Assessment
- **Affected Users**: Anyone whose source resume contains a curly apostrophe, en/em dash, middot, or
  accented character in a claim-bearing field (summary, bullets). Discovered in the v0.15.2 black-box
  test run with a summary containing `’` ("I've").
- **Reproduction Steps**:
  1. Parse a resume whose summary contains a curly apostrophe (e.g. "I've") into a faithful
     `-original.json` that PASSES `validate-faithfulness` (non-ASCII is a WARN, not a hard-fail there).
  2. `resume-tool set-active --resume <original> --source <docx>`
  3. `resume-tool build-base`
  4. Result: `internal_error` / `ValueError` "base auto-fix altered a claim…", non-zero exit, no base
     artifact written. The real exception message is swallowed by the facade/CLI (only
     `exception_type` is reported).
- **Expected vs Actual**: Expected — `build-base` either preserves the non-ASCII verbatim (deferring
  normalization to export, per the faithfulness gate's policy) OR performs the normalization in a
  claim-NEUTRAL way that the claim-preservation gate accepts. Actual — the `FORMATTING_NON_ASCII`
  auto-fix rewrites the character, the extracted claim set changes, `claims_preserved` fails, and the
  whole stage aborts with a generic internal error.

### Root Cause (from test-run inspection)
- `apply_auto_fixes` in `packages/scoring/src/resume_kit_scoring/base_fix.py:199` applies a
  `FORMATTING_NON_ASCII` normalization that mutates claim-bearing text; the resulting claim set no
  longer matches the pre-fix claim set, so the base claim-preservation gate rejects the write.
- The base non-ASCII policy contradicts the faithfulness gate, which explicitly treats non-ASCII as a
  by-design WARN to be normalized at EXPORT, not at base (see [[RIT-T-0155]] which documented the
  by-design non-ASCII warning on `-original.json`).
- The CLI/facade error surface reports only `exception_type` with a generic message (see the related
  swallowed-error finding, RIT-T-0191) so the actual cause is invisible to the user.

## Acceptance Criteria **[REQUIRED]**

- [ ] `build-base` succeeds on a faithful original containing a curly apostrophe (and other common
      non-ASCII: en/em dash, middot, accented letters) and writes `<name>-base.json`.
- [ ] The chosen approach is one of: (A — preferred) do NOT normalize non-ASCII at base; defer it to
      export, consistent with the faithfulness gate's documented policy; or (B) make the non-ASCII
      normalization claim-NEUTRAL (normalize the same characters inside the claim-extraction comparison
      so the before/after claim sets match), so the claim-preservation gate is not tripped by a
      cosmetic rewrite.
- [ ] No claim-preservation regression: a base auto-fix that genuinely adds/removes/alters a *claim*
      still fails the gate. Only cosmetic non-ASCII normalization is reconciled.
- [ ] Regression test: a faithful original with `’` in the summary passes `build-base` (and, per the
      chosen approach, the non-ASCII is either preserved to base or normalized without a claim flip).

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Decide A vs B. Approach A (don't normalize non-ASCII at base) is the most consistent with the
  faithfulness gate's stated policy and with [[RIT-T-0155]]; export already owns non-ASCII rendering.
  Approach B keeps the base normalization but teaches the claim-extraction/comparison to treat the
  normalized and original forms as the same claim.
- **This touches claim-preservation semantics ([[RIT-A-0003]] lineage gates) — needs Daniel's decision
  on A vs B before implementation.** Do not weaken the claim gate to "fix" this.

### Dependencies
- `packages/scoring/base_fix.py` (auto-fix set), the base claim-preservation gate, faithfulness policy
  in `packages/ats` ([[RIT-I-0014]]), export non-ASCII handling ([[RIT-T-0155]]). Governed by
  [[RIT-A-0003]] (which gate governs which transition).

### Risk Considerations
- A wrong "simple" fix that relaxes the claim gate would let real claim drift through at base — high
  blast radius. Keep the gate strict; change only the non-ASCII handling.
- Watch the [[dev-env-editable-installs]] vendoring landmine when testing.

**Recommended Agent: opus + medium** — once the A/B decision is made; touches a safety gate.
