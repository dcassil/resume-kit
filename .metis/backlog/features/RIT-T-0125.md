# Baselining interactivity + ATS-view reuse (accepted RIT-T-0120 deltas)

Captures the three deltas from [[RIT-T-0120]] that Daniel **accepted as documented** on 2026-08-06 (0120 shipped the skills+workflow faithfully to the delivered engine). The delivered baselining engine is narrower than 0120's ACs assumed; this task tracks the enrichments so the deferred work is not lost. None of these block the current baselining flow, which works end-to-end today.

## Objective **[REQUIRED]**

Bring the baselining flow up to the richer interaction model 0120's ACs originally described — interactive `base` fixing and a per-item edit-session `standard` walkthrough — and wire `update-structure` onto RIT-I-0017's single "what the ATS sees" report once it exists.

## Scope — three independent slices

**Slice 1 — Interactive `base` fixing (RIT-T-0120 AC#1 delta).**
- Today: `build_base` is **auto-only** (`packages/facade/src/resume_kit_facade/baseline.py` raises for non-`auto`); `update-structure` applies the auto-safe set and defers judgment items.
- Want: an `interactive` mode where the deterministic auto-safe fixes are presented for per-item approval before the `base` write. Requires an engine mode on `build_base` (or routing base fixes through a review surface) + surfacing it in the `build-base` capability/CLI/MCP/API + the `update-structure` skill.

**Slice 2 — Edit-session `standard` walkthrough (RIT-T-0120 AC#3 delta).**
- Today: `build_standard(root, answers)` is a **batch claim-preservation-gated write** (analyze → apply auto edits + answers → gate → write); the "walkthrough" in `update-best-practices` is only the answer-elicitation loop.
- Want: route each best-practices finding through the RIT-I-0015 edit-session orchestrator for per-item accept/reject/edit (so the `_shared/apply-changes.md` runbook could then apply to `update-best-practices` too). Requires an engine/orchestrator path that turns best-practices findings into `ChangeProposal`s and drives them through `review-edits` while preserving the claim-preservation gate.

**Slice 3 — ATS-view report reuse (RIT-T-0120 AC#6 deferral).** **Blocked by [[RIT-T-0109]].**
- Today: `update-structure` surfaces the deterministic `check-structure` `AtsStructureReport` with a documented TODO.
- Want: once RIT-T-0109's single "what the ATS sees" report exists, `update-structure` surfaces *that* report instead of a standalone structural report (no second ATS view). Small change; just needs 0109.

## Acceptance Criteria **[REQUIRED]**

- [ ] Slice 1: `build-base` supports an `interactive` mode across engine + all four surfaces + the `update-structure` skill, presenting auto-safe fixes for per-item approval before writing `base`; `auto` remains the default and unchanged. Cross-surface parity holds.
- [ ] Slice 2: the `standard` step can run each best-practices finding through the RIT-I-0015 edit-session orchestrator (per-item accept/reject/edit) behind the claim-preservation gate; `update-best-practices` is updated (and may then defer to `_shared/apply-changes.md`). Batch mode remains available.
- [ ] Slice 3 (after RIT-T-0109): `update-structure` surfaces RIT-I-0017's "what the ATS sees" report instead of a standalone `AtsStructureReport`; no second ATS view is printed.
- [ ] No regression to the existing auto/batch baselining flow; full suite + repo-wide mypy stay green.
