# Auto-seed and grow the terminology alias index during ingest/tailoring

## Objective **[REQUIRED]**

Make the terminology alias index actually populate itself during the normal ingest/tailoring flow, so that
alias-aware matching (`match` / `check-keywords` / `check-gaps` / `suggest-terminology`) works from the very
first score instead of being inert out of the box. Today `suggest-terminology` and the alias-aware matchers
are deterministic CLOSED-lexicon matchers: they only mirror resume↔JD wording that already exists in the
built-in lexicon or the project's `alias_file`. On a fresh project `config.alias_file` is `None` and the
built-in lexicon is intentionally minimal, so terminology mirroring returns `[]` and coverage is understated
(e.g. resume "responsive UI" scores as missing the JD's "responsive design"; "mobile-web" misses
"mobile web"; "performance/SEO" misses "web performance"). **No flow step ever creates or grows `alias_file`,
so the whole agent-grown-alias capability (RIT-I-0009) is dormant.** This task adds the missing
orchestration: a truth-gated, human-confirmed pass that SEEDS the alias index after ingest and GROWS it on
every new job — reusing the existing terminology capabilities, not adding new matching logic.

### Type

### Priority
- [x] P1 - High (important for user experience) — without it, keyword coverage is silently understated on

### Business Justification **[CONDITIONAL: Feature]**
- **User Value**: Scores and gap lists reflect what the resume TRULY covers (mirrored wording counts),
  instead of penalizing the candidate for phrasing differences — without editing resume text and without
  fabricating. The alias index compounds in value as more jobs are ingested.
- **Business Value**: Activates already-built capabilities (RIT-I-0009 agent-grown alias index, RIT-I-0010
  terminology alignment) that are currently inert; higher-fidelity match scores are the tool's core promise.
- **Effort Estimate**: S–M. Mostly flow wiring + a candidate-pair generator with a fuzzy/stemmed pre-filter;
  reuses existing learn/suggest/align-terminology capabilities and the alias_file contract.

## Acceptance Criteria **[REQUIRED]**

- [ ] **Seed on first ingest**: Fresh project + one resume + one job, after the ingest/seed step →
      `alias_file` is CREATED and `config.alias_file` is SET (both persisted through the existing config
      contract, RIT-T-0091), populated only with human-confirmed truthful pairs.
- [ ] **Truthful pair honored on re-score**: A confirmed pair (e.g. `responsive UI → responsive design`)
      is honored by `match` and `check-gaps` on the next score, RAISING keyword coverage with NO change to
      resume text.
- [ ] **Grow, don't overwrite**: Ingesting a SECOND job re-runs the pass and APPENDS its new truthful pairs
      to the existing `alias_file` without dropping the first job's entries; duplicates are deduped.
- [ ] **Truth gate preserved**: No pair is added that the resume does not already substantiate. Every
      proposed pair passes human confirmation + the existing truth gate before entering `alias_file`; the
      conservative-lexicon guarantee is NOT weakened for unconfirmed pairs (unconfirmed proposals never
      silently affect scoring).
- [ ] **Explicit ordered flow step**: The tailoring runbook (`resume-workflow`) has alias seeding as an
      explicit step BETWEEN "ingest job" and "check-keywords/check-gaps", gated on "resume + job active", so
      match/check-gaps/suggest-terminology all run alias-aware from the first score.
- [ ] Gates green for any package touched (`ruff`/`mypy`/`pytest`); flow/doc changes verified for reference
      correctness.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- **Reuse, don't rebuild.** The alias_file contract, `learn-terminology` / `suggest-terminology` /
  `align-terminology` capabilities, and the human-confirmation + truth gate already exist. This is
  PRIMARILY a missing orchestration/flow requirement.
- **Candidate-pair generator (the one genuinely new bit).** The closed lexicon cannot PROPOSE pairs it does
  not already contain, so add a conservative fuzzy/stemmed pre-filter that proposes candidate synonym pairs
  between resume wording and JD keywords the resume ALREADY satisfies (e.g. token stemming, normalized
  edit-distance, hyphen/space variants like `mobile-web`↔`mobile web`). This generator only PROPOSES —
  every proposal must still pass human confirmation + the truth gate before it is written to `alias_file`.
  Keep it deterministic/offline where possible, consistent with the matcher's posture; no embeddings unless
  explicitly justified.
- **Seed vs grow.** Seeding (first run) creates `alias_file` + sets `config.alias_file`. Growing (each new
  job) loads the existing file, generates new candidates, confirms, and APPENDS+dedupes. Both go through the
  same confirmation/truth gate; the only difference is create-vs-append.
- **Flow placement.** Insert an ordered step in `resume-workflow` between job ingest and
  check-keywords/check-gaps, with the gate "resume + job active". This guarantees the first score is
  alias-aware.

Recommended Agent: opus + medium — spans the flow runbook, the config/alias_file contract, and a new but
bounded candidate-pair generator with a conservative pre-filter; the truth-gate/confirmation invariants are
load-bearing but the pieces to reuse are well-defined. (If the candidate generator turns out to need
non-trivial fuzzy-matching design, consider splitting that into its own task.)

### Dependencies
- RIT-I-0009 (Agent-Grown Alias Index) and RIT-I-0010 (Terminology-Alignment) — COMPLETED; this task
  activates them via flow.
- Config contract RIT-T-0091 (`alias_file` field, set-active/config persistence).
- Capabilities/skills: `learn-terminology`, `suggest-terminology`, `align-terminology`, and the alias-aware
  `match` / `check-keywords` / `check-gaps`.
- `resume-workflow` runbook (the ordered flow guide).

### Risk Considerations
- **Fabrication risk via the fuzzy pre-filter.** A looser proposer must never let an unsubstantiated pair
  into `alias_file`. Mitigation: proposer only suggests pairs where the resume already satisfies the term;
  human confirmation + truth gate are mandatory; unconfirmed pairs never affect scoring.
- **Overwrite/data-loss risk on grow.** Appending must dedupe and preserve prior entries; add a test that
  a second job never drops the first's pairs.
- **Scope creep into new matching logic.** Keep this orchestration-first; do not modify the deterministic
  matcher's core semantics beyond consuming a (now-populated) alias_file.
