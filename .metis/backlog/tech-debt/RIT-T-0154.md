# resume-kit MCP surface is an undocumented parallel path to the authoritative CLI (opaque schemas + init overlap)

> **DEFERRED — not blocking. Do not action until we have more evidence.**
> This is a developer-experience friction observation, not an error. Nothing failed; the
> CLI-driven path worked cleanly end to end. We are recording it so the friction is captured,
> but the right fix (document the MCP surface vs. thin it out vs. deprecate it) depends on
> whether the MCP tools are actually intended as a first-class entry point or just a
> byproduct of the CLI. Decide that direction with real usage evidence before spending effort
> here. Investigation/decision first; implementation only if warranted.

## Objective **[REQUIRED]**

Resolve the ambiguity between the resume-kit **MCP tool surface** and the **`resume-tool` CLI**,
which today behave as two parallel paths to the same work with the CLI as the de-facto source of
truth. Two concrete frictions were observed during a `parse-resume` ingest debug run on 2026-08-10
(resume-kit 0.9.0 / plugin 1.2.0):

- **F4 — Opaque MCP tool schemas.** Every resume-kit MCP tool advertises the same generic
  parameters (`alias_file`, `human_in_loop`, `no_llm`, `strict`) with `additionalProperties: true`
  and no per-tool documentation of what it accepts or returns. From the schema alone there is no way
  to tell what e.g. `project_init` accepts vs. what `resume_extract_text` accepts/returns. The real
  work ended up driven through the `resume-tool` CLI (which the skills also prefer), so the MCP tools
  were effectively redundant for this run.
- **F5 — `project_init` (MCP) vs. `resume-tool init` (CLI) overlap.** Running the MCP `project_init`
  did not remove the need to also run `resume-tool init` — the `parse-resume` skill instructed the
  CLI init afterwards. Both are idempotent so there was no harm, but which is the source of truth is
  unclear. The skills treat the CLI as authoritative and never call the MCP tools, so the whole MCP
  surface reads as a parallel, less-documented route to the same CLI.

The deliverable is a **decision** on the intended role of the MCP surface, and only then whichever
thin follow-through that decision implies (document it, or thin/deprecate it).

### Technical Debt Impact **[CONDITIONAL: Tech Debt]**
- **Current Problems**:
  - MCP tool schemas are self-similar and undocumented (`additionalProperties: true`, shared generic
    params), so a caller cannot discover per-tool inputs/outputs without reading source or guessing.
  - The MCP surface duplicates CLI capabilities but the skills route exclusively through the CLI,
    leaving the MCP tools as an unexercised, ambiguous second path (e.g. `project_init` vs CLI `init`).
  - New integrators face a "which entry point is authoritative?" question with no documented answer.
- **Benefits of Fixing**: One clearly-documented authoritative path; either the MCP tools become a
  first-class, self-describing surface, or they are thinned/deprecated so there is a single obvious
  way in. Less confusion for anyone (human or agent) driving resume-kit programmatically.
- **Risk Assessment**: Low risk to defer — nothing is broken and idempotency means the overlap is
  harmless today. Risk of acting prematurely: investing in documenting/hardening an MCP surface we
  might instead choose to retire. Hence: decide direction before implementing.

## Acceptance Criteria **[REQUIRED]**

- [ ] A recorded decision on the intended role of the resume-kit MCP surface: (a) first-class,
      self-describing entry point kept in parity with the CLI, or (b) thin wrapper / (c) deprecate in
      favor of the CLI-authoritative path. Capture the reasoning (likely a short ADR or a note on this task).
- [ ] The `project_init` (MCP) vs `resume-tool init` (CLI) relationship is stated explicitly: which is
      authoritative, and whether running one implies/obviates the other.
- [ ] IF direction (a): each MCP tool documents its real accepted params and return shape (no more
      blanket `additionalProperties: true` with only the shared generic params advertised), at least for
      the tools an integrator would actually call (`project_init`, `resume_extract_text`, and peers).
- [ ] IF direction (b)/(c): the redundant/undocumented tools are thinned or marked deprecated, and the
      skills' preference for the CLI is documented as the intended single path.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
Investigation/decision first. Before any code:
1. Enumerate which MCP tools are actually reachable and whether any skill or external consumer calls
   them (grep the skills + any known integrations). If nothing calls them, that strongly favors
   thinning/deprecating.
2. Confirm the `project_init` vs `init` relationship in code — do they write the same state, and does
   one detect the other's output? This settles the "source of truth" question factually.
3. Bring the decision to Daniel (human-in-the-loop) before implementing, since it shapes the public
   surface of the package.

Recommended Agent: opus + medium (surface-level API/DX decision touching the MCP tool definitions
and their relationship to the CLI + skills; needs reasoning across the MCP layer, CLI, and skill
guidance, but is bounded and mostly investigative until a direction is chosen).

### Dependencies
- resume-kit MCP server tool definitions (the `mcp__resume-kit__*` surface).
- `resume-tool` CLI (`init`, `extract-text`, `set-active`, …) and the state/config contract from
  RIT-T-0091 (init + set-active + config schema), which the CLI path already owns.
- The `parse-resume` / `parse-job` skills, which currently prefer the CLI.

### Risk Considerations
- Do not document or harden the MCP surface before the keep-vs-retire decision — that risks wasted
  work on tools we may deprecate.
- If tools are deprecated, preserve backward-compatible aliases per the project's established
  deprecation-alias convention rather than hard-removing.
