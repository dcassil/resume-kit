# Extract shared apply-changes runbook and refactor update-* skills to defer to it (RIT-A-0005 Decision B)

Implements **Decision B** of [[RIT-A-0005]]: extract the copy-pasted "propose → decide → commit → validate → learn" edit spine into one reusable `_shared/apply-changes.md` runbook, and refactor the `update-*` skills so each contains only its type-specific `create-change` step and then defers to the runbook. Depends on [[RIT-T-0123]] (the rename — **done**), so this task uses the new lexicon names throughout. Should land **before [[RIT-T-0120]]**, so 0120 authors `update-structure` / `update-best-practices` against the runbook instead of re-pasting the spine.

## Objective **[REQUIRED]**

Eliminate the duplicated edit-spine prose across the `update-*` skills by creating a single authoritative `_shared/apply-changes.md` runbook (phase vocabulary `create-change → request-change → apply-change → validate-facts → learn-change`) and reducing each `update-*` skill to its distinctive `create-change` body plus a reference to the runbook — with **no behavioral change** and **no capability/engine code change** (the runbook composes the existing `review-edits` orchestrator surfaces).

## The shared runbook — required contents

`_shared/apply-changes.md` must be self-contained enough that an agent handed a set of `ChangeProposal`s can complete the flow. It documents, as the five phases:

1. **create-change** (owned by the caller/type-skill; the runbook states the `ChangeProposal` contract: minimal `replace`/`append`/`add_skill`; include `original` on replace; a `reason`; never target identity/employer/title-of-record/date fields).
2. **request-change** — the mode prompt (`interactive` / `review_at_end` / `auto`), then the `open → prompt → decide` loop with the `EditFeedbackReasonCode` enum required on `reject`/`edit`, `--edited-content` for `edit`.
3. **apply-change** — `commit-session` hard gate; what to do on gate failure (missing decisions, contradicted claims, policy rejection, tamper) — stop and report, never patch around; `reconcile-session` for intentional out-of-band edits.
4. **validate-facts** — run the `validate-facts` skill on the committed `working_path`; unresolved unsupported/contradicted claims block export.
5. **learn-change** — note that decide auto-logs `EditFeedback` and commit returns `grown_aliases` (terminology growth) automatically; point to `learn-change` / `learn-terminology` for explicit out-of-session logging. Then re-score (`check-keywords`) and report before/after deltas.

The mode-prompt text and the reason-code enum, currently duplicated per skill, move into this runbook (single source of truth).

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
1. **Author the runbook first.** Lift the spine from the current `update-keywords` / `update-terminology` bodies (they are near-identical) into `_shared/apply-changes.md`, generalized over "a set of `ChangeProposal`s from any producer." Keep the exact surface names, flags, and gate semantics — this is a lift-and-generalize, not a rewrite.
2. **Refactor each `update-*` skill.** Replace steps 3–7 with a short "follow the shared change-application runbook" directive (mirroring how `_shared/prerequisites.md` is already referenced), leaving each skill's steps 1–2 (`create-change`: how it builds its proposals and proves truthfulness) intact and type-specific.
3. **Diff-verify parity.** Compare each skill's pre-refactor instruction set against (refactored skill + runbook) to prove no step was dropped. Because the "include" is an instruction to read another file, the runbook must be complete on its own.
4. Single-agent execution is sufficient (one new file + two focused edits); no fan-out needed. Author runbook → refactor update-keywords → refactor update-terminology → verify → commit/push. Docs-only; optional patch version bump if bundled with other plugin changes.
