# Investigate: which best-practices rules can ever fire auto_suggestible (standard did nothing without user facts)

## Objective **[REQUIRED]**

**Investigate** why the best-practices analyzer produced **zero** `auto_suggestible` rewrites on the ingest debug run — every finding was classified `needs_user_input`. Determine whether this is expected (the resume is genuinely clean on the mechanical axes) or a coverage gap (the auto-suggest rules are too narrow to ever fire on common mechanical wins). The concrete deliverable is an **answer plus a recommendation**; a **possible outcome is spawning a follow-up task** to change/fix the rule set. This ticket is investigation-first — do not change rules under it; if a change is warranted, create the fix task.

Discovered during the baseline step of a debug run on 2026-08-07 (resume-kit 0.9.0 / plugin 1.2.0).

## Backlog Item Details

### Type
- [x] Tech Debt - Code improvement or refactoring (investigation; may spawn a fix)

### Priority
- [x] P2 - Medium (not a failure — `standard` still produced, just did nothing without user facts; matters for whether baselining delivers value on clean-ish resumes)

### Technical Debt Impact
- **Current Problems**: On the test resume, `check-best-practices` surfaced only `needs_user_input` findings and zero `auto_suggestible` rewrites. Even mechanical wins that should be auto-applyable (weak/duty-verb openers, buzzwords) did not surface as auto-suggestible. Net effect: the `base → standard` step does nothing without the user supplying facts, so on a clean resume `standard` == `base` and the "auto-apply the safe rewrites" promise of baselining delivers no observable value.
- **Benefits of Fixing (if a fix is warranted)**: baselining produces visible mechanical improvements out of the box; users see the tool earn its keep before any Q&A; clearer separation between "we fixed this for you" vs "we need a fact from you."
- **Risk Assessment**: If we widen auto-suggestible rules carelessly, we risk auto-applying rewrites that alter meaning or need a fact — violating the truth / claim-preservation gate. Any rule promoted to auto_suggestible must be provably meaning-preserving.

## Implementation Notes **[CONDITIONAL: Technical Task]**

Read the best-practices analyzer's rule definitions and the `auto_suggestible` vs `needs_user_input` classification logic in `resume_kit` (the engine behind `check-best-practices` / `resume_check_ats` best-practices path). Build the per-rule capability matrix from the rules themselves rather than inferring from one run. Cross-check against the specific findings emitted on `resume-a` to place this run in the matrix.
