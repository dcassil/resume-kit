# Document that the non-ASCII faithfulness warning on -original.json is by-design (until export), not a defect

## Objective **[REQUIRED]**

Add a short, explicit note — in the `parse-resume` skill guidance and/or the `validate-faithfulness`
warning text — stating that a non-ASCII warning on the `-original.json` (e.g. `·` bullet separators
and `'` curly apostrophes) is **expected and correct**, not a defect, and that normalization is
deliberately deferred to export. This is a thin documentation fix: the behavior is already correct,
we are only closing the "is this a bug?" gap for the next person who sees the warning.

Observed during a `parse-resume` ingest debug run on 2026-08-10 (resume-kit 0.9.0 / plugin 1.2.0):
the source resume genuinely contains `·` and `'`. The faithfulness gate correctly warns about
non-ASCII characters, and the skill correctly instructs NOT to normalize them in `-original.json`
(faithful/lossless capture). The result is a permanent warning on every such resume until export —
which is by design, but currently undocumented, so it reads as an unexplained recurring warning.

### Technical Debt Impact **[CONDITIONAL: Tech Debt]**
- **Current Problems**: A correct-by-design non-ASCII warning fires on every resume containing typographic
  characters and persists on `-original.json` until export. Nothing explains that this is intended, so it
  looks like an outstanding issue to anyone reading the gate output.
- **Benefits of Fixing**: The next reader (human or agent) immediately understands the warning is expected
  on `-original.json` and that normalization happens at export — no wasted investigation, no premature
  "fix" that would break faithful capture.
- **Risk Assessment**: Trivial. The only risk of NOT documenting is repeated confusion and the temptation
  to "fix" the warning by normalizing `-original.json`, which would violate lossless capture.
