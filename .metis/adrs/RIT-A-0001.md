# ADR-1: Code-owned edit-session orchestrator with hard write gate

Supports [[RIT-I-0015]] — specifically the design task [[RIT-T-0098]] and its implementation
[[RIT-T-0099]].

## Context **[REQUIRED]**

> **Provenance note:** This ADR (and its parent initiative RIT-I-0015) was auto-drafted by
> subagents during the RIT-I-0014 run and initially recorded a "decided" status that had not
> actually been reviewed. Daniel Cassil reviewed the full initiative + ADR on 2026-08-05 and
> **explicitly approved** the substance and execution — so the `decided` status and decision_maker
> now reflect a real human decision as of that date.

Two real end-to-end tailoring sessions produced the same verdict: the plugin has an **excellent
deterministic core and a strong safety gate**, wrapped in a human-in-the-loop editing layer that is
"designed on paper but not actually wired together." The scoring half (`match`, `identify-gaps`,
`check-ats-structure`, `build-evidence`, `validate-truth`, `export`) is A-grade — fast, reproducible,
correct-first-try, CLI/MCP symmetric. The collaboration half (present change → accept/modify/reject →
capture reason → log → learn) graded **D on orchestration**: it is an *emergent behavior* three separate
agent-only skills (`inject-keywords`, `rank-edits`, `log-edit-feedback`) are supposed to produce, with no
orchestrator, no enforced gate, no CLI/MCP surface, and a weak learner at the end.

The tester's framing is the thesis of this decision: today the workflow is **correct-by-diligence** (its
quality is entirely a function of how disciplined the driving agent is); the goal is **correct-by-default**
(any agent does correct work with it). In the session, the agent bulk-edited the working JSON and skipped
the acceptance loop entirely on the first pass — nothing objected — because a gate that isn't enforced by
tooling is only a suggestion, and suggestions lose to expediency.

Crucially, a code review of `packages/alignment` found the review *machinery already exists* and is good:
- **`ReviewController`** — a deterministic, interface-agnostic, section-by-section human-review state
  machine (`initialize` → `prompt` → `apply_decision`).
- **`ReviewSession`** (Pydantic) — serializable review state explicitly designed to "round-trip between
  turns," holding `pending_changes`, `decisions`, `claim_provenance`, `evidence`, `expected_score_deltas`.
- **`ReviewAction`** enum — `approve / reject / edit / retry / reduce_freedom / increase_freedom / skip`.
- **`apply_diffs`** — deterministic, policy- and truth-gated diff application.
- **`ProjectConfig` / `save_config`** (RIT-T-0091, now complete) — atomic, backward-compatible state
  persistence under `resume-kit/`.

So the gap is **not** missing machinery. `ReviewController` is never reached because nothing **persists**
it to disk, **surfaces** it (no CLI/MCP), **feedback-logs** its decisions, gives it a **mode prompt**, or
binds an on-disk write to logged decisions with a **hard gate**. This ADR decides how to close that gap.

## Decision **[REQUIRED]**

Introduce a **code-owned edit-session orchestrator** implemented as a **thin wrapper around the existing
`ReviewController`** (co-located in `packages/alignment` to reuse `ReviewController`/`apply_diffs` without
a new cross-package edge). The wrapper owns exactly the four things `ReviewController` lacks —
**persistence, surfacing, feedback logging, and a hard write gate** — and changes none of the existing
review/apply/truth logic.

### 1. State model — persisted `EditSessionState`
Wrap (not replace) `ReviewSession` in an envelope:

```
EditSessionState = {
  session_id: str,
  mode: "interactive" | "review_at_end" | "auto",
  active_resume: str,              # path from ProjectConfig
  active_job: str,
  working_path: str,               # resume-kit/working/<resume>.tailored.json
  review_session: ReviewSession,   # REUSED as-is
  original_hash: str,              # sha256 of the -original.json at open()
  committed_hash: str | null,      # sha256 of working_path after last commit()
}
```

- **Single active session per project**, persisted at `resume-kit/working/edit-session.json`, bound to the
  current `(active_resume, active_job)`. Opening a session while another is live **archives** the prior to
  `resume-kit/learning/` first. This matches the existing single-user, per-project scope (config pointers,
  the feedback JSONL log) and keeps stateless-surface resume trivial: any CLI/MCP call re-loads the single
  session file — no session id needs to be threaded through every call.
- Persisted via the RIT-T-0091 atomic write helper (temp file + `os.replace`) so a crash cannot corrupt
  session state.

### 2. Lifecycle — facade capabilities with CLI/MCP/API parity
Surfaced as a `review-edits` command group (CLI), matching MCP tools, and API routes — restoring the
symmetry the scoring half already has:

| Capability | Behavior |
|---|---|
| `open-edit-session(mode, changes)` | Snapshot `original_hash`; seed `ReviewSession` from proposed `ChangeProposal`s (agent-authored **or** provider-generated). |
| `session-prompt()` | Delegate to `ReviewController.prompt` — returns the next section's per-change `Question`s (current/proposed content, reason, evidence ids, expected score impact). |
| `decide-change(path, action, reason_code, note?)` | Delegate to `ReviewController.apply_decision`, **and** append an `EditFeedback` record (RIT-T-0096 enum) via `record-edit-feedback` (RIT-T-0097). |
| `commit-session()` | **HARD GATE** (below) → `apply_diffs` → write `working_path` → store `committed_hash`. |
| `session-status()` | Progress, decided/pending/deferred lists, current truth summary. |

### 3. The hard write gate (enforced in `commit-session`)
Three checks; any failure refuses with a machine-readable error and non-zero CLI exit:
1. **Logged-decision check** — every change about to be applied must have a *terminal* logged decision
   (`approve/reject/edit/skip`), correlated by `ChangeProposal.path` (+`action` to disambiguate; a stable
   synthetic suffix only if one section carries two proposals on the same path). Unlogged change → refuse,
   naming offending paths.
2. **Truth check** — a change whose resulting claim classifies `CONTRADICTED` (post-RIT-T-0095 semantics)
   is refused even if "approved."
3. **Tamper detection** — before any session op, if `working_path` exists and its `sha256` ≠
   `committed_hash` (or ≠ `original_hash` before the first commit), refuse: *"working resume was edited
   outside the session; re-open or reconcile."* This is what actually closes the tester's exact bypass
   (out-of-band bulk editing). We cannot block a raw OS file write, but we make the sanctioned writer the
   only path that produces a *valid* state and detect drift on the next operation.

### 4. Modes (a thin policy over `ReviewController`; the gate is never weakened by mode)
- **interactive** — prompt → decide per change → incremental commits.
- **review_at_end** — collect all proposals, present a consolidated diff, then **still require a logged
  decision per change before commit**.
- **auto** — apply a change *without asking* iff **all** hold: resulting truth status is one of
  VERIFIED / SUPPORTED / USER_CONFIRMED; it does not touch a truth-failing path; and it is **not** a new
  skill/cert/employer **addition** (additions always need human confirmation). Everything else is deferred
  and reported. Auto still writes an `EditFeedback` per auto-decision (outcome `accepted`).

### 5. Provider-optional input
The session accepts **agent-authored `ChangeProposal`s directly** — no LLM provider required. Provider
generation via `align_resume(..., human_in_loop=True)` remains an *optional* upstream source feeding the
same session. This is what lets the loop run deterministically the way the tester needed.

### 6. Undo
Reuse `EditOutcome.undone`: undoing a committed change reverts that field to its `original`, re-commits
(new `committed_hash`), and logs an `EditFeedback` with outcome `undone` (which the learner already weighs
heavier than `rejected`).

## Alternatives Analysis **[CONDITIONAL: Complex Decision]**

| Option | Pros | Cons | Risk Level | Implementation Cost |
|--------|------|------|------------|-------------------|
| **Wrap `ReviewController` (chosen)** | Reuses tested review state machine + serialization + apply/truth gates; least new code; `ReviewController` stays pure | Adds a persistence/feedback/gate layer above it; two objects (`EditSessionState` wraps `ReviewSession`) | Low | M |
| New orchestrator beside it | Full control of the model | Duplicates working, tested machinery; risks divergence from `ReviewController`; more surface area for bugs | High | L |
| Extend `ReviewController` in place | Fewer layers | Mixes on-disk/session concerns into a currently-pure in-memory state machine; harder to test; breaks its "pure w.r.t. inputs" contract | Medium | M |
| **Gate: sanctioned-writer + tamper detection (chosen)** | Detects the tester's exact out-of-band bulk-edit bypass; strongest guarantee reachable without OS enforcement | A content hash to maintain; a legitimate manual reconcile path is needed | Low | S |
| Gate: sanctioned-writer only | Simpler | Does not catch out-of-band edits — relies on skills always routing through commit; the exact failure we saw | Medium | S |
| Identity: explicit `change_id` | Clean for duplicate-path edits | Schema change rippling through generation/review/apply + tests | Medium | M |
| Identity: `path` (+action) (chosen) | No schema change; `path` already on `ChangeProposal`/`ReviewDecision` | Needs a synthetic suffix in the rare same-path-twice case | Low | S |

## Rationale **[REQUIRED]**

The machinery to run a correct human-in-the-loop review already exists and is well-designed; the failure
is that it is unreachable and unenforced. Wrapping `ReviewController` therefore delivers the
"correct-by-default" goal with the **least new code and lowest risk** — we add wiring, not logic. Keeping
`ReviewController`/`apply_diffs`/truth untouched means the A-grade deterministic core and its tests are
undisturbed, and the independent truth-semantics fix (RIT-T-0095) composes cleanly.

The **hard gate must include tamper detection** because the specific, observed failure was an out-of-band
bulk edit, and a sanctioned-writer-only gate would not have caught it. Since we cannot block a raw file
write at the OS level, content-hash drift detection is the strongest honest guarantee: the sanctioned
writer is the only path to a *valid* state, and any drift is refused on the next op until reconciled.

**`path`-based identity** avoids a schema change that would ripple through generation, review, apply, and
their characterization tests — cost we take on only if duplicate-path-per-section proves common (it did
not in either session).

**Single active session** matches the product's actual single-user, per-project scope and removes the need
to thread a session id through every stateless CLI/MCP call — the same design that already makes
`active_resume`/`active_job` work.

## Consequences **[REQUIRED]**

### Positive
- The interactive review becomes a **real, enforced flow** — it cannot be skipped or half-implemented,
  turning correct-by-diligence into correct-by-default.
- `rank-edits` and `log-edit-feedback` gain CLI/MCP parity (via RIT-T-0097), so the learning loop captures
  signal by default instead of only when a diligent agent drives a Python API by hand.
- Out-of-band edits to the working resume are **detected**, protecting the safety-and-trust story that is
  the product's core value.
- No disruption to the deterministic scoring core or its tests; the truth fix lands independently.

### Negative
- A new persisted artifact (`edit-session.json`) and a content hash to maintain; a **reconcile path** must
  exist for the legitimate case where a user *intentionally* hand-edits the working resume (e.g.
  `reconcile-session` that re-hashes and warns, rather than a dead end).
- Slightly more ceremony for the agent (open → decide → commit) versus a free-form edit — mitigated by the
  `auto` mode and by the skills driving it.
- `commit-session` refusing on tamper/unlogged changes is a new failure mode agents/tests must handle.

### Neutral
- The session is single-active; juggling multiple jobs concurrently would require the deferred
  multi-session design (explicitly out of scope now, easy to add later behind an id parameter).
- Mode selection becomes a required up-front choice in the improve step of `resume-workflow`.
