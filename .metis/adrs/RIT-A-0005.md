# ADR-5: Uniform verb-noun skill lexicon and shared change-application runbook for resume-intelligence

**Proposed 2026-08-06 by Daniel Cassil.** Establishes (A) a controlled `verb-noun` naming lexicon for every `resume-intelligence` plugin skill, and (B) the extraction of the shared "propose → decide → commit → validate → learn" edit spine into one reusable `_shared/apply-changes.md` runbook that the `update-*` skills defer to. Directly de-risks [[RIT-T-0120]] (which is about to add two more edit skills) and [[RIT-I-0016]]'s baselining surfaces.

## Context **[REQUIRED]**

The `resume-intelligence` plugin currently ships 17 skills whose names accreted organically: `inject-keywords`, `update-terminology`, `identify-resume-gaps`, `check-ats-structure`, `check-keyword-match`, `build-candidate-evidence`, `resume-to-json`, `log-edit-feedback`, `manage-synonyms`, `review-tailored-resume`, etc. Two structural problems have emerged:

1. **The list is hard to scan and mentally group.** Verbs are inconsistent synonyms across skills that do the same *class* of thing — `inject` / `update` (both gated edits), `identify` / `check` (both read-only reports), `build` / `resume-to-json` (both ingest), `log` / `manage` (both persistence-for-learning). A reader cannot infer a skill's behavior class from its verb, and nothing names the shared machinery every edit skill rides.

2. **The edit spine is copy-pasted prose, about to be duplicated twice more.** `inject-keywords` and `update-terminology` share an identical 8-step body: build `ChangeProposal`s → prompt for mode → per-change prompt/decide (accept/modify/reject + reason code) → `commit-session` hard gate → `validate-truth` → re-score. Only the first two steps (which change type, what proposals) differ. [[RIT-T-0120]] will add `update-structure` (fix ATS issues) and `update-best-practices` for the RIT-I-0016 baselining work — pasting the same spine a third and fourth time. There is already a `_shared/prerequisites.md` include, proving the "factor shared skill prose" mechanism exists; the spine has simply never been extracted the same way.

A key enabling fact grounds both decisions: **the code layer already treats the spine phases as discrete verbs.** The edit-session orchestrator exposes `review-edits open / prompt / decide / commit / status / reconcile` against a persisted `working/edit-session.json`, and the hard write gate is enforced at `commit` regardless of how earlier phases were invoked. `decide` already auto-appends `EditFeedback`; `commit` already returns `grown_aliases`. So the universal apply-and-learn engine is ~90% present in code — this ADR is about **skill packaging and naming**, not new orchestration code, and carries no risk to the write-gate's atomicity.

This decision is fixed now, before [[RIT-T-0120]], because renaming after two more skills adopt the old ad-hoc pattern is strictly more expensive and because [[RIT-T-0120]]'s two new skills should be born into the target lexicon rather than migrated into it.

## Decision **[REQUIRED]**

**Decision A — a controlled `verb-noun` skill lexicon.** Every skill name is `verb-noun`, drawn from a closed vocabulary where each verb denotes exactly one behavior class and each noun one entity. The rule set:

**Verbs (behavior classes):**

| Verb | Means | Mutates the resume? |
|------|-------|---------------------|
| **parse** | source (file / posting) → canonical structured data | no |
| **extract** | derive structured records from already-parsed data | no |
| **check** | deterministic, read-only advisory report or score | no |
| **validate** | deterministic **hard gate** (pass/fail, can block a write) | no |
| **review** | subjective / LLM critique (advisory, non-deterministic) | no |
| **suggest** | enumerate options for a human to choose | no |
| **update** | user-facing gated editor family (drives the spine) | **yes** |
| **apply** | commit decided changes (the write step / spine phase) | **yes** |
| **learn** | persist knowledge for **future** runs; never touches the current resume | no |
| *(utility — genuinely distinct actions, kept as-is)* | `compare`, `select`, `rank`, `export` | varies |

The `parse` / `check` / `update` / `suggest` / `learn` picks each collapse a synonym set (parse⊃create/convert; check⊃report/identify; update⊃inject/modify/change; learn⊃log/record). **`validate` and `review` are deliberately reserved** rather than folded into `check`, because they encode product guarantees a plain "check" does not: `validate-*` can *block a write*; `review-*` is a *non-deterministic LLM opinion*. `apply` vs `learn` is the load-bearing split that removes the last ambiguous verb — **`apply` writes to the resume, `learn` writes only to `learning/` for future deterministic runs.**

**Nouns (entities):** `resume`, `job`, `evidence`, `facts` (evidence-backed claims), `keywords`, `terminology` (surface concept) / `synonyms` (stored alias index), `structure` (parse/layout risk), `change(s)` (unit of edit), plus retained domain nouns `gaps`, `versions`, `best-practices`. The format (`json`) is dropped from names — format is not identity.

**Decision B — extract the shared change-application runbook.** The spine (steps 3–7 of every edit skill) becomes one `_shared/apply-changes.md` runbook, expressed with an explicit **phase vocabulary**:

`create-change → request-change → apply-change → validate-facts → learn-change`

mapping to: build the `ChangeProposal`s → prompt/decide per change (accept/modify/reject + reason code) → `commit-session` hard gate (writes the resume) → run `validate-facts` + re-score → auto-log feedback / grow synonyms for future runs. The four `update-*` skills (`update-keywords`, `update-terminology`, `update-structure`, `update-best-practices`) shrink to *only* their type-specific `create-change` step and then `include` the shared runbook. This is a documentation/runbook extraction on top of the existing orchestrator surfaces — **no new capability code.**

**Full rename map** (◆ = future [[RIT-T-0120]] baselining skills, now born in-lexicon):

| Old | New | Group |
|-----|-----|-------|
| resume-to-json | **parse-resume** | ingest |
| job-to-json | **parse-job** | ingest |
| build-candidate-evidence | **extract-evidence** | ingest |
| check-ats-structure | **check-structure** | check |
| check-keyword-match | **check-keywords** | check |
| identify-resume-gaps | **check-gaps** | check |
| compare-resume-versions | **compare-versions** | check |
| select-best-resume | **select-resume** | check |
| validate-resume-truth | **validate-facts** | check (hard gate) |

| update-terminology | **update-terminology** | update (already canonical) |
| — ◆ | **update-structure** | update |
| — ◆ | **update-best-practices** | update |

## Alternatives Analysis **[CONDITIONAL: Complex Decision]**

| Option | Pros | Cons | Risk Level | Implementation Cost |
|--------|------|------|------------|-------------------|
| **A. Controlled `verb-noun` lexicon + single shared `apply-changes` runbook (CHOSEN)** | List groups by verb at a glance; new skills self-place; spine written once; type-skills become thin producers; `validate`/`apply`/`learn` distinctions preserved | One-time breaking rename across skills + cross-references; requires a migration decision (see Consequences) | Low–Medium | Medium (rename + one runbook extraction; no capability code) |
| **B. Keep names as-is; extract only the shared runbook** | Solves duplication; zero rename churn | Leaves the unreadable/inconsistent list; new 0120 skills still need names invented ad hoc; `learn` vs `apply` ambiguity persists in prose | Low | Low |
| **C. Break the spine into 5 independent skills (`create/request/apply/verify/learn-change`)** | Maximally granular; symmetric names | Two phases (`request`+`apply`) are one gated transaction with no standalone reuse; `verify`/`learn` duplicate existing skills; ×5 boilerplate; caller must sequence them | Medium | High |
| **D. Rename lexicon but collapse `validate`/`review` into `check`** | Fewer verbs | Loses the "this can block me" (gate) and "an LLM opined" (non-deterministic) signals — real product guarantees erased from names | Medium | Low |
| **E. Do nothing** | No work | Both problems compound as 0120 lands; technical-debt interest paid on every future skill | Low now, High later | Zero now |

## Rationale **[REQUIRED]**

The value of a skill list is that a reader can find and trust the right tool. A closed `verb-noun` lexicon (Option A) makes the list *groupable by construction* — every `check-*` is a safe read-only report, every `update-*` mutates through the gate, every `validate-*` can block — so behavior is inferable from the name and future skills have exactly one correct name. Reserving `validate` and `review` (rejecting Option D) keeps the two most safety-relevant signals — "can block a write" and "non-deterministic LLM output" — legible in the name itself. The `apply` (writes resume) vs `learn` (writes only future-learning state) split is what finally makes the verb set unambiguous, and it matches the code: `apply-change` = `commit`, `learn-change`/`learn-terminology` = the feedback/synonym stores that never touch the resume.

Extracting one shared runbook rather than five sibling skills (rejecting Option C) is driven by the code reality: `request`+`apply` are a single gated transaction with no independent reuse, and `verify`/`learn` already exist as skills — five skills would duplicate two and double boilerplate while shifting sequencing burden onto the caller. One runbook with a named phase vocabulary keeps the sequence authoritative and the type-skills thin. Option B (runbook only) leaves the readability problem and forces 0120 to invent names ad hoc; Option E lets both problems compound. The cost is a one-time rename, paid now while it is cheapest — before two more skills entrench the old pattern.

## Consequences **[REQUIRED]**

### Positive
- The skill list groups visually by verb; a reader infers behavior class (safe report vs gate vs mutation vs learning) from the name alone.
- New skills — starting with [[RIT-T-0120]]'s `update-structure` / `update-best-practices` — have exactly one correct name and inherit the shared runbook instead of copy-pasting it.
- The edit spine is authored and maintained once; a change to the decide/commit/validate flow updates every edit skill at its source.
- `validate` (blocks writes) and `review` (LLM opinion) remain legible as guarantees; `apply` vs `learn` makes "does this touch my resume?" answerable from the verb.
- Type-skills shrink to their genuinely distinctive part (`create-change`), improving signal-to-noise per skill file.

### Negative
- **Breaking rename.** Skill names are referenced by users, by cross-skill prose (e.g. `resume-workflow`, prerequisites gates that name upstream skills), and by the plugin manifest. All references must be updated atomically, and any external muscle-memory / docs referencing old names break. A migration strategy is required (recommended: hard-rename in one pass since these are pre-1.0 internal plugin skills, updating all in-repo references together; a deprecation-alias window is the fallback if any external consumer is known).
- Some renames slightly shift connotation and need a one-line description tweak so the folded verb reads correctly (`check-gaps` was `identify-resume-gaps`; `extract-evidence` was `build-candidate-evidence`).

### Neutral
- This ADR fixes the *lexicon and the runbook-extraction decision*; the mechanical rename + runbook authoring are implementation work to be decomposed into tasks (candidate: a small initiative or a task set under [[RIT-I-0016]], sequenced **before** RIT-T-0120 executes so 0120 lands in the new scheme).
- No capability/engine code changes: `apply-changes` composes the existing `review-edits` orchestrator surfaces, `validate-facts` is the renamed `validate-resume-truth` skill, and the learning stores are unchanged in behavior.
- `resume-workflow` and `export-resume` already satisfy the lexicon and are unchanged; `update-terminology` is already canonical.

## Review Schedule **[CONDITIONAL: Temporary Decision]**

### Review Triggers
- A new skill is proposed whose behavior fits none of the defined verbs cleanly (the verb set may need a principled addition, not an ad-hoc synonym).
- A future skill genuinely needs to both mutate the resume *and* persist future-learning state in one step (would test the `apply` vs `learn` split).
- An external consumer of the plugin is discovered that references old skill names (would force the deprecation-alias fallback over a hard rename).

### Scheduled Review
- **Next Review Date**: When [[RIT-T-0120]] begins — confirm its two new skills adopt the lexicon and consume `_shared/apply-changes.md` rather than re-pasting the spine.
- **Review Criteria**: Whether every skill (existing + new) has exactly one lexicon-correct name and every `update-*` skill defers to the shared runbook with only a `create-change` body of its own.
- **Sunset Date**: N/A — intended as a permanent naming/architecture convention for the plugin.
