# ADR-2: Separate scoring representation (ScoreDoc) from build representation via deterministic projection

## Context **[REQUIRED]**

Today a single structured resume model — `ResumeDocument` (`packages/schemas/src/resume_kit_schemas/resume.py`) —
serves three jobs at once: **build** (the source of truth for the finished resume and its export),
**score** (ATS structure + keyword/job-match analysis), and **learn** (feedback/preference derivation).
These jobs pull in different directions and the conflation is now causing measurable defects:

- **Scoring reads build-shaped fields directly.** `matching/keywords.py` and `ats/engine.py` read
  `additional.technicalSkills` (e.g. `ats/engine.py:215`, `keywords.py:197-213`) and walk the raw resume
  dict. When a resume legitimately carries skills inside a *categorized* section rather than the one
  hardcoded field, those keywords are under-counted — the observed **85.8 → 75.8** score drop where the
  tokens the ATS would have read fine were sitting in a section the scorer did not look at.
- **The score does not reflect what a machine actually reads.** A real ATS never sees our JSON. It reads
  the rendered artifact, extracts text, and re-segments it into canonical sections (Experience,
  Education, Skills, …) and entities (name, contact, per-role title/company/dates → computed
  years-of-experience). Scoring build-shaped fields measures *intent*, not *ATS reality*, and lets a
  render/formatting regression ship without moving the score.
- **Build and score cannot evolve independently.** Because scoring couples to build field names, any
  change to the build schema (custom sections, an eventual "ideal structure") risks silently breaking
  scoring, and vice-versa.

An independent agent review recommended splitting the model into distinct representations and scoring the
**rendered artifact** (render → extract text → re-segment). That is the truest possible score, but it
introduces a bundled PDF/DOCX text extractor as a hard dependency, **non-deterministic** scoring (PDF
text order varies across vendors), a parse-confidence model, and a source map for attribution — all of
which fight the deterministic, offline character that makes the rest of resume-kit trustworthy.

This decision fixes the *representation* split and the *how ScoreDoc is produced* question. It is
deliberately scoped to leave the build schema, renderer, and export untouched — those belong to a
separate, later "ideal resume structure" initiative.

## Decision **[REQUIRED]**

Introduce **two representations** with a one-directional derivation:

- **BuildDoc** — today's `ResumeDocument`, **unchanged**. Remains the single source of truth for building
  and exporting the resume. This ADR does not modify it, the renderer, or export.
- **ScoreDoc** — a new, derived, ATS-view representation: canonical ATS sections, extracted entities
  (name, contact, per-role title/company/date-range → computed years-of-experience), and a **zoned
  keyword index** (which tokens appear in which zone: experience / skills-list / summary / education /
  other).

ScoreDoc is produced by a **pure deterministic projection function** `BuildDoc → ScoreDoc` computed in
code — **not** by rendering and re-extracting text. All scoring paths are repointed to read **only
ScoreDoc**, never BuildDoc field names. Keyword/match scoring harvests tokens from every zone of the
zoned index with weights (**experience > skills-list > summary**) plus recency, mirroring ATS behavior.

A read-only **"what the ATS sees"** report is surfaced off ScoreDoc (detected sections, extracted
entities + computed YoE, zoned keyword breakdown) across the existing surface norm (facade + CLI + MCP +
API + skill).

## Alternatives Analysis **[CONDITIONAL: Complex Decision]**

| Option | Pros | Cons | Risk Level | Implementation Cost |
|--------|------|------|------------|-------------------|
| **Deterministic projection (chosen)** | Fixes the missed-keyword bug at the root; scoring depends on zero build field names; fully deterministic/offline; no new dependency; purely additive (build/renderer/export untouched) | Cannot by itself catch a *render* bug (BuildDoc→artifact divergence), since it never renders | Low | Medium — new schema + projection + repoint scoring + report |
| **Score the rendered artifact** | Truest to what an ATS actually reads; catches render/format regressions as score deltas | Bundled PDF/DOCX extractor as hard dependency; non-deterministic scoring; needs parse-confidence + source map; heavy, fights the deterministic character | High | High |
| **Keep single model, patch the scorer to read more fields** | Smallest change | Perpetuates the coupling; every new build-shape (custom/ideal sections) re-breaks scoring; no ATS-view artifact for the report | Medium | Low (but recurring) |

## Rationale **[REQUIRED]**

The stated primary need is narrow: **build JSON and score JSON must be different**, so building can stay
faithful to the finished resume while scoring stays faithful to ATS norms. A representation split alone
satisfies that; it does **not** require scoring the artifact.

Deterministic projection delivers the split while preserving what already makes resume-kit reliable —
deterministic, offline, no network/LLM in a scoring command. It structurally eliminates the
hardcoded-field bug (the projection harvests every zone; scoring can never again read one field and miss
categorized skills) without importing the nondeterminism, dependency weight, and parse-confidence
machinery that artifact-scoring demands.

The one thing projection cannot do — catch a *render* bug — is best addressed elsewhere and later: the
forthcoming "ideal resume structure" initiative constrains the renderer (less room to diverge), and an
optional render→extract **parity check** can be layered on top of projection without making the
authoritative score nondeterministic. Paying for a bundled extractor now, at the cost of determinism,
would be premature.

## Consequences **[REQUIRED]**

### Positive
- The 85.8→75.8 class of bug is fixed at the root: zoned harvesting means categorized skills score
  correctly.
- Build and score evolve independently; the later "ideal structure" work can reshape BuildDoc without
  touching scoring, which reads only ScoreDoc.
- Scoring stays fully deterministic and offline — no new dependency, no vendor-variance nondeterminism.
- A user-visible "what the ATS sees" report becomes nearly free and is the most legible payoff.

### Negative
- Two representations to keep coherent; the projection is now a load-bearing component that must be
  covered by golden-fixture tests.
- Projection alone does not detect render/format regressions — that gap is deferred (mitigated by the
  ideal-structure initiative and an optional later parity check).

### Neutral
- The two existing scores keep their identity: `check-structure` (parse-safety / structural) and
  `check-job-match` (content / match). ScoreDoc becomes the shared substrate both read from; no new score
  types are introduced.
- BuildDoc's `customSections` (keyed by `SectionType`) map into ScoreDoc zones by section type, so the
  projection already has everything it needs from the current schema.

  projection can be simplified or whether a parity check should be promoted.
- Field evidence that render/format regressions are shipping undetected — revisit adding the optional
  render→extract parity check (or, as a last resort, artifact-scoring for a specific path).

### Scheduled Review
- **Next Review Date**: When the ideal-resume-structure initiative enters design.
- **Review Criteria**: Whether projection remains sufficient, or a parity check / artifact-scoring path
  is warranted for render-fidelity coverage.
- **Sunset Date**: N/A — the representation split is intended to be permanent; only the render-coverage
  approach is provisional.
