# ADR-3: Resume version lineage (original → base → standard) with stage-specific validation gates

Supports [[RIT-I-0016]] — the resume-baselining onboarding pipeline. This ADR is **draft / proposed**; it records the version-model and gating decision for that initiative and awaits Daniel Cassil's review before it moves to `decided`.

## Context **[REQUIRED]**

The toolkit is today a **job-tailoring** pipeline. The deterministic ingest boundary (RIT-I-0014) produces exactly one persisted artifact per resume — `<name>-original.json` — behind a `validate-faithfulness` hard gate, and `ProjectConfig` / `config.json` tracks only `active_resume` / `active_job` (+ their source paths and `alias_file`). Every downstream capability (`check-keyword-match`, `inject-keywords`, `align-terminology`, `identify-resume-gaps`, …) then operates **against a specific job description**.

This means there is **no representation of "the candidate's best generic resume"** — a job-independent version that is (a) structurally clean enough to pass a basic ATS parse and (b) strengthened for wording quality — to serve as the stable input to all tailoring. Two consequences follow:

1. **We tailor from a weak baseline.** Structural defects (missing/oddly-named sections, detached dates, PII) and wording defects (duty-listing, buzzwords, no quantification) present in `original` are inherited by every tailored variant. Keyword optimization is layered on top of a resume a parser or recruiter may already reject.
2. **There is nowhere to persist the cleaned/strengthened result.** The config knows only `original`; the fix work done during onboarding (RIT-I-0016) has no home and no lifecycle.

RIT-I-0016 introduces an onboarding/baselining phase that runs once per resume, before any tailoring. That phase does **two materially different kinds of work** with **different correctness contracts**:

- **ATS structural / format / parse fixing** — largely deterministic and mechanically safe (rename a section to a conventional name, normalize date formats, strip prohibited PII, remove placeholder text). The governing invariant is **faithfulness to `original`**: we must not change the *meaning/claims*, only the *structure/presentation*. This is exactly the invariant the existing `validate-faithfulness` gate already enforces at ingest.
- **Generic best-practices wording improvement** — inherently judgment-laden and frequently requires **new facts the system does not have** (e.g. converting "Responsible for the billing service" into a quantified accomplishment needs a real metric from the user). The governing invariant here is **truth**: no fabricated numbers or unsupported claims may be introduced. This is exactly what the existing `validate-truth` (CONTRADICTED/UNSUPPORTED semantics, post-RIT-T-0095) gate enforces during edits.

The decision below is: **how many persisted versions do we introduce, and which validation gate governs each transition.** This is load-bearing for RIT-I-0016's decomposition (config schema, which engine each stage uses, and where the write gates sit) and for any adjacent initiative that reads/writes resume versions — hence recording it as an ADR before decomposing.

## Decision **[REQUIRED]**

Adopt a **three-version lineage** persisted in code-owned project state, with a **distinct validation gate per transition**:

```
             validate-faithfulness              validate-truth
   original ───────────────────────▶  base ───────────────────────▶ standard
  (immutable,     structural/format/       (ATS-passing,   generic best-      (default input
   faithful       parse fixes:              cleanly-        practices          for ALL
   ingest)        auto or interactive)      parseable)      walkthrough:       downstream
                                                            human-in-loop)     tailoring)
```

1. **`original`** — unchanged from RIT-I-0014. Immutable, faithful ingest, `<name>-original.json`.
2. **`base`** — `original` after **structural/format/parse** fixes only. Transition is governed by the **existing faithfulness gate**: `base` must be provably faithful to `original` (structure/presentation may change; claims may not). Written as `<name>-base.json`. `base`'s target is simply *passes a basic ATS structural check*. `auto` mode may produce `base` unattended because every fix it applies is deterministic and faithfulness-preserving.
3. **`standard`** — `base` after the **generic best-practices** human-in-the-loop walkthrough. Transition is governed by the **existing truth gate** (reused via the RIT-I-0015 edit-session orchestrator + hard write gate): every applied change — including rewrites built from user-supplied facts — must pass truth validation. Written as `<name>-standard.json`. `standard` **becomes the default input** for all downstream tailoring.

**Config / resolution decision.** Extend `ProjectConfig` with **optional, additive** `base` and `standard` pointers (plus source provenance mirroring `active_resume_source`). Active-resume resolution for tailoring becomes `standard ?? base ?? original`. Existing projects with only `-original` keep working unchanged (backward compatible). Atomic-write semantics (RIT-T-0091) preserved.

**Gate-reuse decision.** We introduce **no new validator**. `base` reuses `validate-faithfulness`; `standard` reuses `validate-truth` through the RIT-I-0015 orchestrator's hard write gate. The two stages are kept separate precisely so each maps cleanly onto one existing gate rather than needing a blended one.

**Engine decision.** `base` is produced by **extending the existing job-independent `resume_check_ats_structure` engine** (issue codes + fix affordances); `standard` is produced by a **new job-independent best-practices analyzer** (the generic wording model does not exist today and is distinct from the job-keyword-driven composite score).

**Read-model decision (coordination with [[RIT-A-0002]] / [[RIT-I-0017]]).** Both the extended structural check and the new best-practices analyzer **read ScoreDoc** — the canonical ATS view produced by 0017's deterministic `project_scoredoc(BuildDoc) → ScoreDoc` — rather than raw BuildDoc fields or hand-rolled section segmentation. Because 0017 also repoints `check_ats_structure` onto ScoreDoc, **0017's projection + ats repoint land before this initiative's engine extension**, and the new structural rules are authored against ScoreDoc from the start. Section canonicalization performed by the `base` fixer feeds 0017's `customSections → KeywordZone` mapping. This initiative reuses 0017's single "what the ATS sees" report rather than emitting a second ATS-view.

**Severity-taxonomy decision.** This initiative establishes the single grooming-finding **severity taxonomy** — hard-gate / warning / recommendation / review-note / out-of-scope-future — used by the best-practices findings. The industry-guidance-audit initiative [[RIT-I-0018]] **adopts and may extend** this taxonomy; it does not define a competing one.

## Alternatives Analysis **[CONDITIONAL: Complex Decision]**

| Option | Pros | Cons | Risk Level | Implementation Cost |
|--------|------|------|------------|-------------------|
| **A. Three versions, one gate per transition (CHOSEN)** | Each stage maps to exactly one existing gate; `auto` can safely stop at `base`; clean provenance; `standard` is a stable, meaningful default | Two new persisted artifacts + config pointers; more lifecycle to maintain | Low | Medium |
| **B. Two versions (`original → standard`), skip `base`** | Fewer artifacts; simpler config | Blends faithfulness-safe structural fixes with truth-gated wording judgment into one transition needing a combined gate; no safe unattended checkpoint; loses the "ATS-passing" milestone | Medium | Low–Medium |
| **C. No new persisted versions — fix in the working/tailored file at tailor time** | Zero schema change | Re-does baseline work per job; weak baseline persists; nowhere to encode the candidate's best generic resume; contradicts the initiative's premise | High | Low |
| **D. One combined `base+standard` gate (new blended validator)** | Single transition | New validator to build/maintain; duplicates logic already in faithfulness + truth; muddies the two distinct invariants | Medium–High | High |

## Rationale **[REQUIRED]**

The two kinds of onboarding work have **genuinely different correctness contracts**, and the system **already has one gate for each**. A three-version lineage lets each transition reuse exactly one existing gate (faithfulness for structure, truth for wording) instead of inventing a blended validator (Option D) or forcing both invariants through a single transition (Option B). It also yields a **safe unattended checkpoint**: because every `base` fix is deterministic and faithfulness-preserving, `auto` mode can produce `base` without a human, while `standard` — which can require fabricating-tempting facts — always stays behind the human-in-the-loop truth gate. Option C fails the initiative's core premise (persisting the candidate's best generic resume). The extra artifact/lineage cost of Option A is small and additive, and backward compatibility is preserved because the new pointers are optional.

Reusing `resume_check_ats_structure` for `base` and the RIT-I-0015 orchestrator for `standard` keeps this initiative from re-implementing machinery that already exists and is good — the same discipline RIT-A-0001 applied to the edit loop.

## Consequences **[REQUIRED]**

### Positive
- Tailoring always starts from a clean, ATS-passing, wording-strengthened `standard` — every downstream variant inherits the improvements instead of the defects.
- Each transition has a single, already-trusted gate; no new validator to build or audit.
- `auto` vs interactive has a principled boundary: unattended work can go as far as `base` (faithfulness-safe) but never fabricate facts for `standard` (truth-gated, human-in-loop).
- Clear provenance/lineage (`original → base → standard`) aids debugging, comparison (`compare-resume-versions`), and "why did this change?" questions.
- Additive, backward-compatible config change; existing `-original`-only projects are unaffected.

### Negative
- Two new persisted artifacts and config pointers to create, migrate, and keep consistent.
- More lifecycle/UX surface: users (and adjacent initiatives) must understand which version is active and that tailoring defaults to `standard`.
- Resolution order (`standard ?? base ?? original`) is a new invariant every version-consuming surface must honor consistently (parity-tested).

### Neutral
- The `base`/`standard` split intentionally partitions the ATS dos/donts: only structural/parse items gate `base`; wording/quality items gate `standard`; job-dependent items remain out of scope (in the tailoring skills).
- Source-file (PDF/DOCX) layout parse-risk detection remains a separate, bounded concern (RIT-I-0016 REQ-011) and does not change this version model.
