# T1: RequirementAnswer learning rail (extends RIT-I-0013) + dedupe + thin CLI/MCP surface

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0022]]

## Objective **[REQUIRED]**

Add a durable, append-only `RequirementAnswer` learning rail to `resume_kit_feedback`, EXTENDING the
existing RIT-I-0013 substrate (`learning/*.jsonl` + the `append_edit_feedback` / `append_preference_pair`
pattern). This rail records the user's durable answers to "do you have this requirement?" so the interview
(T2 / RIT-T-0159) can pre-filter already-answered items and future jobs never re-ask. Thin by design: ONE
new record type, append/load helpers, one deterministic dedupe function, and ONE thin CLI/MCP command so
the skill writes through the rail rather than hand-editing files. Do NOT stand up a new persistence
mechanism or a parallel store.

## Backlog Item Details **[CONDITIONAL: Backlog Item]**

N/A — this task is assigned to initiative RIT-I-0022.

## Acceptance Criteria **[REQUIRED]**

- [ ] A `RequirementAnswer` model exists in `resume_kit_feedback` with exactly these fields (no more):
      `requirement_key: str` (normalized), `answer: Literal["yes","no","not_in_context"]`,
      `context_tag: str | None`, `evidence_ref: str | None`, `ts: str`.
- [ ] `requirement_key` is produced by REUSING the existing normalization used by matching/keyword gap
      analysis (no new normalization scheme invented for this rail).
- [ ] `append_requirement_answer(record, *, base_path=None)` and `load_requirement_answers(*, base_path=None)`
      exist and follow the SAME append-only JSONL pattern and path convention as the existing learning logs
      (`learning/requirement-answers.jsonl`).
- [ ] `is_already_answered(requirement_key, context_tag) -> Literal["yes","no","not_in_context"] | None`
      encapsulates the dedupe rule: a global `yes`/`no` suppresses (returns the answer); a `not_in_context`
      suppresses ONLY on exact `requirement_key` match AND matching `context_tag`; otherwise returns `None`
      (eligible to ask). Last-write-wins if the same key is answered more than once.
- [ ] Exactly ONE thin CLI/MCP surface is added to write and read these records through the deterministic
      rail (mirroring how existing learning writes are surfaced); no other new command surface.
- [ ] Unit tests cover: append+load round-trip; global yes/no suppression; `not_in_context` suppressed on
      same context, eligible on differing/absent context; last-write-wins; empty-log load returns [].
- [ ] Gates green: `ruff`, `mypy` (feedback pkg), `pytest packages/feedback`.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Mirror `packages/feedback/src/resume_kit_feedback/log.py` exactly: constant relative path, `append_*`
  writer, load reader. Add the model next to the existing feedback models. Reuse the matching-side term
  normalization (see `resume_kit_matching/keywords.py`) for `requirement_key` — import it, do not reimplement.
- Keep `is_already_answered` pure and deterministic (no I/O beyond a provided in-memory list, or a thin
  wrapper that loads then delegates) so it is trivially testable.
- Surface: prefer extending the existing feedback CLI/MCP surface rather than a new module; one write verb,
  one read verb. If unclear where it belongs, follow the pattern used by `edit_feedback_record` / the
  existing `mcp__resume-kit__edit_feedback_record` tool.

Recommended Agent: opus + medium — small surface but it is the durable DATA CONTRACT that T1a, T2, and
future jobs depend on; the dedupe/context-scope semantics are load-bearing and must be exactly right.

### Dependencies
- RIT-I-0013 substrate (`resume_kit_feedback`: `log.py`, models) — BUILT.
- Matching normalization (`resume_kit_matching/keywords.py`) for `requirement_key`.
- Consumed by RIT-T-0158 (evidence_ref linkage) and RIT-T-0159 (pre-filter via `is_already_answered`).

### Risk Considerations
- Getting the `not_in_context` scope wrong (too broad → silently suppress legit different-context asks).
  Mitigation: default to ASK when uncertain; only suppress on exact key + matching context tag.
- Do not over-model: no free-text notes, no confidence scoring, no decay here (that lives in 0013's
  preference layer if ever needed). One record, five fields.
