# T1a: Evidence-as-proof fold-in so confirmed answers become injectable via existing route

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0022]]

## Objective **[REQUIRED]**

Make a confirmed "yes" from the interview actually usable as truthful proof, by implementing the LOCKED
decision — **option (a): fold confirmed `CandidateEvidence` into the master-equivalent proof source that
`analyze_keyword_gaps` already consults.** After this task, a requirement the user confirmed (with grounding
evidence captured) is classified INJECTABLE through the existing route, so `update-keywords` can propose a
truthful edit for it with NO new proof path added to `update-keywords`. This is the load-bearing integration
seam of the initiative; keep it minimal and reuse the existing master-as-proof mechanism.

## Backlog Item Details **[CONDITIONAL: Backlog Item]**

N/A — assigned to initiative RIT-I-0022.

## Acceptance Criteria **[REQUIRED]**

- [ ] Confirmed `CandidateEvidence` (captured on a "yes") is projected into the SAME proof surface that
      `analyze_keyword_gaps` / the injectable classifier already reads as "the candidate can prove this"
      (the master-equivalent source) — no second, parallel proof mechanism is introduced.
- [ ] A requirement/keyword that was `non_injectable` (missing from resume AND master) becomes `injectable`
      once backing `CandidateEvidence` exists for it — verified by a test that runs the gap analysis before
      and after folding in evidence.
- [ ] `update-keywords`' existing proof/injection path consumes this with NO code change to its proof logic
      (the fold-in makes the evidence visible through the route update-keywords already trusts).
- [ ] The truth/faithfulness gate is unchanged and still applies to any resulting edit — this task only
      changes what counts as PROVABLE, never what counts as FAITHFUL, and never fabricates.
- [ ] The fold-in reads evidence by the `evidence_ref` linkage established in T1 (RIT-T-0157) where relevant,
      so the answer rail and the evidence store stay consistent.
- [ ] Tests: (1) evidence → injectable transition; (2) no evidence → stays non_injectable; (3) evidence for
      requirement X does not spuriously make unrelated requirement Y injectable; (4) existing gap/keyword
      tests still pass unchanged.
- [ ] Gates green: `ruff`, `mypy` (matching + evidence + affected pkgs), `pytest` for matching/evidence and
      any package touched.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Start by locating the single seam where injectable classification consults the master as proof
  (`resume_kit_matching/keywords.py`, `analyze_keyword_gaps`; note RIT-T-0126: without a master, `injectable`
  is always empty). The fold-in should make confirmed evidence appear to that seam as additional
  master-equivalent proof — e.g. contributing the evidence's provable terms into the same proof set the
  classifier already builds from the master. Prefer the smallest change that reuses the existing set-building
  code; do not branch a new proof pathway.
- Reuse `resume_kit_evidence` / `CandidateEvidence` as-is for the evidence records; this task is about
  PROJECTION into the proof source, not new evidence modeling.
- Keep the projection deterministic and offline (no LLM), consistent with the matching engine's posture.

Recommended Agent: opus + high — this touches the injectable/proof seam that the rest of tailoring relies
on; a wrong choice here creates compounding rework across T2/T3 and the existing keyword-update flow. It is
the one place in this initiative to reason carefully and verify with before/after tests.

### Dependencies
- RIT-T-0157 (RequirementAnswer rail + `evidence_ref`) — for linkage; can develop in parallel but verify
  against its record shape.
- `resume_kit_matching` (`analyze_keyword_gaps`, keyword proof-set building), `resume_kit_evidence`
  (`CandidateEvidence`), and the `update-keywords` skill's existing proof path (consumer — read to confirm
  no change needed).

### Risk Considerations
- Over-broadening the proof source could make unrelated keywords falsely injectable. Mitigation: fold in
  ONLY the confirmed requirement's provable terms, scoped to that evidence record; test negative cases.
- Must not alter the faithfulness/truth gate or open a fabrication path — provability changes, faithfulness
  does not.
- If the proof source turns out to be more than one seam, STOP and note it in Status Updates before
  widening scope — the initiative assumes a single fold-in point; discovering otherwise is a design signal.

## Status Updates **[REQUIRED]**

### 2026-08-10 — Implemented (LOCKED option (a) fold-in)

**Single seam confirmed.** The proof surface the injectable classifier consults is
exactly one place: in `analyze_keyword_gaps` (`packages/matching/src/resume_kit_matching/keywords.py`),
a missing keyword is classified `injectable` iff `_match_keyword_in_text(keyword, master_text)`
matches. That `master_text` string is the sole master-equivalent proof surface (RIT-T-0126:
without a distinct master it is empty, so injectable is empty). No second seam was found —
the initiative's single-fold-in assumption holds; no scope widening needed.

**How the fold-in works.** Added a keyword-only `confirmed_evidence: Sequence[CandidateEvidence] | None`
parameter to `analyze_keyword_gaps`. A new helper `_confirmed_evidence_proof_text` projects the
verbatim `content` of `user_confirmed` evidence records into the SAME proof surface: the classifier
now reads `proof_text = master_text + " " + evidence_text` instead of `master_text`. Everything else
(the whole-term / alias matcher, the missing-keyword loop, potential-match math) is byte-for-byte
unchanged, so `update-keywords`' proof/injection path — which calls this function — consumes the
evidence with NO change to its proof logic. A confirmed "yes" simply becomes injectable through the
existing route.

**Scoping against false injectables.** Only `user_confirmed=True` records contribute, and only their
own `content` is projected. Because injectability is still decided by the existing whole-term matcher
over that content, evidence proving requirement X (content mentioning "Kubernetes") cannot make an
unrelated requirement Y ("FedRAMP") injectable — Y's term simply does not appear in the evidence text.
Verified by a dedicated negative test. The tailored-vs-master near-identical degeneracy warning still
compares the two resumes only (evidence is not part of that check), so it is unaffected.

**Truth/faithfulness gate unchanged.** This changes only what counts as PROVABLE (the injectable
split); it never fabricates and never touches the faithfulness/truth gate. Evidence read via the T1
`evidence_ref` linkage (the `CandidateEvidence` record a "yes" points at) is consistent with the
answer rail — the projection uses the same `CandidateEvidence` shape T1 links to.

**TDD.** Wrote `packages/matching/tests/test_keywords_evidence_proof.py` FIRST (5 tests, all RED with
`TypeError: unexpected keyword argument 'confirmed_evidence'`), then implemented: (1) evidence →
injectable transition (before/after in one test); (2) no evidence → stays non_injectable; (3) evidence
for X does not make unrelated Y injectable; (4) unconfirmed evidence does not prove; (5) a keyword
already in the resume stays matched, never re-classified. All green after the fold-in.
