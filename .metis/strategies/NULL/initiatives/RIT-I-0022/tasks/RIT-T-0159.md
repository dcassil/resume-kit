# T2: interview-missing-job-description skill (truth-gated, prioritized, four-choice loop)

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0022]]

## Objective **[REQUIRED]**

Author a new `interview-missing-job-description` skill: the interactive, truth-gated driver that walks the
user through the job's MISSING requirements in JD priority order, elicits durable answers with correct
semantics, captures grounding evidence on "yes", persists answers through the T1 rail, and re-scores on
demand. This is prose orchestration that REUSES existing capabilities (`analyze_keyword_gaps`,
`update-keywords`, `resume_kit_evidence`, `resume_check_job_match`, the T1 rail) — it adds no core code.

## Backlog Item Details **[CONDITIONAL: Backlog Item]**

N/A — assigned to initiative RIT-I-0022.

## Acceptance Criteria **[REQUIRED]**

- [ ] The skill builds its question queue from the active JD + `KeywordGapAnalysis` in strict priority
      order: REQUIRED requirements → PREFERRED/nice-to-have → remaining unmatched keywords. No ranking.
- [ ] Before asking, it pre-filters via T1's `is_already_answered` (skips global yes/no; skips
      `not_in_context` only when this job's context tag matches; otherwise asks).
- [ ] Each question offers exactly four responses with the correct, distinct semantics:
      - **No** → persist `RequirementAnswer{answer:"no"}`; no edit.
      - **Yes** → REQUIRE a grounding fact (where/when/what/scale-or-outcome); persist a `CandidateEvidence`
        record + `RequirementAnswer{answer:"yes", evidence_ref:...}`; THEN invoke the `update-keywords` path
        to propose a truthful edit through the normal edit-session gate. A bare "yes" with no grounding is
        NOT accepted.
      - **Need more info** → EXPLAIN the requirement and guide to a confident yes/no/not-in-context; loop
        back to the SAME question; never persist as durable truth; never suppress future asks (telemetry only).
      - **Not in this context** → persist `RequirementAnswer{answer:"not_in_context", context_tag:...}`; no edit.
- [ ] Cadence: after every 4 questions, offer "re-check score or continue"; whenever a score is shown, offer
      "continue questioning or move to final refinement". Re-score uses `resume_check_job_match`.
- [ ] Termination: the loop ends when the score crosses threshold, the user declines to continue, or the
      queue is exhausted — then control returns to the existing final-refinement step (no auto-finalize).
- [ ] Truth-safety: the skill never coaches the user toward "yes", never fabricates evidence, and every
      resulting edit still passes the existing truth/faithfulness gate. The skill is single-responsibility
      and self-gating per the project's skill conventions (RIT-I-0011).
- [ ] The skill is documented with a clear SKILL.md (purpose, when-to-run, the four-choice contract, the
      capabilities it calls) consistent with the other resume-intelligence skills; no new MCP/CLI surface is
      introduced here beyond T1's rail.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Model the skill on `update-keywords` / `check-gaps` (single-purpose, self-gating, confined subagent-friendly).
  It orchestrates; it does not reimplement gap analysis, injection, evidence, or scoring.
- "Yes" path: capture grounding → write `CandidateEvidence` (via `resume_kit_evidence` / extract-evidence
  path) → write `RequirementAnswer` with `evidence_ref` (T1 rail) → hand the now-injectable term to
  `update-keywords`. (Injectability is made possible by T1a/RIT-T-0158 — sequence after it.)
- Keep the interaction legible: one requirement per prompt, four clearly-labeled choices, explicit context
  tag derivation for `not_in_context` (coarse role/industry from the JD).

Recommended Agent: opus + medium — no core code, but the truth semantics (grounding-required "yes",
non-durable "need more info", context-scoped "no") and the loop/cadence control must be exactly right; this
is where the feature either honors or violates the truth posture.

### Dependencies
- RIT-T-0157 (RequirementAnswer rail + pre-filter) and RIT-T-0158 (evidence → injectable) — sequence AFTER
  both.
- Existing skills/capabilities: `update-keywords`, `check-gaps` / `analyze_keyword_gaps`, `extract-evidence` /
  `CandidateEvidence`, `resume_check_job_match`. Skill conventions from RIT-I-0011.

### Risk Considerations
- The biggest risk is semantic drift making the skill a keyword-stuffer: enforce grounding-on-yes and the
  non-durable "need more info" handling explicitly in the skill text.
- Avoid re-ask fatigue: rely on T1 pre-filtering; if the queue is large, respect the every-4 cadence rather
  than dumping all questions.
