# Build subsystem reuse inventory and classification matrix

## Parent Initiative

[[RIT-I-0001]] — Phase 0 — Upstream Audit of Resume-Matcher

## Objective

Phase 0 must classify every relevant Resume-Matcher subsystem using the Reuse / Extract / Adapt / Replace / New taxonomy. Use the pinned ./upstream/ clone from task 0 and write references/reuse-inventory.md only. This is an evidence-grounded audit: locate behavior in upstream files, inspect imports and tests, determine coupling, and classify each subsystem with a one-line justification and target package. No product code may be written.

## Acceptance Criteria

- [ ] references/reuse-inventory.md records the same pinned full upstream commit SHA from task 0 and explains the classification taxonomy: Reuse, Extract, Adapt, Replace, New.
- [ ] The inventory contains one row per relevant subsystem with at least these fields: subsystem, behavior summary, upstream path(s), commit SHA, classification, target package, key dependencies/imports, app.* coupling, upstream tests/fixtures, DB/frontend independence, no-LLM feasibility, and notes/blockers.
- [ ] Every strong reusable candidate from the vision is confirmed or refuted with code-grounded reasoning: MarkItDown PDF/DOCX extraction, Pydantic schemas, LLM resume-to-JSON parsing, date restoration, job keyword extraction, tailoring prompts, diff modification model, allowed paths, blocked fields, original-value verification, skill-addition gates, malformed/unsupported change rejection, omitted-content preservation, LiteLLM support, structural evaluators, and relevant tests.
- [ ] Every Adapt candidate from the vision is classified with code-grounded reasoning: LiteLLM provider integration, LLM configuration, resume parsing, job keyword extraction, improvement prompts, truthfulness prompts, skill-target planning, diff generation/verification, match scoring, cover-letter generation, and PDF/DOCX export.
- [ ] Replace/Leave-behind rows cover web frontend, tracker/Kanban, SQLite persistence, TinyDB migration compatibility, API routers, settings/API-key persistence UI, application job storage, navigation/state management, frontend PDF rendering, interview-preparation UI, and full local app deployment model.
- [ ] New rows cover capabilities absent from upstream: agent plugin package, MCP server, purpose-built CLI, stable public API contracts, freedom 0-10 policy, human-in-loop review controller, candidate evidence model, claim provenance, approved-claim bank, truth-validation engine as needed by resume-kit, multiple resume selection, job-hunter bridge, deterministic ATS engine, and standalone no-LLM analysis mode.

### Technical Approach
Use rg under ./upstream/ to find candidate modules, tests, prompts, config, API routers, persistence, and frontend boundaries. Favor upstream package metadata and imports over guesswork. When a subsystem spans multiple files, list the important files and summarize dependencies rather than pasting long code. Classifications should be conservative: Reuse only for mostly unchanged behavior, Extract for behavior that can be moved with minimal changes, Adapt for useful behavior needing new APIs/boundaries, Replace for unsuitable upstream implementation, and New where there is no meaningful equivalent. Keep target package names aligned with the initiative: document-parser, schemas, llm, matching, alignment, policy, export, tests/characterization, tests/fixtures, mcp, cli, api, evidence, ats, integrations/job-hunter.

### Constraint (teamwork orchestration)
Implementing agent WRITES FILES ONLY. Do not run git (no add/commit/branch/push). Do not run
repo-wide verification (lint/typecheck/build) — the orchestrator does that per wave. Assume zero
prior context beyond this document.

## Verification Steps

1. Run git -C upstream rev-parse HEAD and confirm the SHA matches every inventory row or the inventory-level SHA policy.
2. Use rg to spot-check at least one upstream source path and one upstream test path for parsing, matching, diff/alignment, provider/config, and export subsystems.
3. Confirm each vision-named Strong/Adapt/Replace/New candidate appears in references/reuse-inventory.md exactly once or is intentionally grouped with an explicit note.
4. Confirm every row answers whether it can run without upstream DB/frontend and whether it can operate without an LLM.
