# Diff-aware preference derivation: mine term-diffs (specific-over-vague), replace naive token frequency

## Parent Initiative

[[RIT-I-0015]]

## Objective **[REQUIRED]**

Make the preference learner actually learn. Rewrite `derive_preferences` so it mines the **term-diffs**
already captured on each `EditFeedback` record (`removed_terms` → `added_terms`, `preserved_terms`,
outcome, edit-distance) into meaningful patterns — most importantly "prefers specific over vague" — instead
of the current naive token-frequency count that surfaces stopwords and misses the dominant signal.

## Context

The `EditFeedback` log is well-designed and captured real signal in a live session: 8 records where the
user consistently replaced vague words with specifics (`fixes`→Chrome/Firefox/Edge, `improvements`→
Lighthouse/SSR, `quality`→compatibility). But `derive_preferences` (from RIT-T-0086,
`packages/feedback/src/resume_kit_feedback/preferences.py`) surfaced `accepted_phrases: ["and","for",
"mobile","react"]` and `disliked_patterns: []` — i.e. raw token frequency including stopwords, with the
single clearest pattern in the data (specific-over-vague) never reaching the profile. The log is smart;
the distiller is naive. This task fixes the distiller.

## Acceptance Criteria **[REQUIRED]**

- [ ] `derive_preferences` operates over **diffs**, not raw token frequency: for each record it uses
      `removed_terms`/`added_terms` (and `preserved_terms`, `outcome`, `edit_distance`) rather than
      counting all tokens. Stopwords are excluded from surfaced phrases.
- [ ] A **specificity signal** is derived: when accepted/accepted_modified edits systematically replace
      lower-specificity terms with higher-specificity ones (e.g. vague noun → named tool/technology/
      metric), the profile records a "prefers specific over vague" disliked-pattern (vague terms) +
      accepted-pattern (specific replacements). The live session's 8 records MUST produce this pattern
      (used as a fixture/assertion).
- [ ] Outcome weighting respected: `undone` weighs heavier than `rejected` (as already documented);
      `accepted_modified` contributes both the accepted (added) and rejected (removed) signal.
- [ ] `accepted_phrases` / `rejected_phrases` / `disliked_patterns` reflect genuine repeated signal (a
      minimum support threshold), not one-off tokens; confidence reflects support count with the existing
      time-decay approach.
- [ ] Consumes persisted `PreferencePair` records (from [[RIT-T-0096]]) where they sharpen the signal.
- [ ] Deterministic and offline (caller-supplied timestamps, no clock/network); existing preference
      consumers (Preference-RAG retrieval, ranker `voice_match`) keep working with the richer profile.
- [ ] Table-driven tests including the real 8-record session fixture asserting the specific-over-vague
      pattern is derived and stopwords are absent.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Rewrite the aggregation in `preferences.py` to iterate diffs. A pragmatic specificity heuristic:
  a term is "more specific" if it is a proper noun / named entity / contains digits / is a known
  tool-or-technology (reuse `resume-kit-terms` where possible) versus a generic abstract noun. Keep it
  deterministic and explainable — no ML.
- Preserve the existing profile schema (`UserPreferenceProfile`) field names; enrich their contents.

### Dependencies
Blocked by [[RIT-T-0096]] (PreferencePair persistence). Independent of the orchestrator; improves the
`voice_match` signal the ranker ([[RIT-T-0097]]) uses.

### Risk Considerations
Medium — the specificity heuristic is the judgment call; anchor it with the real session fixture so it is
validated against observed behavior, and keep it explainable so it can be tuned.

### Recommended Agent
**opus + high** — the core "make learning actually learn" algorithm; nuanced and load-bearing for the
whole preference-learning value proposition.
