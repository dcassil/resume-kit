# ADR + design: code-owned edit-session orchestrator and hard write gate

## Parent Initiative

[[RIT-I-0015]]

## Objective **[REQUIRED]**

Design — and capture in an ADR — the code-owned **edit-session orchestrator** and its **hard write gate**
before any implementation. This is the riskiest, most load-bearing, most cross-surface piece of the
initiative; a wrong contract compounds across every surface and the skill rewrites. The ADR must nail
down: the session state model, the mode contract (`interactive` / `review_at_end` / `auto`), the exact
semantics of the hard write gate (what is refused and how), and the cross-surface shape.

## Context

Today the improve loop is prose assembled by the agent from three agent-only skills, so it was bypassed
entirely in testing (bulk hand-edit, no per-change acceptance, zero feedback records). The decision (made
with Daniel) is a **hard gate**: the code-owned session is the only sanctioned write path to the working
resume during improve, and applying a change requires a logged accept/modify/reject decision. This task
produces the design that [[RIT-T-0099]] implements. It builds on [[RIT-T-0095]] (truth semantics),
[[RIT-T-0097]] (feedback/evidence surfaces), and [[RIT-T-0091]] (config/state contract).

## Acceptance Criteria **[REQUIRED]**

- [ ] An ADR document is created in Metis (`adr` type) capturing: context, decision, alternatives (hard
      vs soft gate — with the rationale for hard), consequences (positive + negative), and follow-ups.
- [ ] **Session state model** specified: an `EditSession` schema (session id, mode, working-resume path,
      list of candidate changes each with a stable `change_id`, per-change decision + reason_code, applied
      flag, truth status) and where it persists under `resume-kit/` (via RIT-T-0091 config contract).
- [ ] **Mode contract** specified: precise behavior of `interactive` (per-change prompt), `review_at_end`
      (batch propose, then confirm each before commit), and `auto` (apply only fully-supported,
      non-fabricating changes; defer anything requiring judgment). Defines how a mode is chosen/recorded.
- [ ] **Hard write-gate semantics** specified: the invariant ("no working-resume mutation during improve
      without a matching logged decision"), the machine-readable error shape when violated, and how the
      gate composes with `validate-truth` (truth failure blocks even an accepted change).
- [ ] **Cross-surface shape** specified: which operations are facade capabilities and how CLI/MCP/API
      expose the session lifecycle (open → present → decide → apply → validate → close), including how a
      stateless surface (CLI invocation, MCP call) resumes a persisted session.
- [ ] **Interaction with existing engine** documented: how the session calls `rank-edit-candidates`,
      `record-edit-feedback`, `validate-truth`, and `apply` (`packages/alignment/apply.py`) without
      duplicating them.
- [ ] Open questions and risks enumerated with a recommendation for each (e.g. concurrency/locking of the
      session file, undo semantics, how `auto` mode defines "fully supported").

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Produce the ADR + a design section that [[RIT-T-0099]] can implement directly. No production code in
  this task beyond possibly a schema sketch. Reuse existing `apply`/diff machinery in
  `packages/alignment` rather than inventing a new apply path.
- Anchor the write-gate on `change_id` correlation: `apply` refuses any change whose `change_id` lacks a
  logged decision in the session.

### Dependencies
Blocked by [[RIT-T-0095]] and [[RIT-T-0097]] (the session composes their outputs) and [[RIT-T-0091]]
(state persistence). Blocks [[RIT-T-0099]].

### Risk Considerations
High — this contract is load-bearing. Mitigate by front-loading it as its own task, reviewing with Daniel
before RIT-T-0099 starts, and enumerating open questions explicitly rather than deciding them implicitly
in code.

### Recommended Agent
**opus + high** — architecture/decomposition-defining design work; downstream implementation and skill
rewrites all depend on getting this contract right.
