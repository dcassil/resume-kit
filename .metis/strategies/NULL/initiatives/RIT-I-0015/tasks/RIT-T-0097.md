# Feedback & evidence cross-surface capabilities: record-edit-feedback, rank-edit-candidates, refresh-preferences, add-evidence --confirmed

## Parent Initiative

[[RIT-I-0015]]

## Objective **[REQUIRED]**

Give the deterministic feedback/learning engine and user-confirmation real, first-class surfaces so the
human-in-the-loop steps stop being agent-only (and therefore droppable). Add `record-edit-feedback`,
`rank-edit-candidates`, and `refresh-preferences` across facade + CLI + MCP + API with parity tests; add
`add-evidence --confirmed` to persist user-confirmed evidence; and fix the `build-evidence
--approved-claims` CLI parity bug. This is what turns "the learning loop got zero feedback records" into a
loop that actually captures signal, and turns a verbal "yes, that's true" into persisted evidence.

## Context

`rank-edits` and `log-edit-feedback` have no CLI/MCP/API/facade surface — their own docs say so
(`rank-edits/SKILL.md:36`, `log-edit-feedback/SKILL.md:32`), `REGISTRY` has no feedback capabilities
(`packages/facade/.../capabilities.py:722`), and MCP tool names omit them
(`packages/mcp/.../tools.py:46`). For evidence, an `approved_claims` input path exists in
engine/facade/MCP/API (`builder.py:71`, `capabilities.py:483`, `tools.py:318`, `api/models.py:172`) but is
inputs-only (never persisted), and the CLI `build-evidence --approved-claims` documented in the skill
does not exist (`packages/cli/.../app.py:362`). There is no way to record a user's verbal confirmation as
a persisted `user_confirmed` `CandidateEvidence`.

## Acceptance Criteria **[REQUIRED]**

- [ ] Facade capabilities added and registered in `REGISTRY` for: `record-edit-feedback` (append an
      `EditFeedback` — using the [[RIT-T-0096]] enum — and optional `PreferencePair`),
      `rank-edit-candidates` (deterministic heuristic ranker over `CandidateFeatures`, truth hard-block
      preserved), and `refresh-preferences` (derive/refresh the `UserPreferenceProfile`).
- [ ] CLI commands wrapping each capability, consistent with existing command style; JSON in/out.
- [ ] MCP tools + API routes added per the parity norm; cross-surface parity tests extended to include
      the new capabilities (matching the existing parity suite pattern).
- [ ] `add-evidence --confirmed` capability + CLI/MCP/API: deterministically construct a `user_confirmed`
      `CandidateEvidence` from provided content/kind/tags, persist it to a project evidence file under
      `resume-kit/` (via the [[RIT-T-0091]] config contract), and optionally update an `active_evidence`
      pointer. Idempotent-ish: appending the same confirmation does not corrupt the file.
- [ ] `build-evidence --approved-claims` CLI flag added so CLI matches the facade/MCP/API surface and the
      skill doc; parity test covers it.
- [ ] `rank-edit-candidates` accepts an `alias_file` so the ranker's truth signal is synonym-aware,
      consistent with [[RIT-T-0095]] (no truthful alias falsely hard-blocked).
- [ ] **Envelope-seam fix**: `build-evidence` returns an envelope (`{data: [...]}`) but
      `validate-truth --evidence` expects a bare array — two first-party tools in the same pipeline
      disagree on shape (observed in a live session; required a manual `.data` extraction). Reconcile so
      the loop's evidence I/O is consistent: either `validate-truth --evidence` accepts the envelope, or a
      documented canonical evidence shape both produce/consume. Add a parity/round-trip test asserting
      `build-evidence` output feeds `validate-truth` with no reshaping.
- [ ] `add-evidence --confirmed` returns/derives **stable evidence IDs** (deterministic from content/kind)
      so confirmations are reusable and never require the agent to re-derive IDs by hand.
- [ ] Unit + parity tests green across all four surfaces.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Keep `packages/feedback` as the deterministic engine; the facade capabilities are thin adapters that
  call `append_edit_feedback`, the ranker, and preference derivation. Follow the existing capability +
  `REGISTRY` + CLI + MCP + API + parity-test pattern used by `build-evidence`/`validate-truth`.
- `add-evidence --confirmed` writes to a project evidence file (JSON/JSONL) under `resume-kit/`; use the
  RIT-T-0091 config schema to record/point at it. Reuse `CandidateEvidence`/`EvidenceKind` from schemas.

### Dependencies
Blocked by [[RIT-T-0091]] (config contract for persistence) and [[RIT-T-0096]] (reason enum). Consumes
[[RIT-T-0095]] (synonym-aware truth). Feeds [[RIT-T-0099]] (the orchestrator calls these surfaces).

### Risk Considerations
Medium — cross-surface parity is the bulk of the effort; keep the engine untouched to limit blast radius.
Ensure the evidence-file writer is atomic to avoid corrupt state on failure.

### Recommended Agent
**opus + high** — new cross-surface capabilities + parity substrate that the orchestrator depends on.
