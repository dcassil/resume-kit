# Implement edit-session orchestrator + hard write gate across facade/CLI/MCP/API

## Parent Initiative

[[RIT-I-0015]]

## Objective **[REQUIRED]**

Implement the code-owned edit-session orchestrator and its hard write gate exactly as designed in the
decided ADR [[RIT-A-0001]] (see also [[RIT-T-0098]]), surfaced as a `review-edits` command group across
facade + CLI + MCP + API with parity tests. After this task, applying an edit to the working resume
during improve is impossible without a logged accept/modify/reject decision, and the three-mode loop
(`interactive` / `review_at_end` / `auto`) is a real code flow rather than skill prose.

Implement as a **thin wrapper around the existing `ReviewController`** (per [[RIT-A-0001]]) — reuse
`ReviewSession`, `apply_diffs`, and truth as-is; add only persistence, surfacing, feedback logging, and the
gate.

## Context

The improve loop's human-in-the-loop UX is designed but not wired; a hard gate is required (per decision)
because a prose instruction was trivially bypassed in testing. This task lands the ADR design, composing
the truth semantics from [[RIT-T-0095]] and the feedback/evidence surfaces from [[RIT-T-0097]] over the
[[RIT-T-0091]] state contract.

## Acceptance Criteria

## Acceptance Criteria **[REQUIRED]**

- [ ] `EditSessionState` envelope (wrapping `ReviewSession`) + persistence implemented per [[RIT-A-0001]]:
      single active session at `resume-kit/working/edit-session.json` bound to `(active_resume,
      active_job)`, atomic writes, prior session archived to `learning/` on new open. Stores
      `original_hash` and `committed_hash` (sha256).
- [ ] Facade capabilities for the session lifecycle: `open-edit-session` (records mode, seeds
      `ReviewSession` from agent-authored OR provider-generated `ChangeProposal`s), `session-prompt`
      (delegates to `ReviewController.prompt`), `decide-change` (delegates to
      `ReviewController.apply_decision`; appends `EditFeedback` via [[RIT-T-0097]] with the `reason_code`),
      `commit-session` (HARD GATE), `session-status`, and `reconcile-session` (re-hash + warn for
      intentional manual edits — the escape hatch for tamper detection).
- [ ] **Hard write gate enforced in `commit-session`** (three checks, any failure → machine-readable
      error + non-zero exit): (1) every applied change has a terminal logged decision, correlated by
      `path`(+action); (2) a `CONTRADICTED` result is refused even if approved; (3) **tamper detection** —
      refuse if `sha256(working_path)` ≠ `committed_hash` (or ≠ `original_hash` pre-first-commit) with the
      message "working resume edited outside the session; re-open or reconcile".
- [ ] All three modes implemented and behave per the ADR (`auto` applies only fully-supported,
      non-fabricating changes and defers the rest with a report).
- [ ] CLI + MCP + API expose the lifecycle; a stateless surface resumes the persisted session by id.
- [ ] Re-scoring integrates: after applies, the session can report updated `match`/`ats` deltas by calling
      existing scorers (no reimplementation).
- [ ] Unit tests: gate refuses unlogged write; gate refuses truth-failing accepted change; each mode's
      happy path. Cross-surface parity tests for the lifecycle operations.

## Test Cases **[CONDITIONAL: Testing Task]**

### Test Case 1: Unlogged write is refused
- **Test ID**: TC-001
- **Steps**: open a session; attempt `apply-change` for a `change_id` with no `decide-change` logged.
- **Expected Results**: refused with machine-readable error; working resume unchanged; non-zero CLI exit.
- **Status**: Pass/Fail

### Test Case 2: Truth-failing accepted change is refused
- **Test ID**: TC-002
- **Steps**: `decide-change` accept a change that introduces a `CONTRADICTED` claim; `apply-change`.
- **Expected Results**: apply refused on truth failure; reason surfaced.
- **Status**: Pass/Fail

### Test Case 3: auto mode defers judgment changes
- **Test ID**: TC-003
- **Steps**: run a session in `auto` with a mix of fully-supported and judgment-required changes.
- **Expected Results**: supported changes applied; judgment ones deferred and reported, not applied.
- **Status**: Pass/Fail

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Reuse `packages/alignment/apply.py` diff-application under the gate; the gate is a precondition check on
  logged decisions correlated by `change_id`, not a new apply engine.
- Compose `rank-edit-candidates` / `record-edit-feedback` / `validate-truth` from [[RIT-T-0097]]/[[RIT-T-0095]];
  do not duplicate their logic.
