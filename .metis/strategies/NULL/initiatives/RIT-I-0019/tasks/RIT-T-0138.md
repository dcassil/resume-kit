# Surfaces + update-shape skill + workflow wiring

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0019]]

## Objective **[REQUIRED]**

Phase 6 of RIT-I-0019. Expose `analyze_resume_shape` and `build_structure` across all surfaces
(facade capability functions → CLI → MCP → API) with cross-surface parity, add the `update-shape`
plugin skill, and wire it into `resume-workflow` between the structural/`base` step and the
wording (`standardize`) step.

## Acceptance Criteria **[REQUIRED]**

- [ ] Facade capability functions surface `analyze_resume_shape` and `build_structure`
      (consistent with existing facade capability wrappers).
- [ ] CLI: `resume-tool analyze-shape` and `resume-tool build-structure` commands, matching the
      argument/exit-code conventions of existing commands (gate failure → non-zero exit).
- [ ] MCP: `resume_analyze_shape` and `resume_build_structure` tools registered on the MCP
      server with schemas mirroring the facade signatures.
- [ ] API: routes exposing shape analysis and structure build, parity with the other surfaces.
- [ ] Cross-surface parity tests: facade/CLI/MCP/API produce identical shape reports, identical
      `structure` output, and identical lineage state for the same input (mirroring existing
      parity-test patterns).
- [ ] An `update-shape` plugin skill under `plugins/resume-intelligence/skills/` drives the
      structure pass conversationally: runs the analyzer, applies auto-safe canonicalization,
      surfaces ambiguous section mappings for a decision (never guesses), and never removes
      content. It is single-responsibility and mirrors existing skill conventions
      (frontmatter, `_shared` gate usage, capability-call pattern).
- [ ] `resume-workflow` is updated to insert the structure step **after** `update-structure`/
      `base` and **before** the wording pass, with prerequisite-gating phrasing consistent with
      the existing guide.
- [ ] The `update-shape` skill does not over-claim: it states the pass is deterministic,
      non-destructive, does no wording change and no budget/trim, and defers ambiguous mappings.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
Follow the established surface-adapter chain used by prior capabilities (e.g. `build_base`/
`build_standard` → `resume_build_base`/`resume_build_standard` CLI/MCP/API). Keep adapters thin —
all logic stays in the facade/engine. Author `update-shape` using an existing baselining skill
(e.g. `update-structure`) as the template. Wire the workflow ordering and gate phrasing to match
how baselining already gates tailoring. Reuse the RIT-I-0017 "what the ATS sees" report where a
report view is shown rather than emitting a new one.
