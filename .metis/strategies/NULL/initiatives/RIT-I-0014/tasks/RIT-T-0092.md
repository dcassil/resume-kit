# validate-faithfulness deterministic HARD GATE (engine + surfaces)

## Parent Initiative

[[RIT-I-0014]]

## Objective **[REQUIRED]**

Add the deterministic **faithfulness HARD GATE**: `resume-tool validate-faithfulness` compares the agent-produced `ResumeDocument` JSON against the original source (file or extracted text) and exits non-zero on drift, emitting a machine-readable report of dropped / added / altered content and count mismatches. This is the highest-value new capability — it turns the skill's prose "count the bullets and confirm they match" self-check into a real machine gate that blocks writing an unfaithful conversion.

## Context

There is no faithfulness check anywhere in the engine today. `validate-truth` is a different question (resume claims vs. `CandidateEvidence` derived from the resume — internal consistency, not fidelity to the source document), so it must NOT be repurposed. The interpretation step (text→schema) is agentic and therefore fallible; without a deterministic gate, silent drops/embellishments reach `-original.json`. This gate is what makes it safe to keep interpretation agent-driven.

## Acceptance Criteria

## Acceptance Criteria

## Acceptance Criteria **[REQUIRED]**

- [ ] New engine module (small package or module consumed by the facade) implementing faithfulness checks between source text and a `ResumeDocument`:
  - bullet-count and section-count parity,
  - token-set diff: tokens present in source but absent from JSON (dropped) and tokens in JSON absent from source (added/possibly fabricated),
  - non-ASCII scan (reuse the existing ATS-engine logic rather than reimplementing),
  - verbatim-substring spot checks on high-signal fields (employer names, titles, dates).
- [ ] A `FaithfulnessReport` result schema: overall `passed: bool`, per-check findings with codes (e.g. `BULLET_COUNT_MISMATCH`, `DROPPED_TOKENS`, `ADDED_TOKENS`, `NON_ASCII`), and the offending items.
- [ ] Tolerance/normalization rules (whitespace, casing, punctuation folding — including the non-ASCII punctuation résumés use: middots, curly quotes, en/em dashes) so a **faithful** conversion passes with zero false positives, while genuine drops/alterations fail. **This rule design is the human-in-the-loop checkpoint — confirm with Daniel before finalizing thresholds.**
- [ ] `resume-tool validate-faithfulness --source <file|-> --json <ResumeDocument.json>` accepts either a source file (runs extract-text internally) or pre-extracted text; exits non-zero when `passed=false`; prints the report JSON.
- [ ] Facade capability + MCP/API surfaces per the parity norm (or documented why skipped).
- [ ] Table-driven unit tests: faithful conversion passes; each of {dropped bullet, altered date, added fabricated bullet, section omitted} fails with the right code; a résumé using middots/curly quotes still passes content parity (non-ASCII reported as a warning, not a content-loss failure).

## Implementation Notes **[REQUIRED]**

### Technical Approach
Deterministic diffing only — no LLM. Normalize both sides (source text and flattened JSON text) through a shared normalizer (reuse `resume-kit-terms` normalization where sensible, and the ATS non-ASCII scanner) before comparing token multisets. Report is data, not exceptions; the CLI maps `passed=false` to a non-zero exit. Keep the checker pure and unit-test-friendly (source_text + ResumeDocument → FaithfulnessReport). Accept an optional source path from the config-owner ([[RIT-T-0091]]) but also allow explicit `--source` so this task is testable independently.

### Dependencies
Best wired after [[RIT-T-0091]] (recorded source path) and alongside [[RIT-T-0090]] (extract-text for the `--source <file>` convenience path), but the core checker only needs source text + JSON, so it is not hard-blocked. Consumed by [[RIT-T-0093]].

### Risk Considerations
Primary hazard: **false positives** from over-strict normalization would make the gate reject faithful conversions and erode trust. Mitigate with the table-driven test matrix and the human-in-the-loop threshold review. Secondary: false negatives (missing a subtle alteration) — accept some for v1; count parity + token diff catches the incident class that actually occurred.

### Recommended Agent
`opus + high` — core new algorithm with load-bearing correctness (a wrong tolerance model creates compounding trust/rework problems), plus a new schema other tasks consume. Getting the normalization/tolerance design right is the crux of the whole initiative.
