# Code-owned resume-kit state contract: init + set-active + config schema

## Parent Initiative

[[RIT-I-0014]]

## Objective **[REQUIRED]**

Give the `resume-kit/` working-directory state contract a code owner. Add deterministic `resume-tool init` (scaffold the folder tree + `config.json`) and `resume-tool set-active` (record `active_resume` / `active_job` **and** the originating source file path), backed by a machine-owned config schema. This removes the hand-scaffolding the tester had to improvise and provides the recorded source path that the faithfulness gate ([[RIT-T-0092]]) needs.

## Context

Today the `resume-kit/` folder, `config.json`, and the `active_resume`/`active_job` pointers are pure skill conventions — no code reads or writes them (only `alias_file` is passed through as a parameter). That means the agent hand-authors config and can drift from the canonical shape, and there is nowhere machine-readable that records which source file a given `-original.json` came from. The faithfulness gate cannot wire cleanly without that source-path record.

## Acceptance Criteria

## Acceptance Criteria **[REQUIRED]**

- [ ] A code-owned config schema (Pydantic model) for `config.json` covering at least: `active_resume`, `active_job`, `alias_file`, and a per-active-document **source file path** (e.g. `active_resume_source`, `active_job_source`) plus room for existing preference keys. Backward-compatible load of existing hand-written config.json (tolerate/forward unknown keys; do not clobber preferences).
- [ ] `resume-tool init` deterministically creates the `resume-kit/` tree (`config.json`, `resumes/`, `jobs/`, `working/`, `learning/`) and is **idempotent** — re-running does not overwrite existing pointers or delete content.
- [ ] `resume-tool set-active --resume <json> [--source <file>]` and `--job <json> [--source <file>]` update the pointers and source paths through the schema (atomic write; no partial/corrupt config on failure).
- [ ] Facade capabilities back both commands; MCP/API surfaced per the parity norm (or documented why skipped).
- [ ] Unit tests: idempotent init; set-active records pointer + source; existing config.json with preference keys survives a set-active round-trip.
- [ ] Public exports + config-schema documented in README working-dir section.

## Test Cases

### Test Case 1: Idempotent init
- **Test ID**: TC-001
- **Steps**: run `init` twice; between runs write a value into config.json.
- **Expected Results**: tree exists after first run; second run preserves the written value and existing pointers.
- **Status**: Pass/Fail

### Test Case 2: set-active records source path
- **Test ID**: TC-002
- **Steps**: `set-active --resume resumes/x-original.json --source /path/x.docx`.
- **Expected Results**: config.json `active_resume` + `active_resume_source` set via schema; other keys untouched.
- **Status**: Pass/Fail

## Implementation Notes **[REQUIRED]**

### Technical Approach
Introduce a small config-owner module (likely in core or a dedicated tiny module) with a Pydantic `ProjectConfig` schema and load/save helpers (atomic write via temp-file rename). `init` and `set-active` are thin facade capabilities + Typer commands over it. Preserve the existing `alias_file` semantics and any preference-learning keys already written to config.json (RIT-I-0013). Keep the folder layout identical to the current skill convention so existing projects keep working.

### Dependencies
Foundational for [[RIT-T-0092]] (needs the recorded source path) and [[RIT-T-0093]] (skills call `set-active`). No upstream dependency; can proceed in parallel with [[RIT-T-0090]].

### Risk Considerations
Main risk: clobbering config.json content written by other skills (preference learning, alias pointer). Mitigate with backward-compatible schema (extra keys preserved) and a round-trip test. Atomic writes prevent corruption on crash.

### Recommended Agent
`opus + medium` — introduces a new state contract other tasks depend on, touches multiple surfaces, and must preserve backward-compatible config semantics; substantive but follows the established facade/CLI pattern.
