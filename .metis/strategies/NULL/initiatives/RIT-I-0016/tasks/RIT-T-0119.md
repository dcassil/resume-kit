# Surfaces: facade + CLI/MCP/API adapters + cross-surface parity for baselining capabilities

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0016]]

## Objective **[REQUIRED]**

Expose the RIT-I-0016 baselining capabilities across all four surfaces with parity, following the established capability pattern (a facade capability registered in the facade `REGISTRY`, backed by thin CLI commands, MCP tools, and API routes, and covered by cross-surface parity tests) already used by the existing scoring and edit capabilities. The capabilities to surface are: (1) run the extended job-independent ATS **structural check**, (2) run the **`base` fixer** driver in `auto` or `interactive` mode, (3) run the generic **best-practices score** (emitting the `BestPracticesReport`), and (4) drive the **`standard` walkthrough** lifecycle (open / decide / commit) from RIT-T-0118. Cross-surface parity (identical results for identical inputs) is the load-bearing invariant, consistent with NFR-004.

## Acceptance Criteria **[REQUIRED]**

- [ ] Facade capabilities exist and are registered in the facade `REGISTRY` for: (a) run structural check, (b) run `base` fixer (`auto`/`interactive`), (c) run best-practices score, (d) drive the `standard` walkthrough lifecycle (open/decide/commit).
- [ ] CLI commands, MCP tools, and API routes each expose all four capabilities with consistent input and output contracts (same field names, same result shapes) across surfaces.
- [ ] Cross-surface parity tests assert byte/structure-identical results for the same input across facade / CLI / MCP / API for every new capability (structural check, `base` fix, best-practices score, and the walkthrough lifecycle steps).
- [ ] Public exports and the capability `REGISTRY` are updated so the new capabilities are discoverable through the same mechanism as existing capabilities; nothing is exposed on one surface but missing on another.
- [ ] Deterministic paths remain deterministic across surfaces: the structural check and the auto-suggestible portion of the best-practices score produce identical output on every surface, and there are NO accidental per-item LLM calls introduced in the deterministic paths (NFR-001).
- [ ] The walkthrough lifecycle is surfaced without duplicating the RIT-I-0015 orchestrator or the hard write gate — adapters call the RIT-T-0118 facade capability, which owns the gate.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
Mirror the existing adapter patterns exactly: add facade capabilities and register them in the facade `REGISTRY`; add thin CLI commands in `packages/cli`; add MCP tools in the MCP package (`tools.py`); add API routes in the API package. Adapters must be thin — all logic lives in the facade capabilities (which wrap the RIT-T-0115 `base` fixer, the RIT-T-0117 analyzer, and the RIT-T-0118 walkthrough); the adapters only translate transport-specific input/output. Reuse the established parity-test harness used by the existing scoring/edit capabilities and extend it to cover the four new capabilities across all four surfaces. Update public exports so the new capabilities are reachable identically to existing ones.

### Dependencies
- **RIT-T-0115** — `base` fixer capability being surfaced (blocking).
- **RIT-T-0117** — best-practices score / `BestPracticesReport` being surfaced (blocking).
- **RIT-T-0118** — `standard` walkthrough lifecycle being surfaced (blocking).
- Existing facade `REGISTRY`, CLI (`packages/cli`), MCP (`tools.py`), and API packages, plus the existing cross-surface parity-test harness.

### Risk Considerations
- **Surface drift**: a capability exposed on some surfaces but not all, or with diverging field names, breaks parity — mitigated by the parity test covering every capability on every surface as an acceptance gate.
- **Logic leaking into adapters**: any behavior implemented in an adapter rather than the facade capability risks per-surface divergence — keep adapters thin.
- **Accidental non-determinism**: an adapter or capability introducing an LLM call in a deterministic path would break parity — asserted against in the deterministic parity tests.
