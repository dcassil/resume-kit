# base fix driver (auto/interactive) writing name-base.json behind the faithfulness gate + surfaces

## Parent Initiative

[[RIT-I-0016]]

## Objective

Implement the **`base` fix driver** that turns the coded structural issues + fix affordances emitted by RIT-T-0114 into applied fixes and persists the result as `<name>-base.json` — the second version in the `original → base → standard` lineage (RIT-A-0003). Per that ADR, `base` is `original` after structural / format / parse fixes only, and the transition is governed by the **existing faithfulness gate**: presentation/structure may change, but claims/meaning may NOT.

The driver has two modes:
- **`auto`** — applies ONLY fixes whose affordance is `deterministic-auto-safe` (conventional section renames, date-format normalization, prohibited-PII stripping, placeholder removal, section ordering). It defers every `needs-judgment` item and reports what it deferred; it never changes claims or meaning and never fabricates.
- **`interactive`** — presents each coded issue to the user for **accept / reject / edit**, one item at a time.

On success the written `base` MUST pass both the improved `check_ats_structure` and the faithfulness gate, and the `base` config pointer (via RIT-T-0113's lineage pointer) is updated. The capability is exposed across all surfaces (facade + CLI + MCP + API) with a parity test, per the cross-surface norm.

## Acceptance Criteria

- [ ] **Auto mode is affordance-gated** — `auto` applies only `deterministic-auto-safe` fixes from RIT-T-0114's coded findings, defers all `needs-judgment` items, and returns a structured report of what was applied vs deferred (with codes). It never alters claims/meaning.
- [ ] **Interactive mode is per-issue** — `interactive` yields, for each coded issue, an accept / reject / edit decision; rejected issues are left unchanged, edited issues take the user's replacement, accepted issues apply the suggested fix.
- [ ] **Faithfulness-gated write** — The written `base` passes BOTH the improved `check_ats_structure` (structural score improves relative to `original`) AND the faithfulness gate. Any fix that would alter meaning is refused/deferred rather than written; a test proves a meaning-altering fix cannot reach `<name>-base.json`.
- [ ] **Config pointer updated** — On successful write, config points `base` at the new `<name>-base.json` artifact via the RIT-T-0113 lineage pointer + provenance (derived-from-`original`). Atomic-write semantics preserved; additive/backward-compatible.
- [ ] **Cross-surface parity** — Exposed via facade `REGISTRY` + CLI + MCP + API, and a parity test asserts identical behavior/output/lineage state across all four surfaces for the same input.
- [ ] **Integration test** — A fixture resume with (a) a renamed skills section, (b) inconsistent date formats, and (c) a street address yields, in `auto` mode, a faithful `<name>-base.json` that passes the structural check: the skills section is renamed to the conventional name, dates are normalized to one format, and the street address is stripped — with no change to any claim/meaning.

## Implementation Notes

### Technical Approach
- Consume RIT-T-0114's `AtsStructureReport` findings (code + affordance). Route strictly on affordance: `deterministic-auto-safe` ⇒ eligible for `auto`; `needs-judgment` ⇒ deferred in `auto`, surfaced for decision in `interactive`.
- Implement the deterministic transforms centrally and keep them **meaning-preserving by construction** (renames, date normalization, PII stripping, placeholder removal, ordering) — no transform may touch experience claims, metrics, or narrative content.
- **Reuse the faithfulness validator** (`resume_validate_faithfulness`); do NOT rebuild it. The write is behind a hard gate consistent with RIT-A-0001 — a `base` that fails faithfulness is never persisted.
- Add the capability to the facade `REGISTRY`, then thin adapters in CLI / MCP / API, mirroring the existing capability wiring so parity is structural, not incidental.
- Update the `base` pointer through RIT-T-0113's lineage pointer API rather than writing config fields directly, keeping resolution order (`standard ?? base ?? original`) consistent.
- Section renames/reorders performed here should agree with the conventional-name table RIT-T-0114 uses (which feeds RIT-I-0017's `customSections → KeywordZone` mapping).

### Dependencies
- **Blocked by RIT-T-0114** — needs the coded issues + fix affordances that drive auto/defer routing.
- **Blocked by RIT-T-0113** — needs the `base` lineage/config pointer to record the artifact.
- Reuses the existing faithfulness validator and the atomic-write config substrate.

### Risk Considerations
- A wrongly-classified transform slipping past the meaning-preserving invariant — mitigated by the central transform module, the faithfulness hard gate on write, and the explicit meaning-alteration-refused test.
- Surface drift (one surface behaves differently) — mitigated by the parity test.
- `auto` silently dropping items the user needed to know about — mitigated by the deferred-items report requirement.

## Verification

- Unit tests per transform (rename, date normalization, PII strip, placeholder removal, ordering) asserting the transform is applied correctly and is meaning-preserving.
- A faithfulness-preservation test proving `auto`-mode output passes the faithfulness gate and that a meaning-altering fix is refused/deferred and never written.
- A cross-surface parity test (facade/CLI/MCP/API identical output + lineage state).
- The end-to-end integration test (renamed skills section + inconsistent dates + street address ⇒ faithful, structurally-passing `base`; config `base` pointer updated).
