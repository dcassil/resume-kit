# Generic job-independent best-practices analyzer (deterministic-first) with auto-suggestible vs needs-user-input classification

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0016]]

## Objective **[REQUIRED]**

Build the **new job-independent best-practices analyzer** (Phase 3 of RIT-I-0016) that scores `base` on generic structure + wording quality and emits a `BestPracticesReport` (schema from RIT-T-0116). This engine does not exist today: it is distinct from the job-keyword-driven composite score and is computed **without any job description**. It reads **ScoreDoc** (the canonical deterministic read model from RIT-I-0017 — schema RIT-T-0105, projection `project_scoredoc` RIT-T-0106) for section/zone/entity/bullet segmentation and never re-derives segmentation from raw BuildDoc.

The analyzer is **deterministic-first**: every rule that can be computed mechanically (regex/wordlist/structural heuristics) runs in a reproducible, no-network deterministic core; any soft LLM-assisted judgment (e.g. "is this actually an accomplishment?") is confined behind a clearly separated boundary and is optional. Each finding is classified per RIT-T-0116 as `auto_suggestible` (we can propose a concrete truthful rewrite) or `needs_user_input` (the fix needs facts we don't have — e.g. a metric — so we emit a targeted elicitation prompt instead of fabricating). The report this produces is what the Phase 4 `standard` walkthrough consumes.

## Acceptance Criteria **[REQUIRED]**

Every rule below MUST have at least one **hit** case and one **clean** (no-false-positive) case in the table-driven tests.

- [ ] **AC-1 — Experience-bullet quality rules.** Detects: weak/duty openers ("Responsible for", "Duties included", "Worked on", "Helped with", "Assisted with", "Involved in"); first-person openers (`I`/`my`/`me`); missing strong action verb; missing action→result linkage; over-long bullets; multiple-accomplishments-per-bullet; buried result (result present but not foregrounded); duplicate bullets across jobs; equal-detail-per-job (no prioritization of recent/relevant roles).
- [ ] **AC-2 — Quantification & vagueness rules.** Detects quantification presence/absence and a vagueness wordlist: hedges ("significantly"), vague quantities ("many", "various", "numerous", "large"), and activity/vanity metrics ("attended 40 meetings" style — count of activity rather than outcome).
- [ ] **AC-3 — Buzzword / generic-language rules.** Detects a buzzword wordlist: self-descriptors ("hardworking", "results-driven", "team player"), pop titles ("rock star", "ninja", "guru"), evidence-free adjectives ("strategic", "innovative", "visionary" without supporting evidence), corporate filler, and unsupported superlatives ("best", "leading", "world-class").
- [ ] **AC-4 — Summary rules.** Flags summary length/shape problems (too long, too short, or otherwise off-pattern for a professional summary).
- [ ] **AC-5 — Skills-section hygiene rules.** Detects: proficiency bars/ratings, foundational/assumed tools (e.g. email, web browsing), over-long inventory, duplicate skills, and the "all technical skills only appear in the skills section" (tech never demonstrated in experience) pattern.
- [ ] **AC-6 — Length / relevance rules.** Flags overall length/relevance problems at the whole-document level.
- [ ] **AC-7 — Whole-document consistency rules.** Detects inconsistency in tense, punctuation, capitalization, first/third person, and date format across the document.
- [ ] **AC-8 — Resolution classification.** Every finding is classified `auto_suggestible` vs `needs_user_input` per RIT-T-0116. Concretely: a duty→accomplishment conversion or a "quantify this" finding is `needs_user_input` and carries a **targeted `elicitation_prompt`**; a buzzword removal or a mechanical rewrite is `auto_suggestible` and carries a concrete `suggested_change`. Classification is asserted per rule in tests.
- [ ] **AC-9 — Deterministic core reproducibility + offline.** For a fixed input the deterministic path produces byte-identical findings across repeated runs and executes with **no network access**. A determinism test runs the analyzer twice on a fixture and asserts equal output.
- [ ] **AC-10 — LLM assist is isolated and optional.** Any LLM-assisted soft judgment is behind a clear boundary (an injectable/optional component), is off by default in the deterministic path, and its findings are marked as assisted (per the RIT-T-0116 provenance marker). With the assist disabled, the full rule set above still runs deterministically.
- [ ] **AC-11 — Reads ScoreDoc, not raw BuildDoc.** The analyzer consumes ScoreDoc segmentation (sections/zones/entities/bullets from `project_scoredoc`, RIT-T-0106) for locating findings; it does not hand-roll section segmentation or read raw BuildDoc fields (e.g. `additional.technicalSkills`) directly. Findings' `location` locators are ScoreDoc-consistent.
- [ ] **AC-12 — Emits a valid `BestPracticesReport`.** Output validates against the RIT-T-0116 schema, with correct `severity` assignment per the mapping guidance (wording-quality → warning/recommendation; any soft LLM-assist judgments → review-note) and no generic finding assigned `hard_gate`.

## Test Cases **[CONDITIONAL: Testing Task]**

### Test Case 1: Per-rule hit/clean table
- **Test ID**: TC-001
- **Preconditions**: Analyzer built; RIT-T-0116 schema available; ScoreDoc fixtures for crafted resume fragments.
- **Steps**:
  1. For each rule (AC-1..AC-7), feed a fragment that should trigger it and assert the expected `rule_code` appears with the expected `location` and `severity`.
  2. For each rule, feed a clean fragment and assert the rule does NOT fire (no false positive).
- **Expected Results**: Every rule has a passing hit case and a passing clean case.
- **Status**: Pass/Fail/Blocked

### Test Case 2: Resolution-kind classification
- **Test ID**: TC-002
- **Preconditions**: Analyzer built.
- **Steps**:
  1. Feed a duty-opener bullet with no metric; assert the finding is `needs_user_input` and carries a non-empty `elicitation_prompt`.
  2. Feed a buzzword-laden summary; assert the finding is `auto_suggestible` and carries a concrete `suggested_change`.
- **Expected Results**: Classification and the paired suggestion/prompt match RIT-T-0116's invariant.
- **Status**: Pass/Fail/Blocked

### Test Case 3: Determinism + offline
- **Test ID**: TC-003
- **Preconditions**: LLM assist disabled (deterministic path).
- **Steps**:
  1. Run the analyzer twice on the same ScoreDoc fixture with no network available.
  2. Compare the two `BestPracticesReport` outputs.
- **Expected Results**: Identical output both runs; no network calls made.
- **Status**: Pass/Fail/Blocked

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Implement as the new job-independent best-practices analyzer described in the initiative's Detailed Design (a new analyzer module, or a new module within the ats package). Keep the deterministic rules **table-driven**: wordlists and compiled regexes for openers, buzzwords, vagueness, foundational tools, etc., so rules are data-editable and each maps to a stable `rule_code` from RIT-T-0116.
- Read segmentation from ScoreDoc (`project_scoredoc`, RIT-T-0106) — iterate sections/zones/entities/bullets from the canonical read model; emit `location` locators in the ScoreDoc-consistent vocabulary the schema expects.
- Keep the LLM assist behind a clear, injectable boundary (e.g. an optional judgment provider) that defaults off; the deterministic core must fully function without it. Mark any assisted finding via the report/item provenance marker from RIT-T-0116.
- Build the `BestPracticesReport` as the single output; do not print a second ATS-view (RIT-I-0017 owns the "what the ATS sees" report). Assign severities per RIT-A-0003/RIT-A-0004 mapping guidance; never assign `hard_gate` to a generic wording finding.

### Dependencies
- `blocked_by: [RIT-T-0116, RIT-T-0106]` — needs the `BestPracticesReport` schema + severity taxonomy (RIT-T-0116) and the ScoreDoc projection `project_scoredoc` (RIT-T-0106). Per RIT-A-0003's ordering decision, 0017's projection lands before this engine so the rules are authored against ScoreDoc from the start.
- Downstream: Phase 4 `standard` walkthrough (RIT-I-0015 orchestrator + hard write gate) consumes this report; Phase 5 surfaces/skills serialize it.

### Risk Considerations
- **False positives** from wordlist/regex rules erode trust; the mandatory clean-case per rule guards against this, and severity stays at warning/recommendation (advice, not a blocker).
- **Segmentation drift** if the analyzer re-derives sections instead of reading ScoreDoc — explicitly forbidden by AC-11; author rules against ScoreDoc.
- **Accidental LLM calls in the deterministic path** would break determinism/offline guarantees; the isolation boundary (AC-10) plus the offline determinism test (AC-9/TC-003) guard this.
- **Fabrication temptation**: `needs_user_input` items must elicit real facts, never auto-fill metrics — enforced by classification (AC-8) and, downstream, the truth gate in the walkthrough.
