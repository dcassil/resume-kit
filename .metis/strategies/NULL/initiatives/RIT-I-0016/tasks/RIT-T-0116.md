# BestPracticesReport schema + shared severity taxonomy (owned here; adopted by RIT-I-0018)

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0016]]

## Objective **[REQUIRED]**

Define, in `packages/schemas`, the structured `BestPracticesReport` schema that the generic job-independent best-practices analyzer (RIT-T-0117) emits, and the **single grooming-finding severity taxonomy** used across the whole system. This is the load-bearing data-contract task for Phase 3 of the initiative: the analyzer produces this report, the `standard` walkthrough (Phase 4) consumes it item-by-item, the surfaces/skills (Phase 5) serialize it, and — per [[RIT-A-0004]] — RIT-I-0018's industry-guidance audit **adopts** the severity taxonomy defined here rather than minting a competing one.

Two things are being fixed here so downstream work has one stable contract to build against:

1. The **shape of a flagged item** — a stable rule code, a human-readable message, a target location/path into the resume, a `severity`, a `resolution_kind` (auto-suggestible vs needs-user-input), and either a concrete suggested change or a targeted elicitation prompt.
2. The **severity enum itself** — defined exactly once here as the shared vocabulary (`hard-gate / warning / recommendation / review-note / out-of-scope-future`), documented as the taxonomy RIT-I-0018 adopts, with mapping guidance for which rule classes map to which severity and why `hard-gate` is reserved.

No analyzer logic is built in this task; this is schema + taxonomy + validation/serialization tests + a fixture instance only. RIT-T-0117 depends on this task and consumes its output.

## Acceptance Criteria **[REQUIRED]**

- [ ] **AC-1 — `BestPracticesReport` schema exists in `packages/schemas`.** A new schema (e.g. `best_practices.py` in `resume_kit_schemas`, exported from the package `__init__`) defines a `BestPracticesReport` containing at minimum: a schema/format version marker, the target resume version identity it was computed against (e.g. `standard`/`base` version pointer or document id), an ordered list of flagged items, and a deterministic-vs-assisted provenance marker on the report and/or per item (so the deterministic core is distinguishable from any LLM-assisted finding — mirrors the engine's "deterministic seed, enriched recommendations" contract). The report is a plain data object with no analyzer/engine imports.
- [ ] **AC-2 — Flagged-item shape.** Each item carries all of: (a) a **stable `rule_code`** (string, stable identifier such as `WEAK_OPENER`, `BUZZWORD`, `MISSING_QUANTIFICATION`); (b) a **human-readable `message`**; (c) a **target `location`/path** identifying where in the resume the finding applies (section/zone/entity/bullet reference consistent with ScoreDoc segmentation — a structured locator, not a free-text guess); (d) a **`severity`** drawn from the shared enum; (e) a **`resolution_kind`** enum with exactly the two values `auto_suggestible` (a concrete, truthful rewrite is available) and `needs_user_input` (the fix requires facts the system does not have, e.g. a real metric); (f) an **optional `suggested_change`** (populated for `auto_suggestible`) OR an **optional `elicitation_prompt`** (populated for `needs_user_input`) — the schema must make it representable that exactly one of these two is present per item and validation rejects an item that has neither or that pairs the wrong one with its `resolution_kind`.
- [ ] **AC-3 — Severity taxonomy defined ONCE.** A single `Severity` enum is defined with exactly five members: `hard_gate`, `warning`, `recommendation`, `review_note`, `out_of_scope_future` (wire/string spellings `hard-gate`/`warning`/`recommendation`/`review-note`/`out-of-scope-future` aligned to RIT-A-0003 / RIT-A-0004 wording). It is defined in exactly one place and re-exported; no second severity enum exists anywhere in the codebase (grep-verifiable). Its docstring/module doc names it the shared grooming-finding taxonomy and cross-references [[RIT-A-0003]] (owner) and [[RIT-A-0004]] (adopter).
- [ ] **AC-4 — Documented mapping guidance.** The module (or a co-located doc) states the mapping rule: which rule classes map to which severity — e.g. buzzword/quantification/wording-quality findings → `warning`/`recommendation`; soft LLM-assist judgments → `review_note`; layout/parse-risk items that need source-file inspection (REQ-011) → `out_of_scope_future`; and **`hard_gate` is reserved for truth/faithfulness-class failures and requires explicit per-item justification** (generic best-practices advice must never be silently promoted to a blocker). This matches RIT-A-0004's mapping rule (lane-1 → warning/recommendation, lane-2 → review-note, lane-6 → out-of-scope-future).
- [ ] **AC-5 — Additive / backward-compatible.** The new schema does not modify or break existing result schemas (`results.py`, `analysis.py`, etc.); existing consumers and tests continue to pass unchanged. `BestPracticesReport` is a new type, not a mutation of an existing one.
- [ ] **AC-6 — Validation + serialization round-trip tests.** Schema-level tests prove: construction validation (rejects an item missing a required field, rejects the `resolution_kind` / suggested-vs-elicitation mismatch from AC-2, rejects an unknown `severity` value), and a serialize → deserialize round-trip that reproduces an equal object for a report containing multiple items.
- [ ] **AC-7 — Fixture report instance covering the full matrix.** A committed fixture `BestPracticesReport` instance contains at least one item for **every** severity value AND at least one item of **each** `resolution_kind` (so both `auto_suggestible` with `suggested_change` and `needs_user_input` with `elicitation_prompt` are exercised), and a test asserts the fixture is valid and round-trips.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Add the schema alongside the other pure data models in `packages/schemas/src/resume_kit_schemas/` (e.g. `best_practices.py`), following the existing style in `results.py` / `analysis.py` (same base model / config conventions, same serialization approach the package already uses). Keep it purely declarative: no engine, no I/O, no LLM imports.
- Model `severity` as a string enum with the five members in AC-3; model `resolution_kind` as a two-member string enum. Align the wire spellings with the ADR wording (`hard-gate`, `out-of-scope-future`, etc.) so the taxonomy reads identically across RIT-A-0003/RIT-A-0004 and the code.
- Enforce the AC-2 "exactly one of suggested_change / elicitation_prompt, correctly paired with resolution_kind" invariant with a model validator rather than leaving it to callers, so both the analyzer and any adapter get the guarantee for free.
- Make the `location` locator structured and consistent with the ScoreDoc segmentation vocabulary (section / zone / entity / bullet index) so RIT-T-0117 can emit locators the walkthrough can resolve — do not model it as a free-text string.
- Put the taxonomy docstring and mapping guidance next to the enum so the "defined once, adopted by 0018" statement lives with the code, and cross-reference both ADRs by short code.

### Dependencies
- No task dependencies — `blocked_by: []`. Schema and taxonomy design are independent of the analyzer and the ScoreDoc projection; downstream analyzer (RIT-T-0117) depends on THIS, not the reverse.
- Coordinates with [[RIT-A-0003]] (taxonomy owner) and [[RIT-A-0004]] (taxonomy adopter, RIT-I-0018) — this task is the concrete embodiment of the "defined once" decision.

### Risk Considerations
- **Taxonomy drift / duplication** is the primary risk: if a second severity enum appears (e.g. in RIT-I-0018 or in an adapter), the shared-vocabulary decision is broken. Mitigate by defining it once, re-exporting, and adding a test/grep expectation that there is a single definition.
- **Over-modeling the locator** could couple the schema to ScoreDoc internals; keep the locator to the stable segmentation vocabulary (section/zone/entity/bullet), not ScoreDoc implementation details.
- **Premature hard-gates**: the schema permits `hard_gate` but the mapping guidance and reserved-justification note (AC-4) must make clear it is not for generic advice — the anti-goal called out in RIT-A-0004.
