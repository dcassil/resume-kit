# Version lineage substrate: ProjectConfig base/standard pointers + provenance + resolution (standard, base, original)

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0016]]

## Objective **[REQUIRED]**

Add the optional, additive version-lineage substrate to `ProjectConfig` (`packages/facade/src/resume_kit_facade/project_config.py`, class at ~line 53) so the project can persist the `base` and `standard` pointers RIT-I-0016 produces, and provide the single resolution rule — `standard ?? base ?? original` — that makes `standard` the default tailoring input. Today `ProjectConfig` declares only `active_resume`, `active_job`, `alias_file`, `active_resume_source`, `active_job_source`, `evidence_file`, `active_evidence`; there is NO version pointer beyond the active resume. This is Phase 1 of the initiative and the foundation every later phase writes into: the `base` fixer, the `standard` walkthrough, and `set-active`/tailoring resolution all depend on these fields and this resolver existing first. The change must be strictly backward compatible (existing `-original`-only configs load and behave unchanged) and preserve the atomic-write guarantee established in RIT-T-0091.

## Acceptance Criteria

## Acceptance Criteria

## Acceptance Criteria **[REQUIRED]**

- [ ] `ProjectConfig` gains optional, defaulted `base` and `standard` document-pointer fields, plus source/provenance fields mirroring `active_resume_source` (enough to record that each version was derived from its predecessor — e.g. `base_source` / `standard_source` or equivalent provenance capturing predecessor + derivation stage). All new fields default to `None`.
- [ ] A resolution helper (e.g. `resolve_active_resume(config)`) returns the active tailoring input as `standard ?? base ?? original`, where `original` is the current `active_resume`. Unit tests cover every fallback: standard-present, base-present-no-standard, original-only (legacy), and all-absent.
- [ ] `set-active` / active-resume resolution across the facade honors the new precedence so tailoring capabilities receive `standard` when present.
- [ ] Fully backward compatible: a config JSON containing only `active_resume` (and other legacy keys) loads via `load_config`, validates, and behaves exactly as today; the new fields being absent is not an error.
- [ ] Atomic write preserved: `save_config` continues to write through the temp-file + `os.replace` path (RIT-T-0091) with the new fields, and a simulated mid-write failure leaves no half-written config. `extra="allow"` round-tripping of unknown keys is unbroken.
- [ ] Round-trip test (load → save → load) preserves all pointers and provenance exactly; a schema-validation test asserts the model rejects malformed types for the new fields.

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
- Extend the Pydantic `ProjectConfig` model with `base: str | None = None`, `standard: str | None = None`, and provenance fields mirroring `active_resume_source` (e.g. `base_source` / `standard_source`, or a small provenance shape recording predecessor path + stage). Document each new attribute in the class docstring alongside the existing ones.
- Add the resolution helper where active-resume is resolved (in `project_config.py` next to `load_config`/`save_config`), returning `config.standard or config.base or config.active_resume`. Route facade active-resume consumers and `set-active` through it so precedence lives in exactly one place.
- Do NOT change `save_config`'s atomic mechanism — the new fields serialize through the existing temp-file + `os.replace` path unchanged; `extra="allow"` continues to preserve unknown keys.
- Keep the change additive: no existing field renamed or removed; no existing consumer's behavior altered when the new fields are `None`.
- Coordinate with [[RIT-A-0003]] / [[RIT-A-0002]]: the `base`/`standard` pointers are owned HERE; RIT-I-0017 is additive scoring only and introduces no competing config pointer — no conflict to reconcile.

### Dependencies
- None blocking (Phase 1 foundational; independent of the ScoreDoc/BuildDoc work in RIT-I-0017). Builds on the existing `ProjectConfig` + atomic `save_config` (RIT-T-0091). Downstream phases (base fixer, standard walkthrough, set-active wiring) depend on this task.

### Risk Considerations
- Risk: a consumer reads `active_resume` directly and bypasses the new precedence. Mitigation: centralize resolution in one helper and route facade consumers through it; add a test asserting tailoring input honors `standard` when present.
- Risk: breaking legacy configs. Mitigation: all new fields optional/defaulted; committed legacy fixture test.
- Risk: provenance shape churn if later phases need more fields. Mitigation: keep provenance minimal but sufficient (predecessor + stage); additive extension remains cheap under `extra="allow"`.
