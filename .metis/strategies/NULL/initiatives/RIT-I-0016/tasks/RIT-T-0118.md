# standard walkthrough capability on the edit-session orchestrator (elicitation + truth-gated rewrites + writes standard)

## Parent Initiative **[CONDITIONAL: Assigned Task]**

[[RIT-I-0016]]

## Objective **[REQUIRED]**

Implement the human-in-the-loop `standard` walkthrough: a capability that takes the user item-by-item through the `BestPracticesReport` flagged on `base` and, on acceptance, writes `<name>-standard.json` and repoints config `standard` at it. Auto-suggestible items are proposed directly; needs-user-input items pose a targeted elicitation question, take the user's real supplied fact, and generate a truthful rewrite that MUST pass the truth validator before it can be applied. The walkthrough runs as an edit session on the RIT-I-0015 edit-session orchestrator (`packages/facade/src/resume_kit_facade/edit_session.py`: `open` / `decide` / `commit_session`) behind the hard write gate (RIT-A-0001); every accept/reject/edit decision is logged via the existing feedback log. Per RIT-A-0003, this transition is governed by the truth gate — no fabricated metrics or unsupported claims may be introduced.

## Acceptance Criteria **[REQUIRED]**

- [ ] The walkthrough iterates the flagged items of the `BestPracticesReport` (from RIT-T-0117, shape RIT-T-0116) computed against `base`, mapping each item to a `ChangeProposal` and feeding it into the RIT-I-0015 edit-session orchestrator lifecycle (`open` → `decide` → `commit_session`); it does NOT construct its own writer or bypass the hard write gate.
- [ ] For every item classified `auto_suggestible`, a concrete rewrite is proposed directly (no user fact required) and surfaced for accept/reject/edit.
- [ ] For every item classified `needs_user_input`, the walkthrough emits a targeted elicitation prompt (e.g. "What changed because of your work — e.g. reliability, cost, or time saved, and by roughly how much?") and produces a rewrite ONLY from the user's supplied fact; with no user fact supplied it never fabricates a metric, scope, team size, or outcome, and defers the item instead.
- [ ] Every applied rewrite passes the hardened (post-RIT-T-0112) truth gate on the post-apply artifact; a `CONTRADICTED` (or `UNSUPPORTED`, per truth semantics) result refuses that specific change, keeps the session open, and surfaces the reason to the user rather than writing it.
- [ ] Accept, reject, and edit decisions are each recorded via the existing feedback log (the same log that feeds preference learning) — no new feedback store is introduced.
- [ ] On accept-all (session commit), `<name>-standard.json` is written behind the write gate and the config `standard` pointer (RIT-T-0113) is updated with source provenance, so that active-resume resolution (`standard ?? base ?? original`) now resolves `standard` as the tailoring default.
- [ ] The capability works with agent-authored proposals AND provider-generated ones (provider optional / pluggable), consistent with RIT-A-0001; when no provider is configured the deterministic/agent path still completes a walkthrough.
- [ ] Aborting or rejecting-all leaves no `standard` artifact and no config mutation; the session is discardable without side effects (config untouched, feedback log records the rejections only).

## Implementation Notes **[CONDITIONAL: Technical Task]**

### Technical Approach
Reuse the RIT-I-0015 edit-session lifecycle in `packages/facade/src/resume_kit_facade/edit_session.py` (`open` / `decide` / `commit_session`) and its hard write gate (RIT-A-0001); do NOT rebuild the gate or the writer. The walkthrough is a driver that: (1) loads the `base` artifact and the `BestPracticesReport` produced by the RIT-T-0117 analyzer, (2) maps each flagged report item to a `ChangeProposal` the orchestrator understands, (3) for `needs_user_input` items, renders the item's elicitation prompt, collects the user's fact, and synthesizes a truthful rewrite proposal from that fact (agent-authored or provider-generated), (4) submits each proposal through `decide`, letting the orchestrator's post-apply truth validation (`resume_validate_truth`, hardened by RIT-T-0112) gate application, (5) records each decision through the existing feedback log, (6) on `commit_session`, writes `<name>-standard.json` and updates the config `standard` pointer (RIT-T-0113). Truth checking reuses `resume_validate_truth` / `candidate_evidence_build` — nothing new is validated. The classification (`auto_suggestible` vs `needs_user_input`) is consumed from the report, not recomputed here.

### Dependencies
- **RIT-T-0117** — the best-practices analyzer that emits the `BestPracticesReport` this walkthrough iterates (blocking).
- **RIT-T-0115** — the `base` fixer, which produces the `base` artifact the report is computed against (blocking).
- **RIT-T-0112** — truth-gate hardening, which this walkthrough's per-change gate relies on for its `CONTRADICTED`/`UNSUPPORTED` refusal semantics (blocking).
- **RIT-T-0113** — config `standard` pointer (consumed on commit; not listed as blocker per initiative sequencing but required for the pointer-update criterion).
- **RIT-I-0015** — edit-session orchestrator + hard write gate + feedback log (already landed).

### Risk Considerations
- **Fabrication leak** on `needs_user_input` items is the load-bearing risk: mitigated by requiring a user-supplied fact before any rewrite is generated AND by the mandatory post-apply truth gate that refuses `CONTRADICTED`/`UNSUPPORTED` changes. Both guards must be present; neither alone is sufficient.
- **Gate bypass**: mitigated by routing every change exclusively through the orchestrator's `decide`/`commit_session` — the driver holds no independent write path.
- **Partial-commit consistency**: refused items must not block accepted ones, but an aborted session must leave config and the filesystem untouched (verified below).
