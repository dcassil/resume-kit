# T4: check-gaps proof contract + shared config-pointer doc

## Parent Initiative **[REQUIRED]**

[[RIT-I-0024]]

## Objective **[REQUIRED]**

Reconcile the injectability proof contract between `check-gaps` and `tailor-resume`, and add a single
shared config-pointer contract doc so skills stop referencing pointer/lineage fields ad hoc.
`check-gaps` requires a distinct master resume to classify injectable vs non-injectable, while
`tailor-resume` (post-RIT-I-0023) leans on Flow 1 learning-evidence — the two docs describe the proof
surface differently.

## Acceptance Criteria **[REQUIRED]**

- [ ] `check-gaps/SKILL.md` and `tailor-resume/SKILL.md` agree on what proves injectability: a distinct
      master resume AND/OR Flow 1 learning-evidence, stated the same way in both.
- [ ] The reconciled contract is explicit about what happens when neither a master nor learning-evidence
      is present (gap analysis degrades to keyword-only, clearly labeled).
- [ ] A new `_shared/config-pointers.md` enumerates and defines `active_resume`, `base_resume`,
      `structure_resume`, `refine_resume`, `final_resume`, `active_evidence`, `alias_file`, and the
      lineage/resolution order.
- [ ] `_shared/prerequisites.md` references the new config-pointer doc.
- [ ] Plugin markdown/slug tests remain green.

## Implementation Notes **[REQUIRED]**

### Technical Approach
- Doc-only. Derive the pointer semantics from `ProjectConfig` (`resume_kit_facade.project_config`) so
  the shared doc matches the actual code-owned state contract; do NOT invent fields.
- Reconcile the two skill docs to one proof statement; cross-link them.

### Dependencies
- [[RIT-I-0014]] code-owned `ProjectConfig` state contract.
- [[RIT-I-0023]] `tailor-resume` + Flow 1 learning-evidence surface.

### Risk Considerations
- Keep the shared doc accurate to the current config schema; a wrong pointer name is worse than none.
- Do NOT change scoring/gap code — this is a documentation-contract reconciliation only.

### Recommended Agent
`sonnet + medium` — doc reconciliation grounded in the real `ProjectConfig` schema.
