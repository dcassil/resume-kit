# T1: Durable full-resume learning seed + no-custom handoff policy

## Parent Initiative **[REQUIRED]**

[[RIT-I-0023]]

## Objective **[REQUIRED]**

Add the code-owned substrate Flow 1 needs: seed/merge durable evidence-learning from the full source resume,
including content that will not live in the prepared resume JSON, and define the no-custom handoff policy so
ambiguous/custom content is preserved in learning rather than guessed or dropped.

## Acceptance Criteria **[REQUIRED]**

- [ ] Evidence extraction covers summary, work headers, work bullets, projects, education, technical skills,
      certifications/training, languages, awards, and source custom/unmapped content.
- [ ] A code-owned merge writer persists full-resume evidence into `resume-kit/learning` or the active
      evidence file with deterministic content-addressed IDs and idempotent dedupe.
- [ ] Existing confirmed/user evidence is preserved on merge; rerunning Flow 1 does not delete or duplicate
      prior learning.
- [ ] Source metadata is recorded well enough to trace an evidence item back to the source resume section or
      custom section.
- [ ] The shape/no-custom policy is explicit: prepared output omits custom holding sections, while ambiguous
      content is retained in learning/evidence and accounted for by ledger/provenance.
- [ ] Backward compatibility for existing `ResumeDocument.customSections` inputs remains intact.

## Implementation Notes **[REQUIRED]**

### Technical Approach
- Extend `resume_kit_evidence.build_candidate_evidence` or add a sibling extractor that accepts the source
  BuildDoc/ResumeDocument before no-custom projection.
- Add a facade-level persistence helper/capability only if needed so skills do not hand-edit JSON.
- Reuse `ProjectConfig.active_evidence` / `evidence_file` conventions where possible.
- Keep the content-addressed ID behavior stable; avoid order-based IDs.

### Dependencies
- Existing `resume_kit_evidence`, `CandidateEvidence`, `add-evidence`, and project config state contract.
- Existing shape pass and content ledger from [[RIT-I-0019]].

### Risk Considerations
- Content loss is the primary risk. Tests must prove every custom/unmapped source text line is either mapped
  into a canonical section or present as learning/evidence.
- Do not make learning records a bypass for truth gates; they are proof inputs, not direct edits.

### Recommended Agent
`opus + high` — touches evidence durability and the no-content-loss handoff between shape and learning.
