# build_perfect over reused suggest/apply/learn loop + auto-fit

## Parent Initiative **[REQUIRED]**

[[RIT-I-0021]] — Phase 4 of 7. The orchestration spine (REQ-001/004/005/008/011, NFR-003/004).

## Objective **[REQUIRED]**

Add the `build_perfect` facade capability that ties the stage together: resolve the **tailored**
resume for a given job + its job description, run Phase 1 budget enforcement, ask Phase 2 rankers
for ordered trim candidates + Phase 3 compression candidates, express each as a `ChangeProposal`,
and drive them through the **reused** [[RIT-I-0015]] edit-session orchestrator behind the
[[RIT-A-0001]] hard write gate — applying via the [[RIT-A-0005]]/[[RIT-T-0124]] shared
change-application runbook and recording accept/reject through the [[RIT-I-0013]] feedback loop.
Write the job-specific `final` artifact + pointer + provenance; **never mutate master lineage**.
Include an opt-in **auto-fit** mode that applies the default ranking to budget without prompts
(still logged, still gated, tied/ambiguous cases deferred for a human).

## Acceptance Criteria **[REQUIRED]**

- [ ] `build_perfect(root, *, job, decisions=None, auto_fit=False) -> BuildPerfectResult` in
      `resume_kit_facade`, mirroring the `build_*` shape of prior passes.
- [ ] Resolves the tailored resume for `job` + the active job description; runs `budget_enforce`;
      builds ranked trim + compression `ChangeProposal`s.
- [ ] **Reuse (NFR-004), not reimplementation:** trims/compressions flow through
      `open_session`/`prompt_session`/`decide_change`/`reconcile_session`/`commit_session` behind
      the [[RIT-A-0001]] gate, applied via the shared change-application runbook. A test asserts
      `perfect` routes through these existing capabilities rather than a bespoke apply path.
- [ ] Accept/reject decisions recorded via `record-edit-feedback`, folding into
      `refresh-preferences`/`rank-edit-candidates` ([[RIT-I-0013]]) — no new feedback store.
- [ ] **Content ledger accounting:** every removed unit is accounted as
      `dropped_by_explicit_decision` (interactive) or `dropped_by_ranked_budget` (auto-fit);
      compressions ledgered as `compressed`; unaccounted loss fails the Phase 1 ledger gate.
- [ ] **Auto-fit mode:** applies default job-weighted ranking to budget without per-item prompts;
      `log()`s exactly what it dropped (no silent truncation); ties/ambiguous cases are **deferred**
      (left for a human), not auto-cut; still passes truth/claim + ledger gates.
- [ ] **Lineage/provenance (REQ-011, NFR-003):** writes `<name>-<job>-final.json` (or equivalent) +
      a job-keyed `final`/`perfect` pointer with provenance back to the tailored source + job.
      A test asserts `structure`/`refine`/`base`/`original` are byte-unchanged (canonical Rule 8).
- [ ] Unit/facade tests for interactive + auto-fit paths, reuse assertions, and master
      non-mutation.

## Implementation Notes **[REQUIRED]**

### Technical Approach
- Implement in `resume_kit_facade` alongside the other `build_*` capabilities. Compose Phases 1–3
  (enforcer, rankers, compressor) — do not re-derive their logic here.
- Construct one `ChangeProposal` per candidate; hand to the existing edit-session facade
  (`open_session`/`prompt_session`/`decide_change`/`reconcile_session`/`commit_session`). Interactive
  mode surfaces ranked candidates for decisions; `review_at_end`/`auto` modes map to auto-fit.
- Feedback: call the existing `record-edit-feedback` per decision; do not touch the feedback store
  directly.
- `final` pointer lives in the code-owned `ProjectConfig` (from [[RIT-I-0014]]); key by job so
  multiple job-specific finals coexist from one master.

### Dependencies
- **Depends on Phases 1–3** ([[RIT-T-0142]], [[RIT-T-0148]], [[RIT-T-0149]]) and the reused stacks:
  [[RIT-I-0015]]/[[RIT-A-0001]] edit-session + gate, [[RIT-A-0005]]/[[RIT-T-0124]] change-application
  runbook, [[RIT-I-0013]] feedback (all on main). Transitively depends on RIT-I-0019 + RIT-I-0020.

### Risk Considerations
- The reuse mandate is the whole point — the biggest risk is an agent quietly writing a bespoke
  apply/feedback path. The reuse-assertion tests (NFR-004) are non-negotiable acceptance gates.
- Master non-mutation must be proven, not assumed — assert source files unchanged post-run.

### Recommended Agent
`opus + high` — multi-file orchestration across facade + three scoring modules + three reused
stacks; a wrong seam here creates compounding rework.
